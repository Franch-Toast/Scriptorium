# 函数调用与返回：AArch64栈帧与寄存器的逐步变化

> 本文是「栈回溯」系列的基础篇：把一次函数调用拆成**时刻 0 到时刻 8**，每执行一条指令就同时给出「寄存器面板」和「内存示意图」，让你亲眼看见栈帧是怎么长出来的、又是怎么拆掉的。
>
> 主线使用 AArch64（ARM64），因为性能采集工具（如 `perf_ebpf`）在车端与 QNX 环境中的目标平台正是它；文末第 8 节再用一节对照 x86-64 的等价过程。所有地址、汇编都是教学用示例，真实数值随编译器、优化等级与 ASLR 变化。

> **本系列**：本文（调用与返回的逐步变化） → [三种栈回溯方法总览](./栈回溯方法/三种栈回溯方法总览.md) → [FP帧指针链回溯](./栈回溯方法/FP帧指针链回溯.md) / [DWARF-CFI回溯](./栈回溯方法/DWARF-CFI回溯.md) / [eBPF栈采样](./栈回溯方法/eBPF栈采样.md)。

## 1. 先把画面建立起来

### 1.1 调用栈：一叠写有回程信息的便签

当 `main` 调用 `process`、`process` 又调用 `checksum` 时，程序会形成一条逻辑调用链：

```text
源码调用方向（外层调用内层）
main -> process -> checksum
```

这条链在内存里的物理形态，是线程自己的栈上叠起来的一串**栈帧（frame）**。可以把每个栈帧想成一张便签，上面至少写着：

- 我执行完之后，要回到调用者的哪个位置（**返回地址**）；
- 调用者的栈基准在哪里（**保存的帧指针**）；
- 我的局部变量放在哪。

同一时刻，调用链有三种等价但方向不同的表示，后面看到「调用栈反了」时先分辨是哪一种：

```text
源码调用方向（外层调用内层）
main -> process -> checksum

栈回溯输出的自然方向（当前帧回到调用者）
checksum <- process <- main

pprof 的 Location 列表惯例（leaf first）
checksum, process, main
```

### 1.2 栈的方向：向低地址增长

arm64 的栈是「满递减栈」：栈向**低地址**方向生长，`SP` 始终指向当前栈顶（最低的已占用地址）。压入数据时地址变小，弹出数据时地址变大：

```text
高地址  ┌────────────────────────────┐
        │ 旧数据 / 外层帧            │
        ├────────────────────────────┤
        │      ↓ 入栈方向 ↓          │   保存数据：SP 变小
        ├────────────────────────────┤
        │ 新数据 / 内层帧            │ <- SP
        └────────────────────────────┘
低地址
```

记住一个总原则：**寄存器是 CPU 内部的格子，快但极少；栈是内存里的区域，大但慢。函数调用与返回，就是在寄存器和栈之间成对地「保存与恢复」。**

## 2. 出场人物：寄存器与栈的约定

### 2.1 本文故事里会用到的寄存器

AArch64 有 31 个通用寄存器（`x0`–`x30`）加 `SP`。本文的调用链只围绕其中几个展开，先认识它们：

| 寄存器 | 角色 | 在本文中的任务 |
| --- | --- | --- |
| `x0`–`x7` | 参数与返回值寄存器 | `w0` 递进参数 `11`；函数算完后用 `w0` 带回结果 `40` |
| `x29` | 帧指针 FP（Frame Pointer） | 当前帧的「页眉」：`[x29]` 是上一帧 FP，`[x29+8]` 是返回地址 |
| `x30` | 链接寄存器 LR（Link Register） | 保存「回到调用者」的地址；`bl` 写入它，`ret` 读取它 |
| `SP` | 栈指针（Stack Pointer） | 栈的游标；`stp`/`ldp`/`sub`/`add` 都会移动它 |
| `PC` | 程序计数器（Program Counter） | 指向正在执行的指令；只有 `bl`/`ret`/`b` 等控制流指令能改写它 |

「31 个寄存器」里其余成员快速一瞥，混个脸熟即可：

| 分组 | 成员 | 用途 |
| --- | --- | --- |
| 参数区 | `x0`–`x7` | 前 8 个整型/指针参数；`x0` 兼返回值 |
| 间接结果 | `x8` | 返回大结构体时传隐藏指针 |
| 临时区 | `x9`–`x15` | 编译器随手用，不跨调用保留 |
| 链接器专用 | `x16`/`x17`（IP0/IP1） | PLT 跳转等场景使用 |
| 平台寄存器 | `x18` | 部分系统保留给平台/线程环境 |
| 被调者保存区 | `x19`–`x28` | 想用就必须先备份、返回前恢复 |
| 帧指针 | `x29` | 本文主角之一 |
| 链接寄存器 | `x30` | 本文主角之一 |

小写 `w0` 表示寄存器 `x0` 的低 32 位，用于 32 位整数运算；本文的 `int` 参数走 `w0`。

### 2.2 保存责任：caller-saved 与 callee-saved

比名字更重要的是**谁负责保住寄存器里的值**。ABI（应用二进制接口，可以理解成编译器之间的合同）把寄存器分成三派：

| 派别 | 成员 | 合同条款 | 通俗理解 |
| --- | --- | --- | --- |
| caller-saved（易失） | `x0`–`x18` | 调用者若在调用后还需要它，必须调用前自己保存 | 「借出去可能被弄脏，在乎就先抄一份」 |
| callee-saved（非易失） | `x19`–`x28`、`x29` | 被调者想用就必须先把旧值存起来，返回前恢复 | 「动用先押金，用完要赎回」 |
| 特殊 | `x30`（LR） | 任何函数只要还想返回，就不能弄丢它；要调用别人就先把 LR 存进自己栈帧 | 「唯一的返程票，转交前先拓印一份」 |
| 特殊 | `SP` | 双方共同维护：进入与离开时必须复原 | 「公共楼梯，谁走谁复原」 |

这张合同表直接决定了栈帧的内容：`x29` 属于 callee-saved，所以每个想拿它当帧指针的函数，序言里都要先把旧 `x29` 存进栈；`x30` 会在执行 `bl` 的瞬间被硬件覆盖，所以非叶子函数必须提前把 LR 存进栈。

### 2.3 与 x86-64 的三个关键差异

如果你接触过 x86-64 的 `call`/`push rbp`，先花一分钟看这三点差异，后面的每一时刻就不容易串台：

1. **返回地址不在栈上**。x86 的 `call` 会自动把返回地址压入栈；AArch64 的 `bl` 只是把它写进 `x30`（LR）寄存器。只有等函数决定「我接下来还要调用别人」时，才把 LR 保存进自己的栈帧。
2. **没有 push/pop 指令**。AArch64 用 `stp`/`ldp`/`str`/`ldr` 配合**前索引/后索引寻址**，一条指令就能完成「移动 SP + 存取多个寄存器」。
3. **SP 必须 16 字节对齐**。AArch64 要求栈指针在任何时刻都保持 16 字节对齐，所以栈的每一次移动都是 16 字节的倍数（这也是为什么你会看到预留 16、32 字节这样的数字）。

### 2.4 两个需要拆开读的原语

后文会反复看到这两条指令，先把它们的动作拆开：

```asm
stp x29, x30, [sp, #-16]!    ; 前索引（pre-index）：先减 SP，再存两个寄存器
```

它由两个动作组成：

```text
动作 ①：SP = SP - 16
动作 ②：[SP + 0] = x29     （把旧帧指针抄进新栈顶）
        [SP + 8] = x30     （把 LR 抄进新栈顶 + 8）
```

```asm
ldp x29, x30, [sp], #16      ; 后索引（post-index）：先取两个寄存器，再加 SP
```

它同样由两个动作组成：

```text
动作 ①：x29 = [SP + 0]     （取回旧帧指针）
        x30 = [SP + 8]     （取回 LR）
动作 ②：SP = SP + 16
```

两条指令互为镜像，是 AArch64 建帧与拆帧的核心动作。现在可以开始逐步跟踪了。

## 3. 可复现实验：stack_demo 与它的 AArch64 汇编

### 3.1 示例代码

后面的全部图示都围绕这组极小函数。它故意关闭内联、尾调用优化和帧指针省略，让每个源码函数都有一个清晰可见的物理栈帧：

```c
#include <stdio.h>

__attribute__((noinline))
static int checksum(int x) {
    volatile int local = x * 3;
    return local + 7;
}

__attribute__((noinline))
static int process(int x) {
    int result = checksum(x + 1);
    return result * 2;
}

int main(void) {
    int answer = process(10);
    printf("answer = %d\n", answer);
    return 0;
}
```

当程序停在 `checksum()` 的 `return local + 7` 附近时，逻辑调用链为：

```text
_start -> libc_start_main -> main -> process -> checksum
```

后续分析聚焦 `main -> process -> checksum` 三层。

### 3.2 编译配置和每个选项的作用

在 x86 主机上交叉编译到 AArch64：

```bash
aarch64-linux-gnu-gcc -O0 -g \
  -fno-omit-frame-pointer \
  -fno-optimize-sibling-calls \
  -fno-inline \
  -o stack_demo stack_demo.c
```

| 配置 | 教学中得到什么 | 关闭它后可能看到什么 |
| --- | --- | --- |
| `-O0` | 指令和源码较接近，局部变量常留在栈中 | 重排、寄存器化、删除无用变量，布局变化很大 |
| `-g` | DWARF 调试信息，可还原文件/行号 | 仍可有函数名，但通常没有可靠源码行 |
| `-fno-omit-frame-pointer` | 生成可链式遍历的 `x29` 链 | 帧指针链可能中断，回溯变浅 |
| `-fno-optimize-sibling-calls` | 避免尾调用把一个调用帧「折叠掉」 | 某个源码函数不形成物理栈帧 |
| `-fno-inline` | 避免函数直接嵌入调用者 | 调用关系仍可在 DWARF inline 信息中出现，但栈上没有独立帧 |

这里有一个工程取舍：保留帧指针会占用一个通用寄存器，关闭优化会严重影响性能，因此通常只在诊断构建或可接受性能损耗的模块中启用。

### 3.3 checksum 的近似汇编

为了讲解清晰，假设 `checksum()` 在 `-O0 -fno-omit-frame-pointer` 下生成如下近似汇编（示意，实际寄存器分配由编译器决定）：

```asm
checksum:
    stp  x29, x30, [sp, #-16]!  ; 保存旧 x29 与 LR，SP -= 16
    mov  x29, sp                ; x29 成为 checksum 栈帧的锚点
    sub  sp, sp, #16            ; 预留 16 字节局部空间
    mov  w1, #3
    mul  w1, w0, w1             ; w1 = x * 3
    str  w1, [sp]               ; local 写入栈（示意偏移）
    ldr  w0, [sp]               ; 取回 local
    add  w0, w0, #7             ; w0 = local + 7
    add  sp, sp, #16            ; 归还局部空间
    ldp  x29, x30, [sp], #16    ; 恢复 x29 与 LR，SP += 16
    ret                         ; PC = x30，跳回 process
```

从下文的时刻 0 开始，我们逐条指令跟踪这次调用，每一步都同时给出**寄存器面板**与**栈示意图**。

## 4. 逐步跟踪：时刻 0 到时刻 8

跟踪开始前，先交代 `process` 的现场（它是调用者，已经完成了自己的序言）：

```text
process 调用 checksum 之前：
  process.FP（x29） = 0x7fff_eff0
  SP                = 0x7fff_efd0   （process 局部空间已分配完毕）
  内存 [0x7fff_eff0] = 保存的 main.FP
  内存 [0x7fff_eff8] = 返回 main 的地址 0x401220
  PC                = 指向 process 中即将执行的 bl checksum
```

### 时刻 0：装载参数（`mov w0, #11`）

CPU 动作：把参数 `x + 1` 的结果 `11` 放进 `w0`（第 1 个整型参数寄存器）。

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `w0` | 旧值 | 11 | 第 1 个参数就位 |
| `PC` | 指向本条 `mov` | 指向 `bl checksum` | 顺序推进 |
| `SP` / `x29` / `x30` | 不变 | 不变 | 装参数不需要动栈 |

栈此刻没有任何变化，但出发前的行囊已经收拾完：`w0` 带着参数，`PC` 指向即将执行的 `bl`。

### 时刻 1：执行 `bl checksum`

`bl`（Branch with Link）的硬件动作可以拆成两步理解：

```text
1. x30（LR） = bl 之后那条指令的地址     （返程票写进寄存器）
2. PC        = checksum 的入口地址       （跳转）
```

执行前的现场：`PC = 0x4011dc`（`bl` 指令自身），`LR = 旧值`。执行后：

| 寄存器 | 执行前 | 执行后 | 变化说明 |
| --- | --- | --- | --- |
| `PC` | 0x4011dc | 0x401130 | 跳入 checksum 入口 |
| `x30`（LR） | 旧值 | 0x4011e0 | 返程票就位：`bl` 后下一条指令的地址 |
| `SP` | 0x7fff_efd0 | 0x7fff_efd0 | **不变**：AArch64 的 bl 不碰栈 |
| `x29` | 0x7fff_eff0 | 0x7fff_eff0 | 不变：checksum 还没有自己的锚点 |
| `w0` | 11 | 11 | 不变：参数等待被读取 |

这就是与 x86-64 最直观的差异：返回地址此刻只在**寄存器**里，栈上还什么都没有。

```text
此刻的栈：与 bl 之前完全相同

高地址
0x7fff_eff8  ┌──────────────────────────────────────┐
             │ 返回 main 的地址 0x401220            │
0x7fff_eff0  ├──────────────────────────────────────┤ <- process.FP = 0x7fff_eff0
             │ 保存的 main.FP = 0x7fff_f120         │
             ├──────────────────────────────────────┤
             │ process 帧：result 等局部数据        │
0x7fff_efd0  ├──────────────────────────────────────┤ <- SP = 0x7fff_efd0
             │ （process 预留区的下沿）             │
             └──────────────────────────────────────┘
低地址
```

需要警觉的是：`x30` 是**唯一的返程票**。checksum 只要再执行一次 `bl`（调用别的函数），这张票就会被覆盖。所以，一个「还要调用别人」的函数必须先把它保管到自己的栈帧里——这正是下一个时刻。

### 时刻 2：执行 `stp x29, x30, [sp, #-16]!`

按 2.4 的拆解，这条指令包含两个动作：

```text
动作 ①：SP = 0x7fff_efd0 - 16 = 0x7fff_efc0
动作 ②：[0x7fff_efc0] = x29 = 0x7fff_eff0   （替 process 保住它的锚点）
        [0x7fff_efc8] = x30 = 0x4011e0      （把返程票拓印到栈上）
```

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `SP` | 0x7fff_efd0 | 0x7fff_efc0 | 下移 16 字节：保存区开张 |
| `x29` | 0x7fff_eff0 | 0x7fff_eff0 | 值没变：这一步只是把它「抄」进栈 |
| `x30` | 0x4011e0 | 0x4011e0 | 值没变：同样只是「抄」进栈 |

```text
0x7fff_eff8  ┌──────────────────────────────────────┐
             │ 返回 main 的地址 0x401220            │
0x7fff_eff0  ├──────────────────────────────────────┤ <- process.FP
             │ 保存的 main.FP = 0x7fff_f120         │
             ├──────────────────────────────────────┤
             │ process 帧：result 等局部数据        │
0x7fff_efd0  ├──────────────────────────────────────┤ <- 调用前 process 的 SP
             │ （process 局部数据，不参与回溯）     │
0x7fff_efc8  ├──────────────────────────────────────┤
             │ 保存的 LR = 0x4011e0                 │ <- 本步新写入的返程票
0x7fff_efc0  ├──────────────────────────────────────┤ <- SP = 0x7fff_efc0
             │ 保存的 process.FP = 0x7fff_eff0      │ <- 本步新写入的押金
             └──────────────────────────────────────┘
低地址
```

为什么这两笔「存款」必须做？`x29` 属于 callee-saved——checksum 马上要把它当成自己的锚点，必须先替 process 保住旧值；`x30` 则随时会被 checksum 自己的 `bl` 覆盖，所以先拓印一份到栈上。

### 时刻 3：执行 `mov x29, sp`

CPU 动作：`x29 = SP = 0x7fff_efc0`。只动一个寄存器，却是整个帧指针链的奠基一步。

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `x29` | 0x7fff_eff0 | 0x7fff_efc0 | 锚点切换：checksum 的 FP 正式就位 |
| `SP` | 0x7fff_efc0 | 0x7fff_efc0 | 不变 |
| `PC` | 指向本条 `mov` | 指向下一条 `sub sp` | 顺序推进 |

栈内容与时刻 2 完全相同，但 `x29` 现在稳稳地指向那两个格子：

```text
0x7fff_efc8  ┌──────────────────────────────────────┐
             │ 保存的 LR = 0x4011e0                 │ <- [x29 + 8]
0x7fff_efc0  ├──────────────────────────────────────┤ <- x29 = SP = 0x7fff_efc0
             │ 保存的 process.FP = 0x7fff_eff0      │ <- [x29 + 0]
             └──────────────────────────────────────┘
```

从这一刻起，无论 `SP` 后面怎么移动，都有了一条稳定的公式：

```text
[x29 + 0] = 上一帧的 FP
[x29 + 8] = 返回地址
```

**经典的 FP 链两个格子就此就位**——第 5 节之后的「FP 链回溯」用的就是它们。

### 时刻 4：执行 `sub sp, sp, #16`

CPU 动作：`SP = SP - 16 = 0x7fff_efb0`。只为局部变量、临时值预留空间，**不写任何数据**。`x29` 纹丝不动。

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `SP` | 0x7fff_efc0 | 0x7fff_efb0 | 下移 16 字节，预留区开张 |
| `x29` | 0x7fff_efc0 | 0x7fff_efc0 | 不变：锚点将贯穿整个函数 |
| `PC` | 指向 `sub` | 指向函数体第一条指令 | 序言结束 |

```text
高地址
0x7fff_eff8  ┌──────────────────────────────────────┐
             │ 返回 main 的地址 0x401220            │
0x7fff_eff0  ├──────────────────────────────────────┤ <- process.FP = 0x7fff_eff0
             │ 保存的 main.FP = 0x7fff_f120         │
             ├──────────────────────────────────────┤
             │ process 帧：result 等局部数据        │
0x7fff_efd0  ├──────────────────────────────────────┤
             │                                      │
0x7fff_efc8  ├──────────────────────────────────────┤
             │ 保存的 LR = 0x4011e0                 │
0x7fff_efc0  ├──────────────────────────────────────┤ <- x29，整个函数期间保持稳定
             │ 保存的 process.FP = 0x7fff_eff0      │
             ├──────────────────────────────────────┤
             │ checksum 新预留的 16 字节            │
0x7fff_efb0  └──────────────────────────────────────┘ <- SP = 0x7fff_efb0
低地址
```

### 时刻 5：函数体运行——写入 `local`，产出返回值

函数体不是一条指令，但对寄存器和栈的改动只有两类：往预留区写数据，以及把最终结果放进 `w0`。设参数 `x = 11`：

| 寄存器 / 内存 | 变化 | 说明 |
| --- | --- | --- |
| `w0` | 11（读完即可复用）→ 40 | 参数抄进栈后使命完成；最后承载返回值 |
| `SP` | 0x7fff_efb0（不变） | 函数体内不再移动 |
| `x29` | 0x7fff_efc0（不变） | 锚点稳定，回顾随时可用 |
| `x30` | 0x4011e0（不变） | 本例没再调用别人，票还完好 |
| `[0x7fff_efb0]` | 写入 local = 33 | 函数体写入的数据（示意偏移） |
| `PC` | 在 checksum 内逐条推进 | 此刻停在 `return local + 7` 附近 |

```text
0x7fff_efc8  ┌──────────────────────────────────────┐
             │ 保存的 LR = 0x4011e0                 │
0x7fff_efc0  ├──────────────────────────────────────┤ <- x29 = 0x7fff_efc0
             │ 保存的 process.FP = 0x7fff_eff0      │
             ├──────────────────────────────────────┤
0x7fff_efb0  ├──────────────────────────────────────┤ <- SP = 0x7fff_efb0
             │ local = 33                           │ <- 函数体写入（示意偏移）
             └──────────────────────────────────────┘
低地址
```

此刻调用链 `main -> process -> checksum` 的每张便签都写好了。**这是全系列最重要的一个现场**——若采样恰好发生在这里，寄存器面板是：

```text
PC（x30 之外的另一个说法：当前指令地址） = checksum + 0x18 = 0x401148（示意）
SP   = 0x7fff_efb0
x29  = 0x7fff_efc0
x30  = 0x4011e0
w0   = 40
```

`FP帧指针链回溯`、`DWARF-CFI回溯`、`eBPF栈采样` 三篇文档，都从这个面板出发讲述各自的回溯算法。

### 时刻 6：执行 `add sp, sp, #16`（返回开始）

CPU 动作：`SP = SP + 16 = 0x7fff_efc0`。一步把 `SP` 拉回保存区底部，checksum 的局部空间被「整体作废」——数据其实还在内存里，只是已退出栈的有效范围，后续的新调用会覆盖它们。

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `SP` | 0x7fff_efb0 | 0x7fff_efc0 | 释放局部空间，回到保存区底 |
| `x29` | 0x7fff_efc0 | 0x7fff_efc0 | 不变（马上要恢复成 process 的值） |
| `w0` | 40 | 40 | 返回值原地等待 |

```text
0x7fff_efc8  ┌──────────────────────────────────────┐
             │ 保存的 LR = 0x4011e0                 │
0x7fff_efc0  ├──────────────────────────────────────┤ <- SP = 0x7fff_efc0
             │ 保存的 process.FP = 0x7fff_eff0      │ <- 即将被取回
             └──────────────────────────────────────┘
```

### 时刻 7：执行 `ldp x29, x30, [sp], #16`（恢复现场）

后索引 `ldp` 的两个动作：

```text
动作 ①：x29 = [0x7fff_efc0] = 0x7fff_eff0   （取回 process 的锚点）
        x30 = [0x7fff_efc8] = 0x4011e0      （取回返程票）
动作 ②：SP = 0x7fff_efc0 + 16 = 0x7fff_efd0 （越过保存区，恰好回到调用前）
```

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `x29` | 0x7fff_efc0 | 0x7fff_eff0 | 归还：恢复为 process 的锚点 |
| `x30` | 0x4011e0 | 0x4011e0 | 取回的值与寄存器中现存值相同，但机制上「保证」恢复 |
| `SP` | 0x7fff_efc0 | 0x7fff_efd0 | 与时刻 1 之后的 SP 完全相同 |

```text
0x7fff_efd0  ┌──────────────────────────────────────┐ <- SP = 0x7fff_efd0
             │ 0x7fff_efc0 起的保存区已退出有效范围 │ <- ret 的目标：下一格
             │ （[0x7fff_efc8] 里的 0x4011e0 仍在） │
             └──────────────────────────────────────┘
```

注意一个容易被忽视的点：`x30` 此刻的值「碰巧」还是 0x4011e0，是因为 checksum 没有调用过别的函数；但**恢复语句不能省**——只要函数内部有 `bl`，寄存器里的 LR 就早被覆盖，只有凭栈里的拓印才能还原。

### 时刻 8：执行 `ret`（返回）

`ret` 的硬件动作：`PC = x30`。执行后：

| 寄存器 | 执行前 | 执行后 | 说明 |
| --- | --- | --- | --- |
| `PC` | `ret` 指令地址 | 0x4011e0 | 回到 process 中 `bl` 之后 |
| `SP` | 0x7fff_efd0 | 0x7fff_efd0 | 与调用前一致，无需再动 |
| `x29` | 0x7fff_eff0 | 0x7fff_eff0 | 已是 process 的锚点 |
| `w0` | 40 | 40 | 返回值被 process 取走：`result * 2 = 80` |

```text
对照时刻 1：
  SP ：0x7fff_efd0  →  0x7fff_efd0   （精确回位，不多不少）
  x29：0x7fff_eff0  →  0x7fff_eff0   （精确回位）
  w0 ：11（参数）    →  40（结果）     （使命交接）
```

这就是「栈帧是严格后进先出（LIFO）」的含义：最后调用的 checksum 必须最先撤销；任何一步少弹或多弹 16 字节，返回后一切立即错位。

## 5. LR 为什么必须保存：被嵌套调用覆盖

时刻 1 里 `x30` 恰好一路没被动过，容易被误解为「LR 不用保存也行」。把调用链加深一层就会看到问题。假设有这样的嵌套：

```text
main -> foo -> work
```

- `main` 调用 `foo` 时，`bl` 把「回到 main 的地址」写进 LR；
- `foo` 要调用 `work`，执行 `bl work` 的瞬间，LR 又被改写成「回到 foo 的地址」——**原来那张回 main 的票被覆盖了**；
- 因此 `foo` 必须在 `bl work` 之前，把 LR 保存进自己的栈帧（即时刻 2 的 `stp` 动作）。

```text
foo 调用 work 之前：
    foo 的 LR = 回到 main 的地址

执行 bl work 之后：
    LR = 回到 foo 的地址
    foo 原来的 LR 必须已经在 foo 的栈帧里 —— [foo.x29 + 8]
```

这对回溯的含义是：**非叶子函数的返回地址最终躺在它自己的栈帧里**（每帧的 `[x29+8]`），而叶子函数的返回地址可能还留在 LR 寄存器中。回溯器必须知道当前帧是哪一种形态——这正是后续三种回溯方法要解决的问题。

## 6. 没有完整栈帧的函数

### 6.1 叶子函数：只靠 LR 返回

一个很短的叶子函数可以不碰 `x29`、不动 `SP`：

```asm
leaf:
    add w0, w0, #1
    ret
```

它直接使用寄存器里的 LR 返回。此时：

```text
返回地址仍然在 LR 寄存器中
栈上没有属于它的任何格子
```

### 6.2 只保存 LR 但不建帧指针的函数

另一个常见形态是省略 `x29` 链，但把 LR 保存到栈上：

```asm
middle:
    str  x30, [sp, #-16]!     ; 只保存 LR 并下移 SP
    ...
    ldr  x30, [sp], #16       ; 恢复 LR 并上移 SP
    ret
```

此时 `x29` 已无回溯语义，但返回地址仍躺在 `[SP]` 位置——只要知道指令执行到哪儿、`SP` 相对入口移了多少，就能找回来（这就是 DWARF CFI 描述的事情）。

### 6.3 优化构建与帧指针取舍

在优化等级较高、或编译器被配置为省略帧指针时，`x29` 可能被复用作普通寄存器，`[x29]`/`[x29+8]` 不再具有「旧 FP / 返回地址」的含义。于是：

- 依赖 `x29` 链的快速回溯会变浅或直接中断；
- 「保留帧指针」是用一点性能换确定性回溯的工程取舍：
  - 保留 `-fno-omit-frame-pointer`：回溯稳定、实现简单，代价是一个寄存器与少量指令；
  - 省略帧指针：性能更好，但回溯必须依赖 DWARF CFI 等更复杂的规则。

可以用 `objdump -d` 或 `readelf -wf` 观察一个二进制到底有没有帧指针链与 CFI 规则。

## 7. 源码函数 ≠ 物理栈帧：内联与尾调用

初学时很容易期待「一行源代码调用 = 一个栈帧」。优化编译器会合法地打破这种直觉。

### 7.1 内联：源码有函数，机器码没有调用

若 `checksum()` 足够小，编译器可能直接把它的乘法和加法复制进 `process()`：

```text
源码：process -> checksum
机器码：process 内直接完成 x * 3 + 7
物理栈：只有 process，没有 checksum 帧
```

带完整 DWARF 的调试器/符号化工具仍可能把这段机器码解释为「逻辑上位于 checksum，并且它被内联进 process」，这叫 **inline frame**。它是调试信息推导出的逻辑帧，不是 CPU 栈上的物理帧。

### 7.2 尾调用：返回前直接跳进下一个函数

若函数最后的动作只是返回另一个函数的结果：

```c
int relay(int x) {
    return checksum(x);
}
```

编译器可能把 `bl checksum; ret` 优化成一条 `b checksum`（跳转而非调用）：checksum 结束时直接返回到 relay 的调用者，relay 的独立帧不存在。这叫尾调用优化。

### 7.3 结论：回溯是「当时真实机器状态」的证据

因此，看到某个源码函数不在 CPU profile 中，不能立即断言采集器漏帧。它可能被内联、尾调用消除、异常路径改写，或者处在非标准栈上。分析时应区分：

- **物理回溯**：实际栈和寄存器里可恢复的帧；
- **逻辑调用链**：结合 DWARF inline 信息、运行时信息后展示的源码层级。

## 8. 回家作业：同样的过程在 x86-64 上长什么样

如果你更熟悉 x86-64，可以用这张对照表把本文的全部时刻平移过去，逻辑一一对应：

| 动作 | AArch64（本文主线） | x86-64 |
| --- | --- | --- |
| 发起调用 | `bl checksum`：返回地址写入 `x30`（LR） | `call checksum`：返回地址**压栈** |
| 保存现场并建帧 | `stp x29, x30, [sp, #-16]!` + `mov x29, sp` | `push rbp` + `mov rbp, rsp` |
| 分配局部空间 | `sub sp, sp, #16` | `sub rsp, 0x10` |
| 保存的返回地址在哪 | 调用者栈帧的 `[x29 + 8]`（LR 副本） | 被调者栈帧的 `[rbp + 8]`（call 压入） |
| 拆除现场 | `add sp, sp, #16` + `ldp x29, x30, [sp], #16` | `leave`（=`mov rsp, rbp; pop rbp`） |
| 返回 | `ret`：`PC = x30` | `ret`：从栈顶弹出返回地址 |
| 帧指针链两个格子 | `[x29]`、`[x29+8]` | `[rbp]`、`[rbp+8]` |

x86-64 精简版栈对照（同一时刻「被调函数帧已建立」）：

```text
x86-64                                   AArch64
高地址                                    高地址
  [rbp + 8] = 返回地址（call 压栈）         [x29 + 8] = 返回地址（stp 拓印）
  [rbp + 0] = 保存的调用者 rbp              [x29 + 0] = 保存的调用者 x29
低地址 <- rsp                           低地址 <- sp
```

两者差异只在「返回地址是硬件压栈、还是显式拓印」：恢复调用者的数学结构完全同构——这就是为什么后面三种回溯方法讲的是同一套思想，只是取数位置不同。本文以 AArch64 为主线，是因为性能采集链路（`perf_ebpf` → FlameCraft）的目标平台正是它。
