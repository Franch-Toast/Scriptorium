# FP帧指针链回溯：最简单也最脆弱的栈回溯

> 本文是「栈回溯」系列方法篇之一。FP（Frame Pointer，帧指针）链回溯是最容易在纸上执行的方法：它不读规则表、不依赖内核，只沿着栈里一条约定俗成的「链表」走完调用链。
>
> 前置知识：[函数调用与返回：AArch64栈帧与寄存器的逐步变化](../函数调用与返回：AArch64栈帧与寄存器的逐步变化.md)；方法全景：[三种栈回溯方法总览](./三种栈回溯方法总览.md)。本文示例沿用前置篇 `stack_demo` 的同一套现场数据。

## 1. 一句话理解 FP 链

观察 [函数调用与返回](../函数调用与返回：AArch64栈帧与寄存器的逐步变化.md) 时刻 3 的成果——每个使用传统序言的函数，其栈帧顶部都有两个固定格子：

```text
[x29 + 0] = 上一帧的 FP
[x29 + 8] = 返回地址
```

于是整个调用链在内存里形成一条**单向链表**：结点地址就是 FP 值，结点第一个字存 next 指针（上一帧 FP），第二个字存返回地址（调用者的 PC）。回溯器要做的，只是从头结点开始，不断读这两个格子、跳到下一个结点：

```text
理解它的最短句子：
「上一帧的 FP 和返回地址，总在本帧 FP 的固定位置。」
```

## 2. 内存布局规则

把 `main -> process -> checksum` 停在 `checksum` 函数体内（时刻 5）展开，内存是这样的：

```text
地址              内容                                      所属帧
──────────────────────────────────────────────────────────────────────
0x7fff_efc0       0x7fff_eff0  = process.FP                 checksum: saved FP
0x7fff_efc8       0x000000004011e0 = 返回到 process        checksum: 返回地址
                  ↑
                  checksum.FP = 0x7fff_efc0

0x7fff_efd0       （process 局部数据，不参与 FP 链）
0x7fff_eff0       0x7fff_f120  = main.FP                    process: saved FP
0x7fff_eff8       0x00000000401220 = 返回到 main           process: 返回地址

0x7fff_f120       0x00007fff_f240 = libc 的 FP             main: saved FP
0x7fff_f128       0x00007f...  = 返回到 libc/start          main: 返回地址
```

注意这不是「函数名字串」，而是一个纯粹的指针链表。把它画成链式关系：

```text
checksum.FP        process.FP         main.FP
0x7fff_efc0  --->  0x7fff_eff0  --->  0x7fff_f120  --->  ...
    |                  |                  |
    v                  v                  v
 [FP+8] =           [FP+8] =           [FP+8] =
 0x4011e0           0x401220           0x7f...（libc）
（回 process）      （回 main）        （继续往上）
```

作为对照，x86-64 的链形状完全相同，只是锚点换成了 `rbp`、保存的返回地址来自 `call` 硬件压栈：

```text
[rbp + 0] = 上一帧 rbp
[rbp + 8] = 返回地址
```

这种同构意味着：本文讲的算法在两个架构上是同一个算法，学会一个就够用。

## 3. 人工执行一次 FP 回溯

假设异步采样恰好落在 [函数调用与返回](../函数调用与返回：AArch64栈帧与寄存器的逐步变化.md) 的时刻 5，寄存器现场是：

```text
PC  = 0x401148      （checksum 内部的一条指令，checksum+0x18）
SP  = 0x7fff_efb0
x29 = 0x7fff_efc0
LR  = 0x4011e0
```

回溯器按如下步骤工作：

1. **当前帧**：先把 `PC = 0x401148` 记录为第 0 帧——它属于 `checksum`；
2. **读当前 FP**：`fp = x29 = 0x7fff_efc0`；
3. **读返回地址**：`ra = *(fp + 8) = *(0x7fff_efc8) = 0x4011e0`——它属于 `process`；
4. **读上一帧 FP**：`next_fp = *fp = *(0x7fff_efc0) = 0x7fff_eff0`；
5. **推进**：把 `PC = ra`、`fp = next_fp`，重复第 3、4 步；
6. 最终得到地址序列：`0x401148, 0x4011e0, 0x401220, ...`，再交给符号化阶段显示 `checksum, process, main, ...`。

### 逐步图示：游标如何沿链移动

把回溯器想象成一只手，它每推进一帧只做「两次读、一次跳」。下图把每一步的读取对象直接标在链上：

```text
步骤 1  游标就位：fp = x29 = 0x7fff_efc0
        读 [fp + 8]：得 0x4011e0            -> 记为下一帧的 PC（属于 process）

        0x7fff_efc0 ┌────────────────┐
                    │ 0x7fff_eff0    │ ----- 步骤 2 读它（next_fp）
                    ├────────────────┤
                    │ 0x000000004011e0 │ <--- 步骤 1 读它（ra）
                    └────────────────┘
                      fp = 0x7fff_efc0

步骤 2  读 [fp]：得 0x7fff_eff0              -> 下一帧的 FP

步骤 3  游标跳到 process 帧：fp = 0x7fff_eff0，PC = 0x4011e0
        重复「两次读」：ra = [fp+8] = 0x401220（属于 main）
                      next_fp = [fp] = 0x7fff_f120

        0x7fff_eff0 ┌────────────────┐
                    │ 0x7fff_f120    │ ----- main.FP（下一个游标）
                    ├────────────────┤
                    │ 0x00000000401220 │ <--- process 帧的 ra
                    └────────────────┘
                      fp = 0x7fff_eff0

步骤 4  游标跳到 main 帧：fp = 0x7fff_f120，PC = 0x401220
        继续同样两次读，直到某次读出的 FP 或返回地址无效为止。
```

三轮循环后，回溯器手里的地址序列是：

```text
0x401148（checksum+0x18，来自采样时的 PC）
0x4011e0（process+0x30，来自 [fp+8]）
0x401220（main+0x20，来自 [fp'+8]）
```

整个过程没有读 `SP`，没有读局部变量，也没有查任何表——FP 法的全部证据就是链上每个格子里并排存放的两个指针。这也是它「快」与「脆」同源的原因：读得少所以快；格子一旦被写坏，就没有第二份证据可校验。

## 4. 算法伪代码

真实实现还必须检查内存可读性、地址对齐和边界：

```c
frames.push(current_pc);
for (fp = current_x29; valid(fp); fp = *(uint64_t *)fp) {
    uint64_t return_address = *(uint64_t *)(fp + 8);
    if (!valid_code_address(return_address)) {
        break;
    }
    frames.push(return_address);
}
```

`valid()` 在 AArch64 上通常检查：

```text
next_fp > current_fp        （栈向高地址回到外层帧）
next_fp 位于该线程的栈映射范围内
next_fp 按指针宽度对齐
return address 落在已执行代码映射中
```

这些检查不能保证结果一定正确——它们只保证「不像乱码」，拦不住一条结构合法但语义错误的链（见第 6 节）。

## 5. 为什么它快

每一层只做两个固定偏移的内存读取：一个读上一个 FP，一个读返回地址。它不需要遍历规则表，不需要解释函数中间任意位置的寄存器变化。因此：

- 适合低开销 profiler、崩溃处理器和受限运行环境；
- 对正常 C/C++ 业务代码，保留帧指针后通常稳定、速度很高；
- 概念极简，容易在纸面与面试白板上完整推演。

但「快」来自于它假设所有函数都保持相同形状。一旦这个假设不成立，就会错。

## 6. FP 链会在哪里断掉

### 情况 A：编译器省略帧指针

在优化构建中，编译器可能把 `x29` 当普通寄存器用，序言里没有 `stp x29, x30, [sp, #-16]!` + `mov x29, sp`。此时 `[x29]` 和 `[x29+8]` 可能装着任意临时数据，没有回溯语义。FP walker 若继续读，可能会得到随机值，表现为异常大地址、调用链突然跳到无关库，或只剩当前一帧。

### 情况 B：采样落在 prologue/epilogue 的中间

即使启用帧指针，异步采样也可能恰好落在：

```text
bl 之后、stp 执行之前
stp 之后、mov x29, sp 之前
ldp 恢复期间、ret 之前
```

这些瞬间里，新帧的 FP 链尚未完全建立，或已经开始拆除。可靠回溯器不能只看「函数入口/出口」，而要知道当前 PC 处于哪种栈状态——这正是 DWARF CFI（逐 PC 规则）的价值。

### 情况 C：采样落在「没有建帧」的叶子函数中

这是 AArch64 上最容易被忽视的一种错法。若采样的位置在一个**没有保存 x29 的叶子函数**里（它不碰 `x29`、不动 `SP`，直接靠 LR 返回），那么此时 `x29` 仍然指向**调用者的帧**。FP walker 拿这个 `x29` 去读 `[x29+8]`，读到的其实是调用者的返回地址——**整条链会整体跳过一层**：

```text
真实调用链：checksum(叶子) <- process <- main
FP 法可能输出：process <- main        （checksum 被跳过）

原因：叶子函数里的 x29 是 process 的，读 [x29+8] 得到的是「回 main」，
      而不是「回 process」。
```

要精确处理这种情形，回溯器必须知道「当前 PC 处于未建帧函数的哪段指令」，这正是 FP 链方法本身无法回答的——只有 CFI 规则能逐 PC 描述「此刻 FP 是否仍然可信」。

### 情况 D：栈损坏或栈切换

递归越界、错误指针写入可能覆盖保存的 FP 或返回地址；协程、纤程、语言运行时也可能主动切换到另一块栈。此时链表可能不连续，或 `next_fp` 跳出线程栈的合法地址区间。这类场景只能靠第 4 节的边界检查兜底「止损」，无法恢复真相。

## 7. `-fno-omit-frame-pointer` 的边界

它不是让程序「自动有完整调用栈」的魔法开关。它做的是让**编译器生成的普通函数**保留 FP 链，显著提高 FP 回溯的成功率。仍可能缺失：

- 内联或尾调用优化掉的逻辑函数（物理帧根本不存在，见 [函数调用与返回](../函数调用与返回：AArch64栈帧与寄存器的逐步变化.md) 第 7 节）；
- 未按该选项构建的第三方库；
- 手写汇编、信号 trampoline、JIT 代码；
- 栈已经损坏的异常现场。

所以生产 profiling 的常见策略是：优先使用 DWARF/CFI，FP 作为低成本回退；若系统只支持 FP 回溯，则对关键业务二进制统一开启 `-fno-omit-frame-pointer`。

## 8. 在 perf_ebpf 中的位置

`perf_ebpf` 的 CPU 用户栈**主路径不是** FP 链，而是 BPF 内的 DWARF CFI 回溯（见 [DWARF-CFI回溯](./DWARF-CFI回溯.md)）。FP 链在本项目中以两种面貌出现：

1. **内核与兜底路径**：`bpf_get_stackid()`（见 [eBPF栈采样](./eBPF栈采样.md)）在底层可能使用 FP 展开；当 DWARF 回溯得到的用户栈为空或很浅时，采集器会回退到 stack map 的结果。
2. **输出标签 `[u/fp]`**：stack map 路径产出的用户栈行会被标记为 `[u/fp]`。请注意这只是项目约定的输出标签，说明「这份用户栈来自 stack map」，**不等于**项目在用户态手写了一个 FP `while` 循环。

工程上的完整对应关系见撷简台 [perf_event 与 BPF 内轻量化 DWARF CFI 堆栈回溯](../../../../撷简台/2026-10-12%20perf_event与BPF内轻量化DWARF-CFI堆栈回溯通俗教程.md) 第 5 节的三种方法对比表与第 12.2 节。

## 9. 小结与下一站

```text
FP 法 = 把栈帧当链表：结点 = FP 值，结点内容 = 「上一帧 FP + 返回地址」。
每推进一帧：两次固定偏移读取、一次跳转。
优点：极快、极简；缺点：强依赖编译产物形状，四种场景会断链或跳层。
```
