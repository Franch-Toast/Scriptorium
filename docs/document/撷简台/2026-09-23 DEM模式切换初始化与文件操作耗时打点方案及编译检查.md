# DEM 模式切换初始化与文件操作耗时打点方案及编译检查

## 1. 背景

针对行程 `SILYR-LPD19A-2068599_20260922_163610` 中 DSM 模式切换耗时 `127s` 的问题，已有日志分析显示 DEM 在节点初始化期间可能被 `/fs/usb0-0` 外置文件系统阻塞约 112 秒。本次改动用于将阻塞范围从“节点初始化/环境文件写入”进一步缩小到具体文件操作阶段。

本次只增加诊断计时和日志，不改变节点初始化顺序、文件写入内容、权限处理、异常处理或状态机行为。

## 2. 实施方案

### 2.1 计时基准

在 `src/common/timestamp.h/.cc` 增加 `GetMonotonicTimeUs()`，使用 `std::chrono::steady_clock` 返回微秒值。

使用单调时钟的原因：

- 不受系统时间校准、时区或墙上时间跳变影响；
- 可直接计算同一进程内操作的真实经过时间；
- 日志输出是否延迟不会改变已经计算出的 `elapsed_us`。

### 2.2 节点初始化层

在 `src/node/executable_node_base.cc` 的 `ExecutableNodeBase::Initialize()` 中，对以下阶段分别计时：

- `InitializePaths`
- `InitializeSignal`
- `InitializeLogger`
- `InitializeEnv`
- `InitializeScheduling`
- `InitializeResourceLimit`
- `InitializeCommand`
- `InitializeTotal`

日志前缀为 `DEM_INIT_TIMING`，包含节点名、状态、`fg_id`、`dem_id`、阶段和微秒耗时。

在路径和环境初始化内部增加 `DEM_FS_TIMING` 记录，覆盖：

- 节点日志目录创建；
- DEM other 目录存在性检查和创建；
- 模块数据目录存在性检查和创建；
- 已有模块目录的 `ChownFile` 与权限设置。

这些路径级记录目前全部输出，便于在现场日志中建立完整时间线。

### 2.3 Executor 和 Function Group 聚合层

在 `src/state_managers/executor.cc` 中记录：

- 单个节点 `GenerateNodeInstance` 耗时；
- `Executor::InitializeNodes` 总耗时和节点数量。

在 `src/state_managers/fg_task.cc` 中记录整个 `Executor` 构造耗时。日志前缀为 `DEM_INIT_TIMING`，用于将节点级耗时与功能组、DSM 看到的总耗时对齐。

预期的调用关系为：

```text
FunctionGroupExecutorConstruction
  -> ExecutorInitializeNodes
    -> GenerateNodeInstance
      -> ExecutableNodeBase::Initialize
        -> InitializePaths / InitializeLogger / InitializeEnv / ...
```

### 2.4 环境文件层

在 `src/common/environment.cc` 的 `WriteEnvFile()` 中增加：

- 环境变量文本构造耗时；
- 主 env 文件 `WriteFile` 耗时；
- source env 文件 `WriteFile` 耗时；
- `WriteEnvFile` 总耗时。

日志前缀为 `DEM_ENV_TIMING`，只输出文件路径和耗时，不输出额外的环境变量内容。

### 2.5 通用文件操作层

在 `src/common/file.cc` 中对 `CreateDir()` 和 `WriteFile()` 增加慢操作诊断：

- `CreateDir` 总耗时；
- `WriteFile` 的父目录存在性检查；
- 父目录创建；
- 文件 `open + write + close`；
- `chown`；
- `permissions`；
- 可选 `sync`；
- `WriteFile` 总耗时。

通用文件操作仅在耗时达到 `100ms` 时通过 `DEM_FS_TIMING` 输出，避免正常运行产生大量日志。`WriteEnvFile` 的上层耗时日志始终输出，因此即使单次通用操作低于阈值，也能看到环境文件写入总耗时。

## 4. 现场日志判读方法

### 情况 A：env 文件写入本身耗时约 112 秒

重点寻找：

```text
DEM_ENV_TIMING phase=write_env_file ... elapsed_us=112000000
DEM_FS_TIMING operation=write_file.open_write_close ... elapsed_us=112000000
```

这可以确认阻塞位于 env 文件 `open/write/close` 组合中，再结合 QNX trace 区分具体系统调用。

### 情况 B：`WriteEnvFile` 较快，但 `InitializeEnv` 很慢

继续比较以下日志：

```text
DEM_FS_TIMING operation=check_module_path ...
DEM_FS_TIMING operation=create_module_path ...
DEM_FS_TIMING operation=module_path_permissions ...
DEM_ENV_TIMING phase=write_env_file ...
```

如果某一条路径检查、目录创建或权限设置接近 112 秒，则可以排除 env 文件写入本身。

### 情况 C：`InitializeEnv` 较快，但 `InitializeLogger` 或 `InitializePaths` 很慢

说明卡点位于 NodeLogger 创建、日志目录扫描/创建或路径初始化，应重点检查节点日志目录所在挂载点，而不是只关注 `env_file_*`。

### 情况 D：DEM 侧所有计时均较快

说明阻塞可能发生在当前打点之外，例如锁等待、进程/线程创建、调度初始化或其他依赖服务。此时继续使用 `tracelogger`/SAT 采集内核线程状态和 QNX 资源管理器消息链。

## 5. 编译检查

### 5.1 用户原始命令

执行了用户给出的命令：

```bash
bazel build --config=sa8650_qnx --config=release --config=LP8650-V1-SHARE --config=non-delivery --config=remote-exec --config=remote-exec-host-x86-2004
```

结果：Bazel 返回成功，但提示：

```text
Your request is correct, but requested an empty set of targets. Nothing will be built.
Found 0 targets
Build completed successfully
```

因此该命令只验证了配置解析，没有验证 DEM 源码编译。

### 5.2 实际 DEM 目标编译

根据仓库 `/sandbox/onboard_application/dem/BUILD`，实际可执行目标为 `//dem:dem_launch`。使用完全相同的配置并补充目标：

```bash
bazel build \
  --config=sa8650_qnx \
  --config=release \
  --config=LP8650-V1-SHARE \
  --config=non-delivery \
  --config=remote-exec \
  --config=remote-exec-host-x86-2004 \
  //dem:dem_launch
```

结果：**通过**。

```text
Target //dem:dem_launch up-to-date:
  bazel-bin/dem/dem_launch
Build completed successfully, 24 total actions
```

链接阶段存在仓库原有警告：

- `libdal.so`、`libdalconfig.so.1` 未找到的链接器 warning；
- `libsocket.so.3` 与 `libsocket.so.4` 可能冲突的 warning；
- `elfnote` 无法恢复原文件 ownership 的 warning。

未发现与本次计时改动相关的编译、链接或依赖错误。

首次真实编译还发现节点和状态管理文件遗漏了 `common` 命名空间限定，已补充 `GetMonotonicTimeUs` 的 using 声明，并使用同一命令增量重编译通过。

随后又移除了目录创建后的额外 `ExistFile` 诊断访问，并修正 `ChownFile` 结果记录；使用同一配置再次增量构建，仍然通过：`Build completed successfully, 4 total actions`。

### 5.3 其他检查

- `git diff --check`：通过；
- 构建目标：`//dem:dem_launch`；
- 目标平台：QNX aarch64；
- 未执行车辆侧运行验证，因此目前只能确认“代码可编译”，不能确认现场问题已经消失。

## 6. 后续现场验证

1. 使用本次构建产物部署到能够复现模式切换问题的车辆。
2. 触发至少一次 `ALL_FUNCTION`、`ONLINE_CALIBRATION` 或 `DATA_COLLECTOR_PARKING` 切换。
3. 在 DEM 日志中检索 `DEM_INIT_TIMING`、`DEM_ENV_TIMING` 和 `DEM_FS_TIMING`。
4. 将耗时接近 112 秒的日志路径与 `/fs/usb0-0`、内部路径分别归类。
5. 若定位到具体文件操作，再用 `tracelogger` 对该时间窗口做内核级阻塞链确认。
