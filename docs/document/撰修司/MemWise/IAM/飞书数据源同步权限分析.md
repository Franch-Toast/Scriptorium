# WeKnora 飞书(Lark)数据源同步与机器人权限分析

> 面向：需要理解「飞书数据源为什么要那 4 个只读权限、机器人到底在做什么、这套权限会不会过宽导致泄露」的人（含管理层、安全评审、接手的开发）。
> 依据：WeKnora 源码 `internal/datasource/connector/feishu/`（core / wiki / drive 三包）+ `frontend/src/views/knowledge/settings/DataSourceEditorDialog.vue` + `docs/数据源导入开发文档.md`。
> 结论先行见 [§0](#0-一句话结论)；对「权限过大」担忧的逐条评估见 [§8](#8-对老板担忧的逐条评估)。

---

## 0. 一句话结论

- 这四个权限是**该能力在飞书侧的"最小权限集"，全部只读**（无任何写文档的能力）：`wiki:wiki:readonly`（发现/遍历知识库）、`drive:drive:readonly`（列目录/下载原文件与内嵌媒体）、`drive:export:readonly`（异步导出 doc/sheet/bitable）、`docx:document:readonly`（读新版文档块结构）。删掉任何一个，某类文档的同步链路就会断。
- 「下载/导出**所有云文档**」这个说法，在**应用被授权的内容范围内**是成立的（scope 描述语本身就是"云空间中的文件"）；但在**全企业层面**不成立——**数据可见性由"成员关系"这道闸门决定**，scope 只决定"能不能调用某类 API"，不决定"能读到哪些文件"。
- **scope 砍不掉、也不该砍**，因为飞书没有按空间/文件夹细分的"子 scope"。真正能防信息泄露的控制点在两个"成员/管理"闸门：**① 飞书侧把哪些空间/文件夹授权给机器人；② WeKnora 侧谁能配置数据源、谁能触发全量同步**。建议围绕这两点做治理，见 [§9](#9-weknora-侧现状与建议)。

## 1. 先厘清："机器人"在这里到底是谁

WeKnora 的飞书数据源用的是**企业自建应用 + Tenant Access Token** 模型，不是用户 OAuth 授权：

```go
// internal/datasource/connector/feishu/core/types.go:20
// Uses the self-built app (企业自建应用) authentication model.
type Config struct {
    AppID     string `json:"app_id"`
    AppSecret string `json:"app_secret"`
}
```

关键点：`tenant_access_token` 的**主体是"应用"本身，不是任何一个员工**。所有请求只是 `Authorization: Bearer <tenant_access_token>`，代码里没有 user token、没有 user_id 概念（`core/client.go:188`）。

所以：

- 配置里只要 `App ID + App Secret` 两个字段就够（`DataSourceEditorDialog.vue` 的 fields 只填这两项 + 可选 base_url）；
- 那个"机器人"，就是你在飞书开放平台创建的那个企业自建应用，它作为**一个服务账户**替 WeKnora 读文档；
- 整个同步是**纯拉取（pull）模式**：WeKnora 主动周期调用飞书 API，无事件订阅、无 webhook、无需任何人（员工）在场——这是它能无人值守定时跑的前提。

## 2. 四个权限分别解锁什么

权限（scope）是**授予给应用的**，不是授予给用户个体的。四个权限精确对应四组 API：

| 权限 | 解锁的飞书 API | 代码位置 | 用途 | 需要它的连接器 |
|---|---|---|---|---|
| `wiki:wiki:readonly` | `GET /wiki/v2/spaces`<br>`GET /wiki/v2/spaces/{id}/nodes`<br>`GET /wiki/v2/spaces/get_node` | `core/client.go:304`<br>`core/client.go:342`<br>`core/client.go:383` | **发现 + 遍历知识库节点树**：列空间、列子节点、查单节点父链（资源选择 + 同步时 DFS 遍历） | 仅 `feishu`/`lark`（Wiki 模式） |
| `drive:drive:readonly` | `GET /drive/v1/files?folder_token=`<br>`GET /drive/explorer/v2/folder/{t}/meta`<br>`GET /drive/v1/files/{t}/download`<br>`GET /drive/v1/medias/{t}/download` | `core/client.go:785`<br>`core/client.go:815`<br>`core/client.go:665`<br>`core/client.go:674` | **云盘基础信息 + 下载**：列目录、取文件夹名、下载 `file` 类型原文件（PDF/Word…）、下载文档内嵌图片/附件 | 全部四种 |
| `drive:export:readonly` | `POST /drive/v1/export_tasks`<br>`GET /drive/v1/export_tasks/{ticket}`<br>`GET /drive/v1/export_tasks/file/{t}/download` | `core/client.go:549`<br>`core/client.go:570`<br>`core/client.go:595` | **异步导出**：把 doc/docx/sheet/bitable 转成 `.docx` / `.xlsx` 二进制，再交 docreader 解析 | 全部四种 |
| `docx:document:readonly` | `GET /docx/v1/documents/{id}/blocks` | `core/blocks.go:126` | **读新版文档块结构**：blocks 模式下把 docx 转 Markdown；内嵌表格/多维表格下钻的前提 | 全部四种（见下"为什么 export 也要它"） |

前端把这份清单按连接器类型做了区分（`DataSourceEditorDialog.vue:506`）：**飞书云盘模式（`feishu_drive`）的清单里没有 `wiki:wiki:readonly`**——云盘模式不调 wiki 接口，根目录 `folder_token` 由用户手填。

```
权限 → API → 代码路径 映射图

  wiki:wiki:readonly ──► /wiki/v2/spaces            ──► ListWikiSpaces()    // 资源发现
                     └─► /wiki/v2/spaces/{}/nodes  ──► ListWikiNodes()     // 递归遍历节点树
                     └─► /wiki/v2/spaces/get_node  ──► GetWikiNode()       // 前端展开父子链

  drive:drive:readonly ─► /drive/v1/files            ──► listDriveFiles()      // 云盘列目录
                       ├► /drive/explorer/v2/folder  ──► GetDriveFolderMeta()  // 根目录取名
                       ├► /drive/v1/files/{}/download ─► DownloadDriveFile()   // obj_type=file 原文件
                       └► /drive/v1/medias/{}/download ► downloadMediaFile()   // 内嵌图片/附件

  drive:export:readonly ─► /drive/v1/export_tasks        ──► createExportTask()
                        ├► /drive/v1/export_tasks/{tk}   ──► getExportTaskStatus()
                        └► /drive/v1/export_tasks/file/  ──► downloadExportFile()

  docx:document:readonly ─► /docx/v1/documents/{}/blocks ──► listDocumentBlocks()
```

**为什么"导出"要占用两个权限域？** `docx`/`doc`/`sheet`/`bitable` 走的是**异步导出链路**（`drive:export:readonly`），`file` 类型附件走的是**直接下载链路**（只需 `drive:drive:readonly`），两条链路互不覆盖，所以两个都要。

**为什么默认的 export 模式也要 `docx:document:readonly`？** 默认路径（`FEISHU_DOCX_PARSE_MODE=export`）确实不用 blocks API；但该权限是**切换 blocks 模式的开关**，且 blocks 失败时会**自动回退到 export**（`core/shared.go:330`）——清单里保留它是为了"能力可切换、不因缺权限而断链"，属建议保留而非逐条被用到。

## 5. 同步引擎的容错设计（与安全无关，但解释了"稳定拉取"的代价）

| 设计 | 位置 | 说明 |
|---|---|---|
| 游标 += `edit_time` 快照 | `core/engine.go:90` | `space → node → edit_time` / `folder → file → modified_time` |
| 抓取失败不推进游标 | `core/engine.go:153` | 保留旧 edit_time，下次 `prev != current` 自然重试（#2136，避免偶发导出失败导致永久跳过）；同时 Emit 一条 error item 进同步日志 |
| 全量列出成功才判定删除 | `core/engine.go:203` | `partial == nil` 才比对删除，防止"部分子树没列到"被误判成"已删除"而误删知识 |
| 限流退避 | `core/client.go:154` | 429 尊重 Retry-After、5xx 重试一次、传输错误指数退避(2s/4s/8s)；千文档同步会打数万次调用 |
| 单文件上限 | `core/client.go:144` | 下载体积上限 512MB，防恶意/病理超大响应打爆 worker |

## 6. 权限设计的核心：两层模型（"大 vs 小"必须先分清是哪一层）

老板的担忧和大多数"权限过大"的直觉，都源于把 **scope（能力域）** 和 **数据可见性（成员关系）** 混为一谈。飞书（以及 Google Drive 等）的应用权限是两层：

```
┌─ 第一层：Scope（应用级能力）────────────────────────────────┐
│  在开放平台「权限管理」开通                                    │
│  → 决定应用【能调用哪一类 API】                               │
│  即 wiki:/drive:/docx: 那四个只读权限                         │
│  粒度 = API 域级，不细分到某个空间/文件夹                     │
└──────────────────────────────┬─────────────────────────────┘
                              │ 开通 ≠ 能读到内容
                              ▼
┌─ 第二层：数据可见性（成员/共享关系）─────────────────────────┐
│  机器人必须被【加为知识库空间 / 云盘目录的成员】               │
│  或目标目录对应用开放                                        │
│  → 决定应用【具体能读到哪几个文件】                          │
│  ListWikiSpaces 语义 = "accessible to the app"               │
└────────────────────────────────────────────────────────────┘
```

证据（代码注释 + 行为）：
- `core/client.go:303`：`ListWikiSpaces returns all wiki spaces accessible to the app`——**只返回应用有权限的空间**；
- 云盘方向 `listDriveFiles` 只列**应用有权限的目录**下的文件；对无权限文件，列 API 本身就不会返回、下载会 403。

所以精确的说法是：

> 那四个 scope 让机器人**"有能力"下载/导出任何它"够得着"的文档**；但"够得着的范围"由**谁把哪些空间/文件夹共享给了它**决定，而不是由 scope 决定。scope 一句话概括 = **"对应用可见内容的**只读**全量古籍页能力"**。

## 7. 有没有更小的替代？为什么 scope 砍不掉

结论：**在飞书应用权限的粒度下，这套 scope 已经是"该能力所需的最小集合"，没有更小的版本可配。** 理由：

1. **粒度是 API 域级**：飞书没有"只对空间 A 授予 `drive:export:readonly`"这种按内容细分的 scope。要么有 export 能力，要么没有。
2. **可选的可视范围收缩对同步不可用**：飞书对部分云盘权限提供"仅应用创建的文件"这类可见范围选项，但同步要读的是**员工创建的文档**（而非应用创建的），该选项对场景无意义。
3. **删任何一个都断一节**：
   | 删掉的权限 | 后果 |
   |---|---|
   | `wiki:wiki:readonly` | 资源发现/遍历断 → Wiki 模式整个不可用（Drive 模式本来就不需要它） |
   | `drive:export:readonly` | doc/sheet/bitable 导出断 → 这三类文档全部失败；docx 的 export 回退也失败 |
   | `drive:drive:readonly` | file 原文件 + 内嵌图片/附件下载断；导出产物下载通道也受影响 |
   | `docx:document:readonly` | blocks 模式断（但有 export 回退，属"建议保留"而非硬依赖） |
4. **行业惯例**：飞书官方导入、QNP/语雀/Confluence 的云盘搬运、以及 Google Drive `drive.readonly` OAuth，全是一模一样的模型——scope 全局 + 数据靠 ACL。这不是 WeKnora 拍脑袋要求的，是平台给定的事实。

## 8. 对老板担忧的逐条评估

老板的原话拆解成三个判断，逐条给结论：

> "这个权限感觉还是大了一些" —— **可以理解，但要纠正因果**。
> 真正"大"的不是这 4 个 scope（§7 已证砍不掉），而是**两个成员闸门维护得宽**：
> ① 飞书侧把整个大空间/根目录直接授权给了机器人（而非只给要同步的子目录）；
> ② WeKnora 侧任何人能往里配数据源、选大范围资源、触发全量同步（见 §9）。
> 这两道闸门**是可以收紧、也应该收紧**的，而且收紧它们的效果远大于"少开一个 scope"。

> "下载和导出所有云文档" —— **授权范围内成立，全企业范围不成立**。
> scope 描述语确实是"云空间中的所有文件"，真实泄的是"应用被授权的内容"能被完整导出成可解析格式（docx/xlsx/原文件）。但它**不是**"整个企业云盘任取"——没共享给应用的空间/目录，列都列不出来。老板若担心"机器人能翻全公司文档"，这个担心**与事实不符**（可以演示给他看：建一个应用不开任何成员，`ListWikiSpaces` 返回空）。
> 同时这 4 个全是 **readonly**：不能改、不能建、不能删飞书文档，单向吸取。

> "感觉直接机器人一次性导完了" —— **首次全量属实，之后是增量**。
> - 首次/全量模式：确实会把**勾选的 resource（空间/文件夹）的全量子树** DFS 一遍并下载内容——这是"同步"的定义，也是 WeKnora 的价值所在（要检索就必须落一份内容），这部分无法也不应"去掉"，只能靠**少勾选 + 勾最小范围**来控制。
> - 此后是增量：游标记录每个节点 `edit_time`，仅在节点变化时才重新导出（`core/engine.go:147` 快路径）。
> - 且**永远只碰 `config.ResourceIDs` 里勾选的那些根**——没有全企业扫描。

**信息泄露的真实风险点（按优先级）：**

| 优先级 | 风险点 | 现状 | 是否需改 |
|---|---|---|---|
| **高** | 飞书侧把哪些空间/文件夹授权给机器人（第一道闸） | 未写入 WeKnora 文档，完全靠管理员自觉 | 出**操作规范**：只加子目录、只给「可阅读」、不给「可管理」；定期复核成员 |
| **高** | WeKnora 侧谁能配置数据源/触发全量同步（第二道闸） | `datasource.go:40 getOwnedKnowledgeBase` 只校验 **tenant 归属 + API key 白名单**，租户内能访问该 KB 的登录用户即可增删改数据源、触发全量同步；**未收口到系统管理员/知识库管理员** | **建议代码收口**，参照已落地的"引擎配置仅系统管理员可配"(`SYSTEM_ENGINE_SETTINGS_SECTIONS`) 的做法 |
| 中 | 同步进 WeKnora 的内容的**下游可见性** | 知识库内容默认租户内可见 | 确认产品预期；如需保密度要求，评估按 KB/人员限可见 |
| 低 | 凭据/传输安全 | 已做：凭证 AES-256-GCM 加密入库、TLS、日志不外泄原始 body（`feishuFailure` 只回 i18n 码不吐原始响应） | 无需改 |

## 9. WeKnora 侧现状与建议

**现状（基于源码核实）：**

1. **鉴权入口**：数据源 handler 统一走 `getOwnedKnowledgeBase`（`internal/handler/datasource.go:40`），只检查：
   - `kb.TenantID == 当前租户`（跨租户拒绝）；
   - `AuthorizeTenantAPIKeyKnowledgeBases`（仅对 **API key 调用方**按 KB 白名单二次限制；页面登录用户在无 KB 成员模型的现状下不受此限）。
   - **没有角色判断**：不区分系统管理员 / 知识库管理员 / 普通成员。（对比：引擎类配置已按"仅系统管理员"处理。）
2. **因此**：租户内任意能访问某 KB 的登录用户，都可以：新增/修改/删除该 KB 下的飞书数据源（含上传 App Secret）、浏览外部资源树、触发全量同步、查看同步日志（含失败内容摘要）。

**建议（按 ROI 排序）：**

| 项 | 说明 | 成本 |
|---|---|---|
| A. 飞书侧授权最小化（操作规范） | 文档里补一节：只把「要同步的子空间/子目录」加为机器人成员；仅授予「可阅读」；不得给「可管理」；管理员定期复核 | 纯文档，0 代码 |
| B. 数据源管理权限收口 | 后端 `getOwnedDataSource`/`getOwnedKnowledgeBase` 增加角色判断（系统管理员 or 该 KB 管理员）才允许写操作（增/改/删/触发同步）；只读（列表/日志）可放宽。前端相应隐藏入口 | 中（需先确认 WeKnora 是否已有 KB 级角色模型；没有则至少收口到 `isSystemAdmin`，与引擎配置一致） |
| C. 「全量同步」二次确认 | 手动触发全量（非增量）时前端弹确认，提示"将拉取所有勾选空间/文件夹的完整内容" | 低 |
| D. 同步范围复核 | 定期/大变更时提示已勾选 resource 的广度；或对"根目录/大空间"级选择加警告 | 低 |

> B 与记忆中的既有改动（引擎配置仅系统管理员）同思路：如果团队已接受"配置类功能收口到管理员"，数据源配置顺理成章应纳入同一类。仓库里 `SYSTEM_ENGINE_SETTINGS_SECTIONS`（前端）与后端对应鉴权可作为参考实现。

## 10. 给管理层的一句话答复（可直接转述）

> 这 4 个权限是飞书开放平台给定的、该项能力**无法再小**的**只读**权限集——删掉任何一个，某类文档就同步不进来；它们只授权"调用某类接口"，**不授权"读取全公司文档"**——机器人能读到什么，由"我们主动把哪些知识库/文件夹加给了它"决定。**真正要收小的不是权限，是授权范围和管理入口**：建议 ①飞书侧只给机器人"要同步的子目录 + 可阅读"，②WeKnora 侧把"配置飞书数据源/触发全量同步"收口到管理员（当前只要是租户里能访问该知识库的人都行，这是目前最值得补的洞），③"全量同步"加二次确认。三件事做完，既能保住"无人值守拉取文档进知识库"的能力，又能把泄露面收敛到可控。
