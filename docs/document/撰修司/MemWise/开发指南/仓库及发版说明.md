# MemWise（weknora）开发与发布工作流

> 适用仓库：`git@code.deeproute.ai:deeproute-org/agi/weknora.git`
> 本文回答：以后新功能从哪拉分支、合到哪里、怎么上生产、能不能 squash、
> `deeproute-dev` 与 `deeproute-master` 会不会因为差异而冲突，以及镜像仓库怎么存。

---

## 1. 仓库与分支模型

```
feature/xxx ──MR──▶ deeproute-dev ──(发版)──▶ deeproute-master
                     ▲                           │
                     └── staging 镜像             └── production 镜像
```

| 分支 | 性质 | 用途 | 谁推镜像 |
|---|---|---|---|
| `deeproute-dev` | 集成分支（常绿） | 所有功能合入点，自动构建 **staging** | staging Harbor |
| `deeproute-master` | 生产分支 | **只在发版时**由 dev 向前推进，自动构建 **production** | production Harbor |
| `feature/*`、`zyf/*` | 短期分支 | 开发中，可手动触发流水线验证编译，**不推镜像** | 无 |
| `Tencent-Offical` 等 | 上游镜像分支 | 不要合入 dev/master | 无 |

### 核心设计：CI 是「同一份动态配置」

`deeproute-dev` 与 `deeproute-master` **刻意保持内容完全一致**，共用同一份
`.gitlab-ci.yml`。环境差异不靠"两份不同的 CI 文件"表达，而是靠**跑在哪个分支上**：
CI 根据 `CI_COMMIT_BRANCH` 自动选择 namespace：

- 跑在 `deeproute-dev` → `DOCKER_NAMESPACE=deeproute-staging/memwise`
- 跑在 `deeproute-master` → `DOCKER_NAMESPACE=deeproute-production/memwise`

因此 master 不需要维护一套不同的 CI，**CI 配置本身永远不会因为两侧不一致而冲突**。

## 2. 镜像仓库与 tag

Harbor 项目名对齐 cicd-common 的 `deeproute-staging` / `deeproute-production`，
本仓库再叠一层 `memwise` 前缀（CI 的 `DOCKER_NAMESPACE` = 两级）。

| 环境 | 分支 | 完整镜像地址 |
|---|---|---|
| staging | `deeproute-dev` | `reg.deeproute.ai/deeproute-staging/memwise/memwise-{app,ui,docreader}` |
| production | `deeproute-master` | `reg.deeproute.ai/deeproute-production/memwise/memwise-{app,ui,docreader}` |

- 每个 pipeline 推两个 tag：`0.0.${CI_PIPELINE_ID}` 和 `latest`。
- 镜像名带两层 `memwise`：第一层是 Harbor project 前缀（namespace），
  第二层是 repository 名（`memwise-app` 等），由 `.gitlab-ci.yml` 的
  `IMAGE_NAME` 控制。
- **静态依赖镜像**（非 CI 构建，需手动推一次，且每个环境仓库各推一份）：
  - `memwise/paradedb:v0.22.2-pg17`
  - `memwise/redis:7.0-alpine`
- YAML 里的仓库地址只是**回退默认值**；GitLab CI/CD Variables 里
  `DOCKER_NAMESPACE_PRODUCTION` / `DOCKER_USER_PRODUCTION` 等同名
  `_DEVELOPMENT` / `_PRODUCTION` 变量会覆盖它们（沿用 cicd-common 约定）。
- **注意**：cicd-common / Group 级可能注入的是不带 memwise 的 base namespace
  （如 `DOCKER_NAMESPACE_DEVELOPMENT=deeproute-staging`）。docker job 脚本会对最终
  `DOCKER_NAMESPACE` 做归一化，**强制保证末级是 `/memwise`**，所以无论覆盖值是否带
  memwise，推送目标都只会是 `deeproute-{staging,production}/memwise/...`，不会推错项目。

## 3. 流水线行为

流程两段：`build:frontend`（npm ci + vite build）→ 三个 docker job 并行打镜像。
后端不再预编译，用 `docker/Dockerfile.app` 多阶段在 `golang:1.26-bookworm` 里编。

| 场景 | 是否出流水线 | 行为 |
|---|---|---|
| 推送到 `deeproute-dev` | 自动 | build:frontend + 三个镜像 → **staging** |
| 推送到 `deeproute-master` | 自动 | build:frontend + 三个镜像 → **production** |
| 推送到其它分支 | 不出 | 无流水线 |
| 其它分支点 GitLab「Run pipeline」（web） | 手动 | 只跑 `build:frontend`；docker job 的 rules 只放行 dev/master，**不构建也不推镜像** |

每个 docker job 日志会打印
`branch=… namespace=… image=…`，用于核对最终镜像路径与目标 Harbor。

## 4. 标准开发流程（新功能 / Bugfix）

```bash
# 0) 确保本地 dev 最新
git fetch origin

# 1) 从 deeproute-dev 拉功能分支（不要在 deeproute-master 上拉）
git checkout -b feature/my-feature origin/deeproute-dev

# 2) 开发、本地验证；推送前不会触发任何镜像构建
#    （确实想远程验一下能否编译时，可在 GitLab UI 手动 Run pipeline，它不推镜像）

# 3) 推送并开 MR → deeproute-dev
git push -u origin feature/my-feature
#   GitLab: new merge request → target deeproute-dev

# 4) 评审后合入 deeproute-dev
```

- **能不能 squash？** 能，且建议。合入 `deeproute-dev` 的 MR 建议勾选
  **Squash commits**，让 dev 主线保持每个功能一个提交、历史线性；
  功能分支里的中间提交没必要保留。
- 合入 `deeproute-dev` 后流水线自动跑，staging 镜像即更新，可在 staging 验证。
- 不要在功能分支上反复 push 到 GitLab（无 MR 时不会触发流水线，纯属噪音）。

## 5. 发版到生产

`deeproute-master` **只在你要发版时才推进**；推进那一刻会触发 production 镜像构建。
平时不要动它。两种推进方式任选：

### 方式 A：快速推进（推荐，dev 内容 == master 内容）

由于 master 始终是 dev 的"发布指针"、内容刻意保持一致，发版就是一次
fast-forward：

```bash
git fetch origin
git push origin origin/deeproute-dev:deeproute-master
# 前提：master 没有任何独立提交（见下），因此是 fast-forward，不需要 -f
```

> 若 master 从未创建：先 `git push origin origin/deeproute-dev:refs/heads/deeproute-master` 创建一次。

### 方式 B：评审门禁（想在 MR 上看 dev→master 差异再放行）

```bash
# 首次创建：
git fetch origin
git push origin origin/deeproute-dev:refs/heads/deeproute-master

# 之后每次发版在 GitLab 上建 MR：deeproute-dev → deeproute-master，评审后合并
```

**何时算"一次发版"？** 只有当你主动把 `deeproute-master` 推到某个 dev 提交时，
production 才重新构建（`latest` + 新 `0.0.<pipeline>`）。不做这个动作，
dev 上堆多少代码都不会影响生产镜像。

## 6. 冲突 / 差异问题答疑

**Q：会不会出现 `deeproute-dev` 与 `deeproute-master` 差异导致的冲突？**

- **CI 文件不会**：两侧共用同一份 `.gitlab-ci.yml`，且都从同一历史演进，
  不存在"两侧 CI 不同步"。真正的环境差异在运行时由分支决定。
- **业务代码会**，但只在一种情况：`deeproute-master` 长时间不跟随
  `deeproute-dev`，导致 master 落后很多；之后再想从 dev 拉取/合并时，
  老文件两边都改过就可能冲突。

**对策（保持 master ≈ dev）：**

1. 发版节奏短：功能合入 dev 并验证后尽快推到 master，缩小落后窗口。
2. master **只接受来自 dev 的前进**，永远不要直接改 master
   （包括热修：先在 dev 修好 → 走 MR → 再 fast-forward 到 master）。
3. 由于 master 正常情况下就是 dev 的一个提交指针，两者**没有内容差异**，
   也就没有冲突可言。

**Q：热修上线太慢怎么办？**
热修仍走 feature → dev 的正常流程；dev 合入即出 staging，验证后
fast-forward 到 master 即出 production，路径不变、且不会在 master 上留下
dev 没有的 commit。

## 7. 建议的 GitLab 权限与配置

| 项 | 建议 |
|---|---|
| `deeproute-dev` | 允许 MR；是否允许直接 push 团队自定 |
| `deeproute-master` | **设为 Protected**：禁止直接 push，禁止 force push，只有 owner 能合并/推进；发版即手动执行一次 fast-forward |
| CI/CD Variables | 若 Group/项目里没有 `DOCKER_USER` / `DOCKER_PASSWORD`，需配置 `DOCKER_USER_DEVELOPMENT` / `_PRODUCTION`、`DOCKER_PASSWORD_*`；需要覆盖 namespace 时配 `DOCKER_NAMESPACE_*`。不改也行——YAML 默认值已指向 `memwise` |
| Harbor | `deeproute-staging/memwise` 与 `deeproute-production/memwise` 两个 project 都要存在；`paradedb`、`redis` 各推一份；K8s 集群有拉取授权（或配 docker-registry secret） |

## 8. Helm 部署

chart（`helm/`）只维护一份，环境差异靠**部署时选 overlay**：

- staging 集群：`helm upgrade weknora ./helm -f helm/values-stg.yaml ...`
- production 集群：`helm upgrade weknora ./helm -f helm/values-prod.yaml ...`

两份 overlay 都随仓库走，默认 `app/frontend/docreader` 镜像 tag 为 `latest`
（即 CI 每次推完，`helm upgrade` 就能拉到最新）；需要锁定某个 pipeline 时：

```bash
helm upgrade weknora ./helm -n weknora \
  -f helm/values-stg.yaml \
  --set app.image.tag=0.0.12345 \
  --set frontend.image.tag=0.0.12345 \
  --set docreader.image.tag=0.0.12345
```

> `postgresql` / `redis`（即 paradedb / redis）是静态镜像，tag 固定
> `v0.22.2-pg17` / `7.0-alpine`，不随 CI 变。完整部署说明见 `helm/README.md`。
