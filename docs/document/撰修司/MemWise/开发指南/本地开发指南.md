# WeKnora 本地开发指南

本文说明如何在本地进行 WeKnora 后端和前端开发，同时继续使用 Docker 容器提供 PostgreSQL、Redis、DocReader 等基础设施依赖。

本文基于当前仓库结构和开发脚本编写，项目目录假设为：

~~~text
/sandbox/WeKnora
~~~

如果你的代码目录不同，请将命令中的路径替换为实际路径。

## 1. 开发模式概览

本地开发模式的组件关系如下：

~~~text
浏览器 localhost:5173
        |
        v
本地 Vite 前端
        |
        | /api、/files 代理到 localhost:8080
        v
本地 Go 后端 localhost:8080
        |
        v
Docker 基础设施容器
PostgreSQL / Redis / DocReader / MinIO / Qdrant / Neo4j ...
~~~

| 组件 | 运行方式 | 默认地址 | 是否必需 |
| --- | --- | --- | --- |
| WeKnora 后端 | 本地 Go 进程 | localhost:8080 | 是 |
| WeKnora 前端 | 本地 Vite 进程 | localhost:5173 | 是 |
| PostgreSQL | Docker 容器 | localhost:5432 | 标准版必需 |
| Redis | Docker 容器 | localhost:6379 | 推荐，流处理和任务队列使用 |
| DocReader | Docker 容器 | localhost:50051 | 上传和文档解析需要 |
| MinIO | Docker 容器 | localhost:9000，控制台 9001 | 使用 MinIO 存储时需要 |
| Qdrant | Docker 容器 | localhost:6333，gRPC 6334 | 使用 Qdrant 时需要 |
| Neo4j | Docker 容器 | localhost:7474，Bolt 7687 | 使用知识图谱时需要 |
| Langfuse | Docker 容器 | localhost:3000 | 可选，开发脚本默认开启 |
| Dex | Docker 容器 | localhost:5556 | 测试本地 OIDC 时需要 |

后端和前端直接运行在宿主机，其他未修改的组件继续运行在 Docker 中。修改后端不需要重新构建 app 镜像，修改前端也不需要重新构建 frontend 镜像。

## 2. 前置依赖

建议使用 Linux 或 macOS，并准备：

- Git
- Docker Engine 或 Docker Desktop
- Docker Compose v2，或可用的 docker-compose 命令
- Go，版本以仓库 go.mod 中的声明为准
- Node.js 和 npm，建议使用团队约定的 LTS 版本
- GNU Make、curl
- C/C++ 编译工具和 SQLite 开发包

检查工具：

~~~bash
git --version
docker --version
docker compose version
go version
node --version
npm --version
make --version
curl --version
~~~

### 2.1 Go/CGO 依赖

WeKnora 使用 SQLite 相关 CGO 依赖。标准版默认使用 PostgreSQL，但本地编译仍建议准备 C 编译器、pkg-config 和 SQLite 开发包。

Ubuntu/Debian：

~~~bash
sudo apt-get update
sudo apt-get install -y build-essential pkg-config libsqlite3-dev
~~~

macOS：

~~~bash
xcode-select --install
~~~

不要为了绕过编译错误直接关闭 CGO；这可能导致 SQLite 相关功能无法编译或运行。

### 2.2 前端依赖

进入前端目录检查 Node.js 和 npm：

~~~bash
cd /sandbox/WeKnora/frontend
node --version
npm --version
~~~

项目使用 frontend/package-lock.json 锁定依赖。首次安装或 lock 文件发生变化时使用：

~~~bash
npm ci
~~~

只有在需要更新依赖版本时才使用 npm install，并检查 lock 文件的变更。

## 3. 准备配置

进入仓库根目录：

~~~bash
cd /sandbox/WeKnora
~~~

首次使用且不存在 .env 时：

~~~bash
cp .env.example .env
~~~

开发脚本要求 .env 存在。可以额外创建 .env.local，脚本会在加载 .env 后使用它覆盖本地配置。不要把真实密码、API Key、OIDC Client Secret 等敏感信息提交到 Git。

### 3.1 本地 Docker 依赖配置

本地后端访问 Docker 容器的宿主机映射端口，推荐在 .env.local 中准备：

~~~dotenv
DB_DRIVER=postgres
DB_HOST=localhost
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=CHANGE_ME
DB_NAME=WeKnora

REDIS_ADDR=localhost:6379
REDIS_PASSWORD=CHANGE_ME

DOCREADER_ADDR=localhost:50051
DOCREADER_TRANSPORT=grpc

STORAGE_TYPE=local
LOCAL_STORAGE_BASE_DIR=/sandbox/WeKnora/.local-data/files
~~~

scripts/dev.sh app 在本地开发模式下会自动将下列地址转换为宿主机地址：

~~~text
DB_HOST=localhost
DOCREADER_ADDR=localhost:50051
MINIO_ENDPOINT=localhost:9000
REDIS_ADDR=localhost:6379
MILVUS_ADDRESS=localhost:19530
NEO4J_URI=bolt://localhost:7687
QDRANT_HOST=localhost
~~~

如果 LOCAL_STORAGE_BASE_DIR 为空或仍为容器路径 /data/files，脚本会改用仓库内的 .local-data/files 并自动创建目录。

### 3.2 使用远程基础设施

如果数据库、Redis、DocReader 已经运行在另一台开发机，可以配置：

~~~dotenv
DEV_REMOTE_HOST=192.168.1.100
~~~

此时 make dev-start 会跳过本地 Docker 基础设施，make dev-app 会默认将依赖服务指向该主机。也可以显式配置：

~~~dotenv
DB_HOST=192.168.1.100
REDIS_ADDR=192.168.1.100:6379
DOCREADER_ADDR=192.168.1.100:50051
~~~

远程开发需要确认防火墙、Docker 端口映射和网络路由允许访问 5432、6379、50051 等端口。

## 4. 启动 Docker 基础设施

### 4.1 推荐方式

终端 1 执行：

~~~bash
cd /sandbox/WeKnora
make dev-start
~~~

该命令通过 docker-compose.dev.yml 启动基础设施，默认包括：

- PostgreSQL
- Redis
- DocReader
- Langfuse

默认不会启动 MinIO、Qdrant、Neo4j、Dex 等可选组件。

### 4.2 按需启用可选组件

~~~bash
# 基础设施 + MinIO
make dev-start DEV_ARGS=--minio

# 基础设施 + Qdrant
make dev-start DEV_ARGS=--qdrant

# 基础设施 + Neo4j
make dev-start DEV_ARGS=--neo4j

# 基础设施 + Dex，用于本地 OIDC 测试
make dev-start DEV_ARGS=--dex

# 基础设施 + OpenDataLoader hybrid
make dev-start DEV_ARGS=--odl-hybrid

# 启动所有可选服务
make dev-start DEV_ARGS=--full
~~~

按功能选择组件：

- STORAGE_TYPE=minio 时启动 --minio。
- 使用 Qdrant 向量引擎时启动 --qdrant。
- 开启知识图谱功能时启动 --neo4j。
- 测试 Dex/OIDC 时启动 --dex。
- 只有使用 OpenDataLoader hybrid 解析器时才启动 --odl-hybrid。

### 4.3 直接使用 Docker Compose

~~~bash
docker compose -f docker-compose.dev.yml up -d
~~~

启用 Profile：

~~~bash
docker compose -f docker-compose.dev.yml \
  --profile minio --profile qdrant up -d
~~~

日常开发建议使用 make dev-start，因为脚本会检查 Docker、读取 .env/.env.local、解析 Profile，并输出后续启动提示。

### 4.4 查看状态和日志

~~~bash
make dev-status
make dev-logs
~~~

也可以直接查看：

~~~bash
docker compose -f docker-compose.dev.yml ps
docker compose -f docker-compose.dev.yml logs -f postgres redis docreader
~~~

PostgreSQL 首次启动可能需要等待初始化。后端启动前，至少确认 PostgreSQL、Redis 和 DocReader 已经运行。

## 5. 编译和启动后端

### 5.1 推荐方式：开发脚本

终端 2 执行：

~~~bash
cd /sandbox/WeKnora
make dev-app
~~~

等价命令：

~~~bash
./scripts/dev.sh app
~~~

脚本会：

1. 检查 Go 是否安装。
2. 加载 .env 和 .env.local。
3. 将本地 Docker 服务地址转换为 localhost。
4. 创建本地文件存储目录。
5. 设置 CGO 编译参数。
6. 检测到 air 时启用热重载，否则使用 go run ./cmd/server。

后端默认地址：

~~~text
http://localhost:8080
~~~

健康检查：

~~~bash
curl -f http://localhost:8080/health
~~~

Swagger：

~~~text
http://localhost:8080/swagger/index.html
~~~

### 5.2 生成本地后端二进制

需要明确验证编译产物时：

~~~bash
cd /sandbox/WeKnora
make build
~~~

产物为：

~~~text
/sandbox/WeKnora/WeKnora
~~~

加载开发环境并启动二进制：

~~~bash
cd /sandbox/WeKnora
set -a
source .env
if [ -f .env.local ]; then source .env.local; fi
set +a

export DB_HOST=127.0.0.1
export DOCREADER_ADDR=127.0.0.1:50051
export REDIS_ADDR=127.0.0.1:6379
export MINIO_ENDPOINT=127.0.0.1:9000
export MILVUS_ADDRESS=127.0.0.1:19530
export NEO4J_URI=bolt://127.0.0.1:7687
export QDRANT_HOST=127.0.0.1
export LOCAL_STORAGE_BASE_DIR=/sandbox/WeKnora/.local-data/files

mkdir -p "$LOCAL_STORAGE_BASE_DIR"
./WeKnora
~~~

make build 执行的是：

~~~bash
go build -o WeKnora ./cmd/server
~~~

更接近发布构建的方式：

~~~bash
make build-prod
./WeKnora
~~~

日常开发优先使用 make dev-app，因为它会自动加载环境变量并支持 Air。需要独立验证二进制或模拟发布产物时，再使用 make build 或 make build-prod。

### 5.3 后端热重载

安装 Air：

~~~bash
go install github.com/air-verse/air@latest
export PATH="$(go env GOPATH)/bin:$PATH"
~~~

重新执行：

~~~bash
make dev-app
~~~

仓库根目录中的 .air.toml（如果存在）会被 Air 使用。修改 Go 文件后，Air 会自动重新编译并重启后端。

没有安装 Air 时，修改后端代码需要按 Ctrl+C 停止，再重新执行 make dev-app。

### 5.4 IDE 调试

IDE 的启动目标设置为：

~~~text
cmd/server
~~~

工作目录必须设置为：

~~~text
/sandbox/WeKnora
~~~

调试环境至少需要数据库、Redis、DocReader 和本地文件目录相关变量：

~~~dotenv
DB_DRIVER=postgres
DB_HOST=localhost
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=CHANGE_ME
DB_NAME=WeKnora
REDIS_ADDR=localhost:6379
DOCREADER_ADDR=localhost:50051
DOCREADER_TRANSPORT=grpc
LOCAL_STORAGE_BASE_DIR=/sandbox/WeKnora/.local-data/files
~~~

## 6. 安装和启动前端

### 6.1 安装依赖

终端 3 执行：

~~~bash
cd /sandbox/WeKnora/frontend
npm ci
~~~

如果 node_modules 已存在且 lock 文件没有变化，可以跳过这一步。

### 6.2 启动 Vite

推荐从仓库根目录执行：

~~~bash
cd /sandbox/WeKnora
make dev-frontend
~~~

等价命令：

~~~bash
./scripts/dev.sh frontend
~~~

该命令最终执行 npm run dev，前端默认地址为：

~~~text
http://localhost:5173
~~~

Vite 会代理：

~~~text
/api   -> http://localhost:8080
/files -> http://localhost:8080
~~~

因此浏览器访问 localhost:5173 时，前端请求不需要手工改成 8080。

### 6.3 修改后端代理地址

后端不在 localhost:8080 时：

~~~bash
export VITE_DEV_PROXY_TARGET=http://127.0.0.1:18080
make dev-frontend
~~~

也可以使用：

~~~bash
export FRONTEND_BACKEND_URL=http://127.0.0.1:18080
~~~

配置优先级：

~~~text
VITE_DEV_PROXY_TARGET > FRONTEND_BACKEND_URL > http://localhost:8080
~~~

### 6.4 前端生产构建和测试

~~~bash
cd /sandbox/WeKnora/frontend

# 生产构建
npm run build

# TypeScript/Vue 类型检查并构建
npm run build-with-types

# 类型检查
npm run type-check

# 测试
npm run test
~~~

使用生产构建产物预览：

~~~bash
npm run build
npm run preview
~~~

预览地址默认是：

~~~text
http://localhost:4173
~~~

## 7. 标准启动流程

### 7.1 三个终端

终端 1：启动基础设施。

~~~bash
cd /sandbox/WeKnora
make dev-start
~~~

终端 2：启动本地后端。

~~~bash
cd /sandbox/WeKnora
make dev-app
~~~

终端 3：启动本地前端。

~~~bash
cd /sandbox/WeKnora
make dev-frontend
~~~

浏览器访问：

~~~text
http://localhost:5173
~~~

### 7.2 一键启动

仓库还提供交互式脚本：

~~~bash
cd /sandbox/WeKnora
./scripts/quick-dev.sh
~~~

一键脚本适合快速体验。日常开发建议使用三个终端分别运行基础设施、后端和前端，便于查看日志和单独重启组件。

### 7.3 只开发后端

~~~bash
cd /sandbox/WeKnora
make dev-start
make dev-app
~~~

使用健康检查或 Swagger 验证 API：

~~~bash
curl -f http://localhost:8080/health
~~~

### 7.4 只开发前端

先确保后端已经运行在 localhost:8080，然后：

~~~bash
cd /sandbox/WeKnora/frontend
npm ci
npm run dev
~~~

## 8. 修改代码后的工作流

### 8.1 后端

安装 Air 时：

~~~text
保存 Go 文件 -> Air 自动编译 -> 后端自动重启
~~~

未安装 Air 时：

~~~text
保存 Go 文件 -> Ctrl+C -> make dev-app
~~~

修改环境变量、数据库迁移、依赖或启动参数后，应停止后端并重新执行 make dev-app。

### 8.2 前端

Vite 默认支持热更新：

~~~text
保存 Vue/TypeScript/CSS 文件 -> 浏览器自动刷新或局部更新
~~~

修改 package.json 或 package-lock.json 后：

~~~bash
cd /sandbox/WeKnora/frontend
npm ci
~~~

修改 Vite 配置、代理地址或前端环境变量后，重启 make dev-frontend。

### 8.3 DocReader 和其他容器组件

修改 Go 后端或 Vue 前端不需要重建 Docker 镜像。以下情况才需要重建对应容器：

- 修改 docreader/ 代码或 DocReader Dockerfile。
- 修改 Compose 中的镜像构建参数。
- 修改需要进入容器的运行时依赖。

重建 DocReader：

~~~bash
cd /sandbox/WeKnora
docker compose -f docker-compose.dev.yml build docreader
docker compose -f docker-compose.dev.yml up -d docreader
~~~

OpenDataLoader hybrid 首次使用：

~~~bash
make dev-start DEV_ARGS=--odl-hybrid
~~~

## 9. 数据库迁移

默认 AUTO_MIGRATE=true 时，后端启动会自动执行迁移。

需要手动执行时：

~~~bash
cd /sandbox/WeKnora

# 查看迁移版本
make migrate-version

# 执行迁移
make migrate-up

# 回滚迁移
make migrate-down
~~~

创建新迁移：

~~~bash
make migrate-create name=add_example_field
~~~

迁移命令使用当前 shell 中的数据库环境变量。执行前确认 DB_HOST、DB_PORT、DB_USER、DB_PASSWORD 和 DB_NAME 指向预期数据库。

不要在未确认数据卷的情况下清理数据库。开发环境中的命名卷可能包含本地调试数据。

## 10. 测试和代码检查

### 10.1 后端

~~~bash
cd /sandbox/WeKnora

# 格式化修改过的 Go 文件
gofmt -w path/to/changed.go

# 全部 Go 测试
make test

# 等价命令
go test ./...

# 下载 Go 依赖
make deps

# 静态检查，需要预装 golangci-lint
make lint
~~~

只修改一个模块时，优先运行定向测试：

~~~bash
go test ./internal/application/service/... -count=1
~~~

### 10.2 前端

~~~bash
cd /sandbox/WeKnora/frontend
npm run type-check
npm run test
npm run build
~~~

提交前建议至少确认：

1. 修改的 Go 文件通过 gofmt。
2. 受影响的 Go 包通过定向测试。
3. TypeScript/Vue 修改通过 npm run type-check。
4. 前端生产构建通过 npm run build。

## 11. 停止服务

### 11.1 停止本地后端和前端

在运行后端和前端的终端按：

~~~text
Ctrl+C
~~~

使用 Air 时，停止 Air 主进程，不要只停止某次编译生成的子进程。

### 11.2 停止开发环境容器

~~~bash
cd /sandbox/WeKnora
make dev-stop
~~~

等价命令：

~~~bash
./scripts/dev.sh stop
~~~

该命令会停止并移除 docker-compose.dev.yml 创建的容器，但默认保留命名卷中的数据库、Redis 和 MinIO 数据。

只停止容器、不移除容器：

~~~bash
docker compose -f docker-compose.dev.yml stop
~~~

### 11.3 避免误停完整 Compose 环境

开发环境使用：

~~~bash
docker compose -f docker-compose.dev.yml ...
~~~

完整 Docker 环境使用：

~~~bash
docker compose -f docker-compose.yml ...
~~~

执行停止命令前确认 Compose 文件，避免误停止仍在使用的完整环境。

## 12. 常见问题

### 12.1 Docker 无权限或无法连接

~~~bash
docker info
docker compose version
~~~

如果 Docker daemon 未运行，先启动 Docker Desktop 或 Docker Engine。如果当前用户没有 Docker socket 权限，需要加入 Docker 用户组或使用具备权限的终端。

### 12.2 .env 不存在

~~~bash
cd /sandbox/WeKnora
cp .env.example .env
~~~

然后确认数据库和 Redis 密码与 Compose 配置一致。

### 12.3 后端连接不上 PostgreSQL

~~~bash
make dev-status
docker compose -f docker-compose.dev.yml logs postgres
~~~

本地后端应使用：

~~~text
DB_HOST=localhost
DB_PORT=5432
~~~

不能把 Docker 内部服务名 postgres 用作宿主机后端的地址，除非开发环境另有 Docker 网络配置。

### 12.4 后端连接不上 Redis

~~~bash
docker compose -f docker-compose.dev.yml logs redis
~~~

检查：

~~~text
REDIS_ADDR=localhost:6379
REDIS_PASSWORD=与 .env 一致
~~~

### 12.5 后端连接不上 DocReader

~~~bash
docker compose -f docker-compose.dev.yml logs docreader
~~~

本地后端配置：

~~~text
DOCREADER_ADDR=localhost:50051
DOCREADER_TRANSPORT=grpc
~~~

如果启用了 TLS 或 mTLS，客户端和 DocReader 必须使用匹配的证书、CA、SNI 和认证 Token。

### 12.6 前端 API 404 或 CORS 错误

先检查后端：

~~~bash
curl -f http://localhost:8080/health
~~~

再检查 Vite 启动日志中的代理目标是否为：

~~~text
http://localhost:8080
~~~

后端使用其他端口时：

~~~bash
export VITE_DEV_PROXY_TARGET=http://127.0.0.1:<backend-port>
make dev-frontend
~~~

当前 Vite 配置默认代理 /api 和 /files。新增后端路径时，检查是否也需要增加代理配置。

### 12.7 npm 依赖或 esbuild 失败

~~~bash
cd /sandbox/WeKnora/frontend
node --version
npm --version
rm -rf node_modules
npm ci
npm run type-check
npm run dev
~~~

如果是原生模块或 esbuild 平台二进制错误，确认 Node.js 架构与操作系统匹配，并使用 lock 文件重新安装依赖。

### 12.8 Go/SQLite/链接错误

~~~bash
go env CGO_ENABLED CC CXX
pkg-config --modversion sqlite3
~~~

Ubuntu/Debian：

~~~bash
sudo apt-get install -y build-essential pkg-config libsqlite3-dev
~~~

清理 Go 构建缓存后重试：

~~~bash
go clean -cache
make build
~~~

### 12.9 修改 .env 后没有生效

环境变量只在进程启动时读取。停止后端并重新执行：

~~~bash
make dev-app
~~~

如果修改的是容器环境变量或 Compose Profile，需要重新创建相关容器：

~~~bash
make dev-restart
~~~

### 12.10 端口被占用

~~~bash
ss -ltnp | rg ':5173|:8080|:5432|:6379|:50051'
~~~

修改端口后同步更新代理或组件地址。例如后端使用 18080：

~~~bash
export VITE_DEV_PROXY_TARGET=http://127.0.0.1:18080
make dev-frontend
~~~

## 13. 本地开发和完整 Docker 部署对比

| 项目 | 本地开发模式 | 完整 Docker 模式 |
| --- | --- | --- |
| 后端 | 宿主机 go run 或二进制 | app 容器 |
| 前端 | 宿主机 Vite，默认 5173 | NGINX 容器，默认 80 |
| PostgreSQL | Docker | Docker |
| Redis | Docker | Docker |
| DocReader | Docker | Docker |
| MinIO/Qdrant/Neo4j | 按 Profile 启动 | 按完整配置启动 |
| 后端修改 | 重启或 Air 热重载 | 重建 app 镜像 |

## 16. IAM(OIDC/OAuth2)登录本地联调

> 本节针对「WeKnora 接入公司 IAM(Drauth SSO），登录改为走 OAuth2 授权码流程」的本地验证，补充了 2026-08 实测中踩到的坑。仅用于本地/联调，生产按环境变量切换。

### 16.1.0 域名对应关系（2026-09 起）

WeKnora 前端 / OIDC 回调域名与 IAM(Drauth) 后端域名是**两套**，别混：

| 环境 | WeKnora 前端域名（回调 = `{origin}/api/v1/auth/oidc/callback`） | IAM Drauth 地址（`IAM_BASE_URL`） |
| --- | --- | --- |
| stg | `https://stg-memwise.srv.deeproute.cn` | `https://stg-drplatform-backend.deeproute.cn/drauth` |
| prod | `https://memwise.srv.deeproute.cn` | `https://drplatform-backend.deeproute.cn/drauth` |

- 换 WeKnora 域名/端口，**必须**先在 IAM 侧把 `https://<weknora域名>/api/v1/auth/oidc/callback` 登记进白名单，否则授权跳回被拒。
- 本地联调用 **stg 域名**（`stg-memwise.srv.deeproute.cn`），不经 prod。
- 详细的三进程搭建、自签证书、反代脚本、headless 验证见
  `../../IAM/本地联调与测试指南.md`。

### 16.1 lite 模式(SQLite + 内存队列)最省事

无需 Postgres/Redis/DocReader，单二进制即可跑通登录链路：

```bash
# 构建 lite 二进制(跳过前端打包)
SKIP_FRONTEND=1 make build-lite     # 产物 ./WeKnora-lite

# 用 .env 里配好 OIDC 变量后启动
set -a && . ./.env.lite && set +a
./WeKnora-lite                       # 监听 :8080
```

关键环境变量(值按实际 IAM 环境填，勿提交真实密钥):

```
DB_DRIVER=sqlite
DB_PATH=./data/weknora.db
RETRIEVE_DRIVER=sqlite
STREAM_MANAGER_TYPE=memory
OIDC_AUTH_ENABLE=true
AUTH_IAM_ONLY=true                                  # 全局仅允许 IAM 登录，拦截本地 login/register
IAM_BASE_URL=https://<iam-host>/drauth
OIDC_AUTH_DISCOVERY_URL=https://<iam-host>/drauth/.well-known/openid-configuration
OIDC_AUTH_ISSUER_URL=https://<iam-host>/drauth
OIDC_AUTH_PROVIDER_DISPLAY_NAME="DeepRoute IAM"     # 注意：含空格必须加引号，否则 set -a 会把它当命令
OIDC_AUTH_CLIENT_ID=<client_id>
OIDC_AUTH_CLIENT_SECRET=<client_secret>
OIDC_AUTH_SCOPES="openid profile email"
OIDC_BIND_BY_SUBJECT=true
OIDC_USER_INFO_MAPPING_USER_NAME=username
OIDC_USER_INFO_MAPPING_EMAIL=email
OIDC_AUTH_SYNTHETIC_EMAIL_DOMAIN=<company-domain>   # IAM 不下发 email 时用它合成
SSRF_WHITELIST=<iam-host>                           # 见 16.3
```

### 16.2 无浏览器的 headless 授权码流程(curl 驱动)

联调时不必真开浏览器登录页，可用 IAM 的密码登录接口拿 accessToken 后直接驱动 `/oauth/authorize`，它会带 `code` 302 回调:

```bash
BE=http://127.0.0.1:8080
IAM=https://<iam-host>/drauth
RU=https://<registered-callback>/api/v1/auth/oidc/callback   # 必须是 IAM 已注册的 redirect_uri
RUENC=$(python3 -c "import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1],safe=''))" "$RU")

# 1) 后端生成带签名 state + 下发 nonce cookie
URLRESP=$(curl -s -c ck.txt "$BE/api/v1/auth/oidc/url?redirect_uri=$RUENC")
STATE=$(echo "$URLRESP" | python3 -c "import json,sys;print(json.load(sys.stdin)['state'])")
STATEENC=$(python3 -c "import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1],safe=''))" "$STATE")

# 2) 密码登录换 accessToken(字段可能是 body.accessToken 驼峰)
AT=$(curl -s -X POST "$IAM/auth/login" -H "x-tenant-id: <tid>" -H "Content-Type: application/json" \
      -d '{"providerCode":"<provider>","username":"<u>","password":"<p>"}' \
     | python3 -c "import json,sys;b=json.load(sys.stdin);b=b.get('body',b);print(b.get('accessToken') or b.get('access_token') or '')")

# 3) 带 Bearer 调 authorize，302 直接带 code 回调
LOC=$(curl -s -D - -o /dev/null -H "Authorization: Bearer $AT" \
      "$IAM/oauth/authorize?client_id=<cid>&redirect_uri=$RUENC&response_type=code&scope=openid+profile+email&state=$STATEENC" \
     | grep -i '^location:' | tr -d '\r' | sed 's/^[Ll]ocation: //')
CODE=$(python3 -c "import urllib.parse,sys;print(urllib.parse.parse_qs(urllib.parse.urlparse(sys.argv[1]).query).get('code',[''])[0])" "$LOC")

# 4) 回调换本地 WeKnora token(需带 nonce cookie)
curl -s -D - -o /dev/null -b ck.txt "$BE/api/v1/auth/oidc/callback?code=$CODE&state=$STATEENC" | grep -i '^location:'
# 成功: Location: /#oidc_result=<base64>   失败: /#oidc_error=...
```

浏览器方式:因回调注册的是 HTTPS 域名，需本地 `/etc/hosts` 劫持该域名到 `127.0.0.1`，再起一个 HTTPS 反向代理(Caddy/mkcert）监听 443，把 `/api/*`、`/files/*` 转 `:8080`，其余转 Vite `:5173`；Vite 7 会校验 Host，需在 `vite.config.ts` 的 `server.allowedHosts` 加该域名。

### 16.3 SSRF 白名单(必须)

后端 HTTP 客户端默认阻断私网 IP。若 IAM 主机解析到内网地址(如 10.x），authorize URL 生成或 token 交换会报 `resolves to restricted IP ... private IP address`。用 `SSRF_WHITELIST` 放行(精确主机名 / 通配 / CIDR，逗号分隔）:

```
SSRF_WHITELIST=<iam-host>
```

### 16.4 Drauth 非标准响应的兼容点(已在代码处理)

实测 Drauth 与标准 OIDC 有三处差异，`internal/application/service/user.go` 已做兼容(改动别回退）:

- `/oauth/token` 返回 `{"body":{...},"status":"SUCCESS"}` 外壳，且字段是**驼峰** `accessToken`/`idToken`/`tokenType`——`oidcTokenResponse.UnmarshalJSON` 同时容忍下划线与驼峰、并解包 `body`。
- userinfo 同样有 `{"body":{...}}` 外壳，且用户名字段是 `username`（非 `preferred_username`)——`fetchOIDCUserInfo` 解包 `body`，`resolveOIDCUserInfo` 增加 `username` 兜底。
- iss 不一致:access_token 的 `iss` 是短名 `drauth`，id_token 的 `iss` 是完整 URL。后端解 id_token，故 `(issuer, subject)` 绑定存的是**完整 URL**。

### 16.5 已知坑:SQLite 全量快照滞后于 Postgres 版本化迁移

> 这是仓库既有问题，与 IAM 无关，但会挡住 lite 模式建号。

`migrations/sqlite/000000_init.up.sql` 是 SQLite 的一次性全量建表快照，而 `migrations/versioned/`(Postgres）已到 000084。二者未同步，快照缺了后续迁移新增的列/表，实测触发:

- `table tenants has no column named api_principal_config`(建 workspace 失败)
- `table users has no column named is_system_admin`(建 user 失败)
- `no such table: system_settings` / `task_pending_ops`(仅 WARNING，有 env fallback，不致命)

临时解法(联调用，非根治）——给现有本地库补列:

```bash
python3 - <<'PY'
import sqlite3; c=sqlite3.connect('data/weknora.db')
def addcol(t,col,decl):
    if col not in [r[1] for r in c.execute(f"PRAGMA table_info({t})")]:
        c.execute(f"ALTER TABLE {t} ADD COLUMN {col} {decl}"); print("added",t,col)
addcol("tenants","api_principal_config","TEXT DEFAULT NULL")
addcol("users","is_system_admin","NUMERIC DEFAULT 0")
c.commit(); c.close()
PY
```

根治建议:把这些缺失列/表补进 `migrations/sqlite/000000_init.up.sql` 快照，或新增一条 SQLite 迁移使其与 Postgres 对齐(单独提 PR，不在 IAM 分支处理）。
