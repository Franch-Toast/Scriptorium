### 2.2 Step2 Driver 下载+解压分析 (36,657ms)

- Driver 包大小: \~4.5GB (STRIP_DRIVER zip)
- 下载+解压是整个入库流程的最大瓶颈
- **优化建议**:

  1. Driver 包缓存命中时可跳过（已实现，但首次分析无法避免）
  2. 考虑增量下载或只下载需要的二进制文件
  3. 使用更快的解压算法或并行解压

### 2.3 Step3b 符号索引生成分析 (9,472ms)

- 对 Driver 包中所有二进制文件生成符号索引
- **优化建议**:

  1. 符号索引持久化缓存（已实现 `.symindex.json.gz`）
  2. 增量索引：只索引新增的二进制文件
  3. 并行化索引生成

## 六、优化建议汇总

### 高优先级

1. **Driver 包增量下载**: 只下载实际需要的二进制文件（根据 folded 数据中出现的进程名），而非整个 4.5GB 包
2. **Driver 包预缓存**: 对常用车辆/版本的 Driver 包进行预缓存

### 中优先级

1. **pprof 转换批量优化**: 减少 per-section gzip 压缩次数，合并多个 section 后一次性压缩
2. **符号索引增量更新**: 对已索引的二进制跳过重新索引
3. **FrostDB 查询优化**: 添加更精确的 partition pruning，减少扫描行数
4. **resolveStacks 批量写入**: 优化 Arrow builder 的内存分配模式

### 低优先级

1. **服务端 trim 阈值调整**: 增大默认 trim 阈值，减少传输到前端的节点数
2. **前端虚拟化渲染**: 确保只渲染视口内的火焰图节点（已部分实现 useVisibleNodes）
3. **Arrow IPC 压缩**: 在 gRPC-Web 层启用更高效的压缩

**查询阶段优化详情：**

1. Arrow Builder 预分配容量：`NewLocationsWriterWithCapacity` 预计算 stack 数量和 location 总数，减少 builder 扩容次数
2. 移除非 FrostDB 列的 GROUP BY：`function_name` 等火焰图展示字段不再传给 FrostDB 聚合
3. 添加 Explain 日志：便于后续诊断查询计划

**重要发现：selectMerge 性能对 FrostDB 数据布局敏感**

- 多次重复入库同一 trip 会导致 FrostDB block 数量增加，selectMerge 从 960ms 膨胀到 2900ms+
- 清除旧数据后重新入库，selectMerge 恢复到 \~1000ms

### 7.7 优化3 — FrostDB 数据去重（入库前清除旧数据）

**问题**：重复分析同一 trip 时，FrostDB 会累积多份相同数据，导致 `selectMerge` 查询性能线性退化。

**方案**：在每次入库前，通过 `FrostDBResetter` 执行 `DropDB` + 重建 DB/Table，确保数据干净。使用 `swappableIngester` 实现运行时原子替换 ingester 实例。

**实现文件**：

- `pkg/flamecraft/parca.go` — `swappableIngester` + `FrostDBResetter`
- `pkg/foldedresolver/handler.go` — `DataResetter` 接口定义
- `pkg/foldedresolver/trip_handler.go` — Step 4b 调用 `ResetData`
- `pkg/server/server.go` — 注入 `DataResetter`

**验证结果（两次连续分析同一 trip）**：

| 指标 | 去重前（第2次入库） | 去重后（第2次入库） | 变化 |
|-|-|-|-|
| selectMerge | 2,900ms+ | **1,032ms** | **-64%** |
| FrostDB records | 多个 block | **1 record** | 数据干净 |
| Query 总计 | 4,000ms+ | **2,589ms** | **-35%** |
| FrostDB Reset 耗时 | N/A | \~80ms（首次）/ \~2.6s（有数据时） | 可接受 |

**结论**：去重机制有效解决了重复入库导致的查询性能退化问题，确保每次查询都在干净的单份数据上执行。
