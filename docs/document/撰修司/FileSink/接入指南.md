# FileSink 接入示例、Planning 迁移与验证

本文示例使用当前头文件真实接口。示例中的 256 任务、2MiB、500ms 等是演示选择，业务应按快照大小、频率和退出要求配置；库默认值见[API](./api接口.md)。以下 3 个带 main 的 C++ 代码块分别可作为独立文件编译，另有 Work 扩展片段。

## 1. 先确定生命周期与降级策略

在接入前写清 5 个决定：

1. 数据是可丢调试记录，还是最终状态恢复缓存？前者用 FileSink/Executor，后者优先 Cache。
2. 同路径哪些写、删、改名存在依赖？将它们归属同一 stream 或同一 Cache key。
3. 提交失败怎么办？帧内只计数、丢弃或留待业务下一次更新，不能同步补写、循环重试或等待 ticket。
4. 谁拥有快照？移交后是否仍有可变 alias、arena 回收、this 销毁等风险？
5. 谁在启动初始化和管理停机时观察结果？需要保留尾批还是允许快速丢弃？

不要在每一帧临时创建 executor、Cache 或 FileSink。路径解析、环境变量、线程创建、Config 校验、流/key 分配均在启动阶段完成。帧内也不应为“判断是否有文件”先调用 exists/stat；文件状态应由 worker 或初始化结果提供。

## 2. FileSink：滚动 CSV 的完整接入

例子使用独立 executor，open 在启动阶段等待确认；帧函数只提交自带换行的记录并统计拒绝。关闭前停止生产者，管理线程共享一个 500ms 等待截止点。`fastShutdown=false` 保留关闭时的尾批；显式 flush 的结果也被检查。

~~~cpp
// example: file_sink_lifecycle.cc
#include "base/file_sink/file_sink.h"

#include <atomic>
#include <cerrno>
#include <chrono>
#include <cstdio>
#include <string>
#include <thread>
#include <utility>

namespace io = deeproute::common;
using namespace std::chrono_literals;
using Clock = std::chrono::steady_clock;

// 只供启动/停机管理线程使用，帧内禁止这种重试。
template <class Submit>
io::FileSubmission SubmitControlUntil(Submit submit, Clock::time_point deadline) {
  for (;;) {
    auto s = submit();
    if (s || s.ticket.result().error != EBUSY || Clock::now() >= deadline)
      return s;
    std::this_thread::sleep_for(1ms);
  }
}

bool WaitSuccessUntil(const io::FileSubmission& s, Clock::time_point deadline) {
  if (!s) return false;
  if (!s.ticket.done()) {
    const auto remaining = std::chrono::duration_cast<std::chrono::milliseconds>(
        deadline - Clock::now());
    // 防止把剩余 0ms 传给 wait：0 表示无限等待。
    if (remaining.count() <= 0 || !s.ticket.wait(remaining)) return false;
  }
  return s.ticket.status() == io::FileTaskStatus::Succeeded;
}

// 业务帧调用。不在这里 printf/MLOG、wait、flush 或同步补写。
bool OnFrame(io::FileSink& sink, std::string record,
             std::atomic<size_t>& rejected) {
  auto s = sink.appendAsync(std::move(record));
  if (!s) {
    rejected.fetch_add(1, std::memory_order_relaxed);
    return false;
  }
  return true;  // 仅表示接收，不是落盘确认
}

int main() {
  // 启动管理阶段：先建池，再建 sink。
  io::AsyncFileExecutor::Config pool_config;
  pool_config.max_tasks = 256;
  pool_config.max_bytes = 2 * 1024 * 1024;
  pool_config.workers = 2;
  pool_config.thread_name = "trajectory_dump";
  io::AsyncFileExecutor executor(pool_config);

  io::FileSink::Config config;
  config.outputDir = "/tmp/file_sink_docs/csv";
  config.filePrefix = "trajectory";
  config.fileHeader = "timestamp,x,y";
  config.batchMode = io::FileSink::BatchMode::Auto;
  config.batchSize = 100;
  config.autoFlushInterval = 200ms;
  config.maxFileSizeMB = 50;
  config.maxFileCount = 20;
  config.fastShutdown = false;
  io::FileSink sink(config, executor);

  const auto start_deadline = Clock::now() + 500ms;
  const auto opened = SubmitControlUntil([&] { return sink.openAsync(); },
                                         start_deadline);
  if (!WaitSuccessUntil(opened, start_deadline)) return 1;

  std::atomic<size_t> rejected{0};
  OnFrame(sink, "1000,1.0,2.0\n", rejected);
  OnFrame(sink, "1020,1.1,2.2\n", rejected);

  // 管理停机阶段：实际业务先停止/汇合全部 OnFrame 生产者。
  const auto deadline = Clock::now() + 500ms;
  const auto flushed = SubmitControlUntil([&] { return sink.flushAsync(); },
                                          deadline);
  const bool flush_ok = WaitSuccessUntil(flushed, deadline);
  // flush 失败/超时仍发出一次关闭请求；重试只发生在管理期限内。
  const auto closed = SubmitControlUntil([&] { return sink.closeAsync(); },
                                         deadline);
  const bool close_ok = WaitSuccessUntil(closed, deadline);
  const auto stats = sink.getStats();
  std::printf("rejected=%zu failures=%zu bytes=%zu\n",
              rejected.load(), stats.failedWrites, stats.totalBytes);
  executor.stop(false);
  // 演示允许 debug 记录被拒绝；计数交给监控，不能据此阻塞帧。
  return flush_ok && close_ok && stats.failedWrites == 0 ? 0 : 2;
}
~~~

上例的期限约束的是管理线程的 ticket 等待，不是 syscall 完成期限，也不是严格硬实时端到端保证。若 close 入队失败，FileSink 会尽力保留关闭意图；退出是否完成仍需观测，不能把 false 当作“已关闭”。不要在帧线程照搬 WaitSuccessUntil。

若业务只要最佳努力日志，可保留 fastShutdown=true 并接受尾批丢弃。若要压缩，只需在初始化设置 `config.format = io::FileSink::Format::Compressed`；读取端要支持 zstd 多 frame。无批量追加则设置 BatchMode::None。

### 共享 FileWriter 池的配置顺序

需要全进程多个默认 FileSink 共享预算时，在**构造第一个 sink 之前**执行以下启动代码：

~~~cpp
// API 配置片段：嵌入业务 Init，非独立 main。
deeproute::common::FileWriter::Config writer_config;
writer_config.maxQueueSize = 1000;
writer_config.maxQueueSizeBytes = 10 * 1024 * 1024;
writer_config.workerThreadCount = 2;
writer_config.syncIntervalBytes = 2 * 1024 * 1024;
const bool initialized =
    deeproute::common::FileWriter::getInstance().initialize(writer_config);
// initialized=false 时由启动流程处理；成功后再构造默认 FileSink。
~~~

FileWriter 已被惰性初始化后，再 initialize 会返回 true 而不应用新配置。调试输出与重要恢复缓存仍建议分池；不要以增加 worker 数代替业务限频。

## 3. AsyncFileCache：protobuf 保存与删除

下面用 protobuf 自带 Struct 作为可编译示例，实际替换为项目的恢复 proto。key 在启动时固定；所有更新/删除都走同一 Cache。Frame 侧先检查快照大小再复制，文本序列化与 fsync 留在 worker。

~~~cpp
// example: latest_cache.cc
#include "base/file_sink/async_file_cache.h"
#include "base/file_sink/async_proto_file.h"
#include <google/protobuf/struct.pb.h>

#include <chrono>
#include <memory>
#include <new>
#include <utility>

namespace io = deeproute::common;
using namespace std::chrono_literals;
constexpr size_t kRecovery = 0;

bool SaveLatest(io::AsyncFileCache& cache,
                const google::protobuf::Struct& frame_state) {
  // 演示业务单快照限制；Cache 总预算还包括旧在途及 desired。
  if (frame_state.SpaceUsedLong() > 1024 * 1024) return false;
  try {
    auto snapshot =
        std::make_shared<const google::protobuf::Struct>(frame_state);
    auto op = io::ProtoFileOperation("", std::move(snapshot));
    // Cache 会用固定 key 的 path 覆盖 op.path。
    op.durability = io::FileDurability::FileSync;
    return cache.publish(kRecovery, std::move(op));
  } catch (const std::bad_alloc&) {
    return false;  // 帧继续输出，由业务计数/降频
  }
}

int main() {
  io::AsyncFileCache::Config config;
  config.paths = {"/tmp/file_sink_docs/cache/recovery.txt"};
  config.max_snapshot_bytes = 4 * 1024 * 1024;
  io::AsyncFileCache cache(std::move(config));  // 启动阶段

  google::protobuf::Struct state;
  (*state.mutable_fields())["revision"].set_number_value(1);
  const bool first = SaveLatest(cache, state);
  const bool deleted = cache.remove(kRecovery);  // 删除也是最新状态
  (*state.mutable_fields())["revision"].set_number_value(2);
  const bool latest = SaveLatest(cache, state);
  // first / deleted 对应的中间版本允许不落盘，最终期望为 revision=2。
  if (!first || !deleted || !latest) return 1;

  // 管理阶段，确认不再有并发 publisher 后才做 drain。
  if (!cache.drain(500ms)) return 2;
  const auto health = cache.health(kRecovery);
  return health.saved_generation >= health.desired_generation ? 0 : 3;
}
~~~

如果最终要求是删除，就在最后执行 remove，不要紧接着再次 publish。remove 返回 false 时最新删除并未被接收，业务不能默默当作成功。需要在后续业务周期重申或记录未完成的意图，但不能帧内 while 重试。

Cache 解决进程存活期间的 latest 收敛，不提供掉电 tombstone。进程在删除真正完成前退出，或删除目录项未持久化时，重启仍可能读到旧文件；需要业务恢复校验，或另行设计持久化版本/删除协议。

### 只写一次 proto 时的便捷入口

已有通用 executor、无需 latest 重试时，调用 `WriteProtoASCIIAsync(executor, stream, path, message)` 或 Binary 版本即可。它在调用线程复制 proto，所以仍应先限制 message.SpaceUsedLong，再调用；返回 accepted 后不能马上认为文件可读或持久化完成。

## 4. Executor：备份、替换和清理

把有依赖的操作作为一个 sequence 提交，避免本业务相邻提交穿插；对已接收的后续删除复用同一个 stream。序列中明确设置 rename 的 missing_ok，避免忽略 descriptor 与便利 API 默认值的差异。

~~~cpp
// example: ordered_files.cc
#include "base/file_sink/async_file_executor.h"

#include <chrono>
#include <string>
#include <utility>
#include <vector>

namespace io = deeproute::common;
using namespace std::chrono_literals;

bool CompletedOK(const io::FileSubmission& s) {
  // 仅用于此 main 演示的管理线程。
  return s && s.ticket.wait(500ms) &&
         s.ticket.status() == io::FileTaskStatus::Succeeded;
}

int main() {
  io::AsyncFileExecutor executor;
  const auto stream = io::AsyncFileExecutor::newStream();
  const std::string path = "/tmp/file_sink_docs/sequence/state.txt";

  io::FileOperation backup;
  backup.kind = io::FileOperation::Kind::Rename;
  backup.path = path;
  backup.destination = path + ".bak";
  backup.missing_ok = true;  // 首次不存在源文件允许继续

  io::FileOperation replace;
  replace.path = path;
  replace.data = "revision=2\n";
  replace.durability = io::FileDurability::FileSync;
  std::vector<io::FileOperation> sequence;
  sequence.push_back(std::move(backup));
  sequence.push_back(std::move(replace));
  const auto written = executor.submitSequenceAsync(stream, std::move(sequence));
  if (!CompletedOK(written)) return 1;
  const auto removed = executor.removeAsync(stream, path + ".bak");
  return CompletedOK(removed) ? 0 : 2;
}
~~~

真实帧路径只保留提交和返回值处理；上例 wait 是为了管理程序演示检查结果。sequence 没有回滚；rename 成功、replace 失败时，目标可能只存在于 .bak。上例没有开启 retry，避免重放备份步骤改变恢复结果。单纯更新恢复缓存不需要先备份，应直接 atomicReplace 或 Cache。

### 自定义 Work：拥有数据，完整计费

当格式无法用 FileOperation 表示时可直接 submit。下面是可独立编译的函数片段，调用者提供已预分配的 stream 和 executor：

~~~cpp
// example: custom_work.cc
#include "base/file_sink/async_file_executor.h"

#include <memory>
#include <string>
#include <utility>

namespace io = deeproute::common;

io::FileSubmission SubmitSnapshot(io::AsyncFileExecutor& executor,
                                 io::AsyncFileExecutor::Stream stream,
                                 std::string path, std::string bytes) {
  auto snapshot = std::make_shared<const std::string>(std::move(bytes));
  const size_t charge = snapshot->size();
  return executor.submit(
      stream, charge,
      [path = std::move(path), snapshot](io::FileOperations& files) {
        return files.atomicReplace(path, *snapshot,
                                   io::FileDurability::FileSync);
      });
}
~~~

这里的 make_shared 发生在调用端，仍可能抛 bad_alloc，业务调用边界要按自身策略捕获；该片段不是无异常/无分配实时封装。Work 必须只操作自有快照与 worker 资源，禁止捕获帧栈引用、裸 this、借用文件句柄或调用需要业务主线程推进的同步等待。

## 5. 结果观察与故障降级

帧侧可以读取轻量状态/原子计数，但建议管理监控周期汇总，避免每帧日志放大问题。大量任务不要永久保存全部 tickets；用有界跟踪表或 aggregate stats。需要逐个确认时，在终态后及时释放 ticket。

| 观测面 | 推荐指标 | 解释 |
| --- | --- | --- |
| 实时业务 | frame latency、trajectory 发布间隔、心跳 | 真正的目标，不能只证明 worker 线程存在 |
| executor | running、oldest_running_ms、outstanding、bytes、rejected | 存储是否停顿、是否碰到准入限制 |
| Cache | desired/saved 差值、stage/error、上次成功年龄、rejected | 最新恢复状态是否落后，何处失败 |
| FileSink | rejected 业务计数、failedWrites、尾批条数、编码字节 | 接收丢失与后台失败分开观察 |
| 系统 | CPU、RSS、dirty pages、线程优先级/亲和 | 后台化后的资源竞争和容量影响 |

错误恢复原则：

- 可丢 debug：拒绝即计数丢弃，后续帧继续；必要时降低 dump 频率或关闭。
- latest cache：publish 成功后由 dispatcher 保留意图并重试；publisher 拒绝则未接收，需要业务后续重申。
- 不幂等 append/rename：不自动重放；分析部分成功的结果，必要时引入业务序列号/去重协议。
- 存储持续不可用：业务轨迹继续，持久化健康降级可见；不要为修复日志回退同步 I/O。
- shutdown 超时：报告未完成、按退出策略继续；不无限 join，不声称后台 syscall 被取消。

## 6. Planning 接入案例

### 6.1 缓存与 debug 分路

适配代码：`/sandbox/planning/planning/common/pnc_utils/async_file_io.h:18`、`async_file_io.cpp:28`。

| 业务接口 | 后台机制 | 帧侧契约 |
| --- | --- | --- |
| InitializePlanningFileIO | 创建固定 Cache、64 个 debug hash stream、预热后台 executor | Planning::Load 启动阶段调用 |
| PublishPlanningCache | LastParkin / LastManuallyParkin / TrackingTraj 三个固定 key | 复制不可变快照，发布 desired，不等待 |
| RemovePlanningCache | 同 key 的 Remove desired | 不直接 filesystem::remove |
| PlanningCacheHealth | Cache Health | 看版本差与失败，而非以提交 bool 判定落盘 |
| DrainPlanningFileIO | 只 drain 关键 Cache | 管理阶段限时等待，不包含 debug 输出 |
| WritePlanningDebugProto / SubmitPlanningDebugFiles | 独立于 Cache 的 debug/background executor | 可丢、无帧内重试，路径 hash 保序 |
| AsyncDebugStream | CPU buffer + 后台 Append/AtomicReplace | 格式化不打开文件；close 仅提交，检查 fail 状态 |

算法缓存目录在启动时读取 `DR_MODULE_ALGORITHM_CACHE_DIR`，默认 `/ext_data/debug/algorithm`，转成绝对、词法规范路径。debug 有 64 个路径 hash stream；同路径保序，hash 冲突只增加后台等待，路径别名仍需业务统一。

调试流含 header 最大 1MiB，超限置 badbit 并丢整段；debug proto/图像在复制前检查 10MiB，关键 cache 检查 4MiB。序列化/PNG 编码在 worker，格式化与必要快照复制仍在 producer；这些不是所有资源的精确上限。

### 6.2 时序如何改变

原 last_parkin 保存失败只记日志，内存更新和业务完成不依赖文件成功，因此迁移后以内存状态推进 PARKING_DONE/trajectory，文件在后台最终收敛。last_manually_parkin 及对应删除遵循同一原则。

tracking_traj 原先主要在析构保存。现在在加载/更新坐标转换后最多每秒尝试一次 checkpoint，并用 revision 和车辆位姿变化避免重复快照；记录结束补最终快照，清空缓存时也提交删除意图，防止旧 checkpoint 覆盖清空结果。

准备关闭时先提交最终快照，在 Calculator::Close 管理阶段 drain 最多 500ms。新管理阶段钩子 PrepareForShutdown 与 common 类布局变化都要求依赖方重编，不保证旧 ABI。

原文本格式和恢复校验继续保留；异步化改变完成时间，不提供新的恢复协议。删除失败、未落盘就退出、FileSync 没有目录同步等情况下旧缓存仍可能复活，当前方案明确接受该遗留风险。

### 6.3 哪些仍保留同步语义

初始化配置/恢复文件读取、LQR LUT 生成后立即读回、离线工具仍有同步依赖。若要进一步迁移，应给业务增加初始化等待态/异步加载结果，而不是把读取扔后台后继续使用未准备好的数据。

MLOG 后端、allocator/page fault、第三方库隐式 I/O 不在本次文件 API 迁移范围；车端仍要沿线程栈验证剩余阻塞来源。不要仅凭 API 带 Async 就认定整个帧已没有同步等待。

## 9. 常见误用速查

| 误用 | 后果 | 正确做法 |
| --- | --- | --- |
| accepted 就认为保存成功 | 忽略后续 open/fsync/rename 失败 | ticket 或 Cache Health |
| 每帧 submit 后 wait | 又把存储等待拉回帧线程 | 管理观察，必要时改业务等待态 |
| 队列满后同步补写/循环重试 | 慢盘时再次击穿帧预算 | 丢弃/合并/后续更新 |
| write、remove 使用不同 stream | 删除后旧任务又写回 | 同 stream 或固定 Cache key |
| 把全部路径放同一 latest stream | 无关文件互相替代 | 每逻辑 key 一个 stream |
| FileSink append ticket 成功就读文件 | 数据可能还在尾批 | 管理等待后续 flush/close ticket |
| fastShutdown 默认用于必须完整的尾批 | 关闭丢数据 | false + 显式管理确认 |
| 捕获 Message& / arena 裸指针 | worker 使用已回收或变化内存 | 自有不可变快照 |
| 对部分写失败的 append 开 retry | 重复/损坏记录 | 幂等协议或放弃自动重放 |
| 认为 flush/close 一定 fsync | 误判掉电持久性 | 需要原子替换时显式选择 durability |
| 认为 maxFileCount 是磁盘硬配额 | .tmp、其他文件、检查间隔未计入 | 系统容量监控与业务限流 |
| shutdown timeout 被当作 syscall 取消 | 对在途资源生命周期判断错误 | 允许后台资源保留，按期限退出 |
