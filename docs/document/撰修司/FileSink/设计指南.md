# FileSink 异步 I/O 设计与一致性

本文描述 2026-10-19 工作区的实际实现，版本基线见[入口](./index.md#文档基线)。接口签名见[API](./api接口.md)，可直接改造业务的代码见[接入指南](./接入指南.md)。

## 1. 问题与设计目标

本次 case 的故障链是：RPA 泊入时，planning 帧线程调用包含无条件 fsync 的 `common::SetProtoToASCIIFile`；可写卷被录包/归档打满或严重争用，单帧达到 2.5～6 秒；`/planner/trajectory` 停发，击穿约 1 秒的 CBW 泊车心跳，触发 `CONTROL_PLANNING_LOST_HEARTBEAT(33009)`，继而 BLC MRM、APA/RPA 退出。这些时间和故障码来自本次 case，不是库的性能保证或新测量结果。

问题不局限于 write/fsync。mkdir、open、close、rename、remove、目录扫描、stat 和路径探测都可能等待文件系统。仅将 write 放在线程池、仍让帧线程执行轮转或关闭，无法完整隔离此类等待。

这次设计遵循以下原则：

1. **帧输出优先。** 文件系统等待不进入已迁移的帧路径，提交失败不得退回同步写或忙等。
2. **从提交到关闭都隔离。** FileSink 的 fd、尾批、压缩、轮转和清理由有序 worker 独占。
3. **有限资源、显式降级。** 任务数和逻辑数据量有限；满队列、竞争、停止均可拒绝。业务必须选择丢弃、合并或降频。
4. **语义先于线程。** 先分清“事件追加”“最新状态”“必须先落盘才能继续”，再选择入口。
5. **完成与持久化可观测。** 明确入队、执行、文件可见、掉电持久化之间的差别，不能用一个 bool 混为一谈。

这里的“异步 I/O”是**同步文件系统调用在后台线程执行**，不是 POSIX AIO/io_uring。正在阻塞的 syscall 仍然可能长时间不返回；库隔离它的调用线程并限制新增负载，不能取消内核等待或修复存储设备。

## 2. 业务是否允许异步，先问什么

| 业务关系 | 可采用的设计 | 必须说明的代价 |
| --- | --- | --- |
| 调试 dump 不影响下一帧 | Executor/FileSink，失败可丢 | 日志可能缺失、截断或未完成轮转 |
| 内存状态是权威，文件用于下次启动恢复 | Cache，保存最新期望状态 | 进程退出或掉电前可能尚未保存 |
| rename 备份后再覆盖文件 | 同 stream 的一个 sequence | 有顺序但没有事务回滚 |
| 刚写文件就读回作为算法输入 | 启动阶段同步完成，或改业务状态机 | 不得在帧线程提交后立刻 wait |
| 持久化完成后才允许业务状态跃迁 | 业务等待态 + 管理/后台结果通知 | 需要定义超时、失败及恢复逻辑，单换 Async API 不够 |
| 删除后重启绝不能读到旧状态 | 另行设计持久化 tombstone/版本恢复协议 | 当前 Cache 的删除意图不提供该保证 |

新设计没有修改全局 `SetProtoToASCIIFile` 的同步返回契约；它仍可供确有同步依赖的初始化/工具代码使用。迁移发生在确认可以改变持久化时序的业务调用点。

## 3. 分层与重要对象

~~~mermaid
flowchart TB
    RT[业务帧线程：快照、限额、提交]
    MG[启动 / 管理线程：初始化、观察、限时等待]
    FS[FileSink：滚动追加门面]
    PC[AsyncFileCache：固定 key 最新状态邮箱]
    PH[async_proto_file：快照与序列化适配]
    EX[AsyncFileExecutor：stream 排序、准入、ticket]
    DP[Cache dispatcher：合并与重试准入]
    CE[Cache 独立 executor：单 worker]
    WK[worker：FileOperations / fd / 压缩 / 轮转]
    DISK[文件系统：可能长时间阻塞]
    RT --> FS
    RT --> PC
    RT --> PH
    RT --> EX
    MG --> FS
    MG --> PC
    MG --> EX
    PH --> EX
    FS --> EX
    PC --> DP --> CE
    EX --> WK
    CE --> WK
    WK --> DISK
~~~

- `AsyncFileExecutor` 不依赖 protobuf，负责资源准入、同 stream 串行、不同 stream 并行、延时重试和任务结果。
- `FileOperations` 是 worker 使用的同步文件原语，也是故障注入边界。直接在帧线程调用它会重新引入同步 I/O。
- `FileOperation` 表示写、追加、删、改名及其快照；`FileSubmission` 表示是否接收，`FileTicket` 表示后续状态。
- `AsyncFileCache` 处理“希望某个路径最终是什么状态”，补上普通提交被拒绝后没有持久化意图的问题。它使用专属 dispatcher 和单 worker，不复用调试输出池。
- `FileSink` 处理连续日志文件的批量、压缩、轮转和清理，不将所有文件业务强行解释为日志。
- `FileWriter` 保留老的 FdGuard 接口，并为默认 FileSink 提供共享池。它不再为 FileSink 增设第二层批处理。

为什么不让所有业务共用一个线程？单 worker 会让一个慢盘请求阻塞所有文件业务。多 worker 能隔离部分 stream，但全部 worker 被同一存储拖住仍会停止推进。因此重要恢复缓存与大量 debug 数据分池。**分池隔离线程占用，不隔离底层磁盘带宽、文件系统服务或 CPU 资源。**

## 4. Stream：依赖关系由调用者指定

同一 executor 内，一个 stream 同时最多执行一个任务；普通任务按成功准入顺序推进。多个生产者并发提交时，以内部成功准入顺序为准，不保证按函数调用开始时间排序。

`Stream` 不是文件路径。使用不同 stream 写同一文件、不同 executor 写同一文件、路径别名或符号链接指向同一文件，都不会自动建立互斥或因果关系。业务应在初始化时分配 stream，并在同一逻辑资源的所有操作中复用。

`SubmitOptions.delay` 用于延时任务；尚未到期的任务可被同 stream 的普通任务越过，所以不能将延时任务当作严格 FIFO 屏障。失败后的 retry 保留该 stream 的重试顺序；较新的 latest 意图可以替代旧重试。

### Sequence 有序，但不是事务

`submitSequenceAsync` 将多个 FileOperation 放到一个 worker 任务中，逐项执行，首个失败就停止。一个合法用途是“备份旧文件 → 原子替换新文件”，防止本业务的下一次覆盖插到两步之间。

它不提供多文件事务：若 rename 成功、新文件写失败，备份已存在，旧目标路径可能已不存在。其他 stream/进程仍可能观察或修改中间状态。sequence 返回首个失败或最后一步结果，其中 published 不是整条 sequence 的累计修改标记；后续失败的 published=false 不代表前面没有成功修改文件。开启 retry 会从第一步重放整个 sequence，必须确认每一步及其组合均可幂等；append 和普通 rename 不应盲目重试。

## 5. 准入、背压与内存

Executor 的 `submit` 使用 try-lock，不等待 worker 的 syscall，也不等待全局准入互斥锁。竞争可返回 EBUSY；超出任务数或逻辑字节预算可返回 ENOSPC；停止返回 ESHUTDOWN。**Queue/ENOSPC 是队列预算不足，其他阶段的 ENOSPC 才可能是磁盘满，必须结合 stage 判断。**

准入预算覆盖排队、在途、退避重试以及 FileSink 保留尾批的逻辑 payload。任务已执行但数据还留在尾批时，通过内存 token 保留字节计费，防止“队列为空、尾批无限增长”。空的批量条目不进入尾批，避免绕过字节预算。

预算不是 RSS 硬上限。以下成本仍在预算外或只是近似计量：

- 提交前业务已创建的 string/proto 快照，以及短时旧新快照共存。
- 路径、ticket、队列节点、闭包、vector/string capacity 和 allocator 元数据。
- 序列化输出、批量拼接、zstd 压缩临时区、线程栈。
- 内核 dirty pages、文件系统缓存，以及调用者自己长期保存的 tickets。

自定义 Work 必须正确上报所持快照大小；传 0 并捕获大对象会规避逻辑字节限额。调用者也要控制帧内快照大小和创建频率。库没有提供“任意大 proto 零成本异步化”。

## 6. 最新状态邮箱：写、删除统一为期望状态

普通 Executor 提交拒绝意味着任务没有进入系统，业务若随即遗忘，就会永久丢失这个意图。恢复缓存更适合使用 AsyncFileCache：初始化固定 key/path，生产者原子发布最新不可变 snapshot，dispatcher 重试向专属 executor 准入。

~~~mermaid
sequenceDiagram
    participant P as 业务帧
    participant M as key 的 desired
    participant D as dispatcher
    participant W as 单 worker
    P->>M: publish 写 A，generation 1
    D->>W: 执行 A
    Note over W: fsync 阻塞
    P->>M: remove，generation 2
    P->>M: publish 写 B，generation 3
    D->>W: latest 意图 B
    Note over D,W: 未执行的旧意图可合并
    W-->>D: A 返回，不能撤销已在途操作
    W->>W: 执行 B
    W-->>D: saved generation 更新到 3
~~~

删除是一个正式 generation，不是独立线程里随手 remove；否则旧的排队写可能在删除后再次生成文件。已经在途的旧 syscall 无法中断，期间可能短暂看到旧内容；最新意图成功后才收敛到目标状态。

dispatcher 大约每 20ms 检查一次；准入失败留待后续周期重试。执行失败开启 1、2、4、8、16、30 秒封顶的退避。当前实现没有按错误码区分暂态/永久错误，序列化错误也会重试到被更新或停止，必须观察 Health。

Cache 默认总快照预算 4MiB，包含 desired 与在途旧 snapshot；成功后仍保留 desired。新版在分配/替换时可能与旧版共存，即使新版单独小于上限也可能被拒绝。`remove` 的 payload 为 0，但仍需要分配对象，不等于不会失败或已经持久化的 tombstone。

固定 key 表与独立 dispatcher 避免 publisher 去拿 worker/executor 锁。不过 shared_ptr 原子操作可能有内部同步，CAS 在竞争下可能重试，因此不宣称 lock-free、wait-free 或硬实时 WCET。

## 7. 文件完整性、可见性与掉电持久性

原子替换流程在 worker 中完成：

~~~text
创建父目录 → 同目录 mkstemp → 完整写临时文件
  → [可选 fsync 文件] → 检查 close → rename 发布
  → [可选 fsync 父目录]
~~~

同目录临时文件避免跨文件系统 rename；短写及 EINTR 由 writeAll 处理。rename 前失败保留旧目标并尝试清理临时文件；清理自身失败仍可能留下临时文件。异常时 fd 的 RAII 清理也发生在 worker。

| FileDurability | 成功所代表的动作 | 未提供的额外保证 |
| --- | --- | --- |
| AtomicVisibility | 临时文件写完、close、rename 成功 | 不主动 fsync，掉电后内容/目录项仍有风险 |
| FileSync，默认 | 临时文件 fsync 后 close、rename | 没有同步父目录，不能视为完整的掉电发布协议 |
| FileAndDirectorySync | 再同步父目录 | 文件系统/设备实际语义仍需目标平台验证 |

若 rename 已成功但父目录 fsync 失败，ticket 为 Failed，同时 `FileResult.published=true`。新内容已经可见，不能报告“写失败，旧文件仍在”或据此做错误回滚。FileAndDirectorySync 只同步目标的直接父目录，不递归同步 ensureParent 新建目录的全部祖先；完整掉电发布协议还需结合目录预创建与平台语义验证。

替换使用 mkstemp 创建新 inode，模式为 0600，不复制旧 inode 的 mode/owner/ACL 等属性。有权限或共享读取要求的业务需要额外设计。FileSink 的日志 open 是另一条路径，使用 0644（仍受 umask 影响）。

追加写失败可能已写入部分字节，无法自动回滚；重试可能重复记录。remove/rename 本身没有额外目录 fsync。FileSink 的 flush 是写出尾批，不能替代持久化级别接口。

## 8. FileSink 内部的所有权与批量

FileSink 每实例分配一个 stream；worker 独占 fd、当前路径、文件大小、压缩和 batch。producer 的短暂准入锁不覆盖文件系统调用，所以慢 write/fsync/rename 不会通过 fd mutex 把帧线程拖住。

`appendAsync` ticket 为 Succeeded 可能只意味着数据进入 worker 的尾批。None 模式直接写；Auto 在条数或时间达到条件时写；Manual 需业务调用 flushAsync。独立 timer 每约 20ms 最多为每 sink 保持一个待执行控制任务，避免慢盘时 timer 请求无限累积。200ms 的自动刷新间隔是调度条件，worker 被阻塞时不提供 200ms 完成保证。

压缩在 worker 进行，每个 header/数据块是独立 zstd frame，文件可包含多个 frame。轮转、最终 rename、目录扫描和旧文件删除也在 worker。FileSink 保留一层批处理，FileWriter 不再二次延迟交接。

`fastShutdown=true` 默认允许关闭时丢弃未写尾批。需要尾批完整的用户应设置 false，并由管理线程检查 flush/close tickets；即使如此，文件系统错误仍可能造成丢失。不要把 accepted 的追加记录理解为无损审计日志承诺。

## 9. 结束与资源生命周期

关闭顺序建议：停止业务生产者 → 提交最后快照/flush/close → 管理线程在总期限内检查结果 → 停 executor。业务须确保销毁不与对象成员方法并发。

- `ticket.wait(timeout)`、`drain(timeout)` 只限制调用者等待，不中断 syscall；ticket.wait 的 0 是无限等待。
- executor `stop(false)` 停止新准入和后续重试，保留可推进的已排队任务；`stop(true)` 另取消排队任务。在途任务继续到返回。
- owner executor 析构取消待执行任务，不 join 在途 worker。worker 持有共享状态，避免对象销毁后的悬空访问；永久卡住时资源保留到进程退出。
- `share()` 是不负责停止 owner 的共享句柄；销毁句柄不会停止 owner，owner 停止后句柄也不能继续准入。
- 显式 openAsync 路径的 FileSink 析构只请求后台关闭；默认 fastShutdown 可能丢尾批。外部池已停且任务清空后，由后台池尝试收尾。
- Cache 析构请求 dispatcher 停止，不等待最新 desired 持久化。需要保存时先 drain；不要依赖析构隐式保存。

旧 FileSink 的 open/write 仍等待；旧 close 对 ticket 的等待在 fastShutdown 下为 200ms，否则为 closeTimeout。其 EBUSY 准入重试在计时等待前，**这个数值不是旧 close 从入口到返回的严格最坏耗时上限**。

## 10. 当前实现的边界

已实现：有界逻辑准入、后台文件原语、stream 顺序、ticket、原子替换、Cache 合并/重试、FileSink 后台生命周期与清理、故障注入。

没有实现：强制 syscall 超时/取消、完整多文件事务、跨进程排序、持久化 tombstone、掉电后的代际恢复协议、按存储卷的全局 QoS、任意任务的优先级调度、硬实时 WCET 保证。

这些边界决定业务仍需定义：记录是否可丢、旧缓存是否可接受、启动时如何校验、保存落后多久告警、何时降频、退出时愿意等待多久。planning 当前沿用旧恢复校验，删除失败或掉电后旧缓存仍可能复活，不能把异步迁移描述为已消除此风险。
