# 接入指南

先按业务需求选择 service 单次操作、普通文件或连续输出。三个入口可以共享同一个 service；高吞吐输出与关键状态写入需要隔离排队时，分别创建实例。完整接口见[API参考](./API参考.md)。

## 选择 Bazel 依赖

仓库使用 Bazel wrapper 规则，业务 target 可按需加入：

```python
load("@deeproute_build_tools//rules/modules:common_cc_wrapper.bzl", "common_cc_binary")

common_cc_binary(
    name = "capture_demo",
    srcs = ["capture_demo.cc"],
    deps = [
        "//base/async_file:async_file_output",
        # 需要 Proto 时添加：
        # "//base/async_file:async_proto_file",
        # 以及业务实际使用的 proto target。
    ],
)
```

只使用普通文件时依赖 `:async_file` 即可，不需要 zstd 或 protobuf。`:async_file_output` 依赖核心与 zstd，`:async_proto_file` 依赖核心与 protobuf。按所用类型包含公共头，不包含 `internal`。

## 完整示例：单次写入与连续采集

下面程序用原子计数观察后台错误，回调不执行同步日志 IO。这里用提前返回处理接收失败，实际业务可替换为明确的丢弃、降级或稍后重试策略。

```cpp
#include <atomic>
#include <memory>
#include <string>

#include "base/async_file/async_file_output.h"
#include "base/async_file/async_file_service.h"

namespace af = deeproute::base::async_file;

int main() {
  af::ServiceOptions service_options;
  service_options.max_pending_tasks = 1000;
  service_options.max_registered_resources = 128; // 含未打开、失败和关闭中的资源。
  service_options.max_pending_bytes = 10 * 1024 * 1024;
  af::AsyncFileService service(service_options);

  auto errors = std::make_shared<std::atomic<size_t>>(0);
  auto on_done = [errors](const af::FileResult& result) {
    if (!result) errors->fetch_add(1, std::memory_order_relaxed);
  };

  af::WriteOptions snapshot_options;
  snapshot_options.sync_file = true;
  if (!service.AsyncWriteFile("/tmp/app/state.txt", "state v1\n",
                              snapshot_options, on_done)) return 1;

  af::OutputOptions output_options;
  output_options.directory = "/tmp/app/capture";
  output_options.prefix = "frames";
  output_options.format = af::OutputOptions::Format::kZstd;
  output_options.batch_mode = af::OutputOptions::BatchMode::kAuto;
  output_options.batch_records = 100;
  output_options.file_header = "capture schema=v1";
  output_options.max_file_bytes = 50 * 1024 * 1024;
  output_options.max_file_count = 20;
  output_options.max_total_bytes = 500 * 1024 * 1024;

  auto output = service.MakeOutput(output_options);
  if (!output || !output->AsyncOpen(on_done)) return 1;
  // Open 已接收即可继续提交；保留业务原有行尾，库不会重复补换行。
  if (!output->AsyncWrite("frame 1\n", on_done)) return 1;
  if (!output->AsyncWrite("frame 2\n", on_done)) return 1;
  if (!output->AsyncClose(on_done)) return 1; // 默认 Drain，刷出尾批。

  // 真实应用先停止所有生产者，再在管理线程执行。
  if (!service.Shutdown()) return 1;
  return errors->load(std::memory_order_relaxed) == 0 &&
                 service.GetStats().failed == 0
             ? 0 : 1;
}
```

生产代码应同时看拒绝计数和后台错误。仅检查 `AsyncOpen` 的 bool 不能证明打开成功；权限或磁盘问题可能在之后的回调中出现。发生打开错误时，已接收的 Write 会得到状态错误，业务需要据此禁用采集或重建对象。

## 普通文件：指定路径持续写入

适用于已有自定义二进制格式、不需要轮转的文件。头文件为 `async_file.h`。

```cpp
#include "base/async_file/async_file.h"
#include "base/async_file/async_file_service.h"

namespace af = deeproute::base::async_file;

bool SubmitRawFile(af::AsyncFileService& service, af::Completion on_done) {
  auto file = service.MakeFile();
  if (!file) return false;
  af::OpenOptions options;
  options.mode = af::OpenOptions::Mode::kCreateNew;
  if (!file->AsyncOpen("/tmp/app/raw.bin", options, on_done)) return false;
  if (!file->AsyncWrite(std::string("\0\1\2", 3), on_done)) return false;
  if (!file->AsyncSync(on_done)) return false;
  return file->AsyncClose(on_done);
}
```

本地 `file` 门面离开作用域后，已接收任务仍持有资源。业务长期写入时应把门面保存为模块成员；析构只请求关闭，不表示后台已经完成。

此例依次提交 Sync 与 Close，它们进入同一队列，Close 会等 Sync 执行后处理。若在 Sync 的回调中再提交 Flush/Sync，前一个控制槽此时尚未释放，可能返回 false；需要把下一次控制请求调度到回调返回之后。

## 单次文件操作组合

同一 service 可以依次提交写入、改名和删除，保证执行顺序；但它们是**独立请求**，前一个失败不会自动跳过后一个，也没有跨操作事务。

```cpp
// 已持有 service 和 on_done。
bool accepted = service.AsyncWriteFile("/tmp/app/new.txt", "content", {}, on_done);
if (accepted) {
  accepted = service.AsyncRename("/tmp/app/new.txt", "/tmp/app/current.txt", on_done);
}
```

如果 rename 必须以写入成功为条件，应在写入完成成功后再提交，或由业务状态机驱动。回调中可以提交新任务，但容量仍包含当前任务，service 也可能已进入关闭，因此仍要处理返回 false。单纯保存一个完整文件通常直接 `AsyncWriteFile` 就够了。

不应对一个仍打开的输出文件直接执行 remove/rename 来替代输出对象的轮转。输出对象维护路径、fd 与完成命名，应让它自己管理这些步骤。

## Proto 快照：两种所有权选择

引用重载最容易使用，复制完成后原消息可以继续修改。这里以 protobuf 自带的消息演示，实际接入替换为业务 proto。

```cpp
#include <google/protobuf/descriptor.pb.h>
#include "base/async_file/async_proto_file.h"

google::protobuf::FileDescriptorProto descriptor;
descriptor.set_name("capture.proto");
bool accepted = service.AsyncWriteProtoText(
    "/tmp/app/schema.pbtxt", descriptor, {}, on_done);
// 返回后可修改 descriptor；提交期间不应有并发修改。
```

较大的消息若已经由业务生成不可变快照，可使用共享重载避免再次深拷贝：

```cpp
#include <memory>
#include <google/protobuf/message.h>

auto message = std::make_shared<google::protobuf::FileDescriptorProto>();
message->set_name("capture.proto");
std::shared_ptr<const google::protobuf::Message> snapshot = std::move(message);
bool accepted = service.AsyncWriteProtoBinary(
    "/tmp/app/schema.pb", std::move(snapshot), {}, on_done);
```

移交后不要通过其他别名修改消息。Text/Binary 的序列化与文件写入都在 worker 上执行，容量按消息内存占用申报，不能只按二进制文件预计大小配置额度。

## 回调、拒绝与重试

| 情况 | 业务建议 |
| --- | --- |
| 返回 false | 记录拒绝；根据数据重要性丢弃、降采样或以后重试；不要等待一个不会发生的回调 |
| `kWrite` 且写入量非零 | 追加可能部分成功，不要盲目重放；用业务记录 ID、文件格式或新快照处理 |
| `kScan/kRemove` 清理失败 | 查看对象状态及磁盘占用，排查目录权限；已成功记录通常不应重写 |
| `kCancelled` | Fast 关闭的预期损失，按业务策略统计 |
| 无回调但需要知道健康度 | 定期读 service/file 的 `GetStats()`，比较计数增量 |

回调应短小，例如更新原子计数、复制结果到业务事件队列。不要捕获短生命周期对象的裸指针或引用；库析构超时后回调仍可能发生。可用 `shared_ptr` 保持结果接收状态，或用 `weak_ptr` 在接收方已销毁时安全忽略。

## 正常停机与有限等待

正常停机顺序是：停止生产者 → 按需要提交 Sync → 关闭服务入口并 Drain → 确认 worker 退出 → 释放回调依赖资源。

```cpp
service.AsyncShutdown(af::ShutdownMode::kDrain);
bool exited = service.Wait(std::chrono::seconds(2));
if (!exited) {
  // 业务允许舍弃尚未开始的工作时，再升级 Fast。
  service.AsyncShutdown(af::ShutdownMode::kFast);
  exited = service.Wait(std::chrono::milliseconds(200));
}
// exited=false 时，保留回调所需外部资源；在途 IO 仍可能继续。
```

若必须无损排空且允许等待，管理线程可直接 `Shutdown(kDrain)`。不要在业务关键路径、worker 回调或每帧函数中使用同步 Shutdown。不要依赖 service 的默认析构完成所有记录：析构请求的是 Fast。

## 迁移采集业务时的检查点

保持原业务所需的批量模式、delimiter、文件头、zstd 级别、轮转大小、同步阈值与清理上限；这些配置统一放在 `OutputOptions`。创建输出对象后要显式 `AsyncOpen`，不再由业务创建 fd。回调改用 `FileResult` 并增加接收失败处理，停机改为显式 Drain。

相同目录与前缀只交给一个活跃输出对象。保留原业务记录字节；None 的多行块/二进制逐条原样输出，Auto/Manual 在同文件跨批也按 delimiter 分隔，不强制增加文件末尾换行。业务原先作为普通记录提交的表头仍应作为记录提交，不要改为轮转后重复的 file_header。确认消费端支持 zstd 多帧，且只把已完成命名的文件当作正常收尾产物。旧库和新库可以并存，但不应同时管理同一组输出文件。
