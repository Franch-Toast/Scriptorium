# 01 总体设计与用例组织

## 1. 职责与框架选择

PlatformBench 的主要资产是可追溯需求、方法明确的测试源码及相关数据。公共辅助只解决重复出现的问题，测试程序保留所属框架的原生入口和使用方式。

| 测试类型 | 推荐实现 | 用例作者负责 |
| --- | --- | --- |
| 底软需求检查 | GoogleTest 的 TEST/TEST_F/参数化测试 | 需求对应关系、检查方法、断言和诊断证据 |
| CPU/内存性能 | Google Benchmark 的注册、fixture 和参数组合 | 负载、计时、工作量计数、正确性和缓存假设 |
| 后续推理性能 | Google Benchmark 调用运行时，或接入已有性能工具 | 模型、输入、后端、完成边界及正确性 |
| 其他已有测试 | 可独立执行并产出报告的程序 | 依赖、退出约定、结果说明及必要的离线解析 |

GoogleTest 的测试总时长不作为操作性能指标。Google Benchmark 默认输出的迭代统计及重复运行结果不代表逐次原始延迟；确需逐次数据时，由具体用例设计附件和采集方法，不改变全仓库的结果要求。

无需将两套框架嵌入一个程序。断言、fixture、迭代、预热和参数化沿用原生机制，脚本不实现第二套测试循环。公共平台库与框架无关，可以被不同框架共享。

## 2. 当前源码目录与阅读顺序

实现仓库为 `/sandbox/PlatformBench`。以下为实际维护的源码目录；空领域和未来 SDK 目录不预建。

```text
PlatformBench/
  BUILD                         # 聚合目标、OS 选择条件、全仓源码快照集合
  WORKSPACE                     # 公司构建仓库及固定版本第三方依赖
  .bazelrc                      # 公司配置导入、11 组配置别名、C++17/opt 设置
  .bazelversion                 # Bazel 7.6.1
  .gitignore                    # 忽略构建、结果和缓存
  README.md                     # 快速开始、目录速览、配置及运行约定
  cases/
    requirements/
      os/
        os_requirements_test.cc
        BUILD
    benchmarks/
      cpu/
        integer_benchmark.cc
        BUILD
      memory/
        bandwidth_benchmark.cc
        BUILD
  platform/
    api/system_info.h
    os/linux/system_info.cc
    os/qnx/system_info.cc
    os/unsupported_platform.cc
    BUILD
  support/
    process.cc
    BUILD
  suites/
    default.sh
    BUILD
  scripts/
    bazel.py
    workspace_status.py
    package.py
    build_matrix.py
    build_matrix.sh
    run.sh
    host.py
    analyze.py
    BUILD
  packaging/
    bundle.bzl
    BUILD
  tests/
    test_workflow.py
    BUILD
  toolchains/
    defs.bzl
    qnx_sdk.bzl
    BUILD
```

每个源码层级的职责如下。各领域 `BUILD` 声明原生目标与依赖，父目录的源码集合用于打包时保留完整源码快照。

| 目录 | 放什么、由谁使用 | 扩展时修改位置 |
| --- | --- | --- |
| `cases/` | 目标机运行的测试用例；直接依赖原生框架和所需公共库 | 新检查或基准从这里开始，不向脚本增加测试逻辑 |
| `cases/requirements/` | 底软需求检查，按 OS、内存、调度等领域组织 | 一个真实需求对应一个源文件，按依赖决定可执行目标粒度 |
| `cases/requirements/os/` | 当前 OS 信息和空参数处理示例，共两个 GTest | `os_requirements_test.cc`；当前没有正式产品需求编号 |
| `cases/benchmarks/` | CPU、内存等资源性能方法 | 新方法附计时边界、工作量口径和正确性依据 |
| `cases/benchmarks/cpu/` | 单线程 uint64 整数混合运算基准 | `integer_benchmark.cc` |
| `cases/benchmarks/memory/` | 64 KiB/64 MiB 工作集的对齐缓冲区复制基准 | `bandwidth_benchmark.cc` |
| `platform/` | 与测试框架无关的公共 OS 库及构建选择 | 新增确有复用需要的 OS 能力 |
| `platform/api/` | 公共声明，当前为系统身份和在线 CPU 数查询 | `system_info.h`，不暴露厂商 SDK 类型 |
| `platform/os/` | 公共声明的平台实现及未知平台拒绝文件 | `linux/` 与 `qnx/` 定义同名符号，Bazel 只链接一份 |
| `platform/os/linux/` | Linux 的 `uname`、`sysconf` 读取及原始错误诊断 | Linux 专有实现留在这里 |
| `platform/os/qnx/` | QNX 的相同接口实现，目前也使用 POSIX 调用 | QNX 差异留在这里，不改变测试源码 |
| `support/` | 多处复用的辅助；当前只提供 `pb_process` | `process.cc` 负责进程、会话、信号、原始 wait 状态和清理，不负责测量 |
| `suites/` | 受信任的 Shell 执行清单 | `default.sh` 调整项目顺序、filter、超时和失败策略 |
| `scripts/` | 主机工具及目标机串行入口 | 构建/打包与部署/运行职责见下一表 |
| `packaging/` | Bazel 交付规则与集合定义 | `bundle.bzl` 收集产物，`BUILD` 定义默认包和内存选包 |
| `tests/` | 宿主机编排回归，使用夹具验证异常与证据处理 | `test_workflow.py`，不用于硬件性能验收 |
| `toolchains/` | 公司工具链注册与必要的 QNX SDK 视图适配 | `defs.bzl` 注册，`qnx_sdk.bzl` 处理布局和版本一致性；不存 SDK 二进制 |

`scripts/` 的职责拆分：

| 文件 | 作用 | 运行位置 |
| --- | --- | --- |
| `bazel.py` | 设置源码来源并调用 Bazel；中文路径时复制到 ASCII 工作区 | 开发主机 |
| `workspace_status.py` | 收集提交号、工作区状态、源码位置和公司配置版本 | Bazel 构建主机 |
| `package.py` | 发起包目标构建；按描述收集 ELF、runfiles、许可及源码并打包 | 开发主机/Bazel 构建动作 |
| `build_matrix.py` | 逐配置构建，记录日志、ELF 信息、`matrix.tsv/json` | 开发主机 |
| `build_matrix.sh` | 调用同一 Python 矩阵工具的便捷入口 | 开发主机 |
| `run.sh` | 清单一次登记、预检、串行执行、超时控制及结果保存 | 目标机，本机也可运行本机包 |
| `host.py` | SSH/SCP 部署，调用一次 `run.sh`，回收后分析 | 主机 |
| `analyze.py` | 解析原生 GTest XML/Benchmark JSON 和执行证据 | 主机 |

`out/` 是建议的包与构建矩阵输出位置，`results/` 是建议的运行/回收位置，
`bazel-*` 是 Bazel 创建的输出链接；这些不是源码目录，均忽略提交，可清理后重建。
运行结果中的 `items/`、`args/`、`artifacts/`、`tmp/`、`analysis/` 见第 04 篇。
交付包的 `licenses/` 由固定版本依赖自动生成，源码仓库不保存许可副本；
包内 `source/` 用于追溯本次构建，详见第 03 篇。

建议先读 `README.md` 与 `suites/default.sh`，再读三个示例源码及其 `BUILD`；
需要修改执行方式时读 `run.sh`/`analyze.py`，需要新增平台时读 `.bazelrc` 和 `toolchains/`。

先按测试目的、再按领域分层，不按 gtest/benchmark/onnx 划分顶层目录。需求检查与性能评估可以共享底层能力，但分别表达判定目标。厂商专有用例放在相关领域的专有子目录，不因新增 SDK 复制整个仓库。

一个底软需求对应一个源文件，可以包含多个 TEST 或参数化实例，不强制一条 TEST 对应一个文件。真实需求标识出现在文件说明和稳定测试名中；需求修订时同步更新判定说明。不由工程自行编造需求编号或准入值。

仅供单个用例使用的 fixture、数据和辅助代码就近放置，多处复用后再提取到 support。平台库自身的开发测试放在对应组件的 test 子目录，与面向目标板的检查用例分开。

## 3. 三种粒度独立选择

| 粒度 | 表达内容 | 调整依据 |
| --- | --- | --- |
| 源文件 | 一个需求或一组紧密相关的性能方法 | 可理解性与需求追溯 |
| Bazel 可执行目标 | 依赖、链接和进程边界 | 可以独立或合并同领域文件 |
| 清单项目 | 一次进程调用及其参数 | 原生 filter 选择一个或多个测试 |

不固定全仓库唯一的构建粒度。在 BUILD 附近说明选择依据：

- 依赖、权限和初始化相同，且都是稳定检查时，可以合并。
- 不同 SDK、易崩溃调用、特殊权限和状态变更用例，优先独立目标。
- 性能目标按测试方法及依赖边界组织，避免加载无关 SDK。
- 同进程崩溃可能中断后续测试并损坏整份原生报告；需要隔离时，用多个清单项目分别启动并传 filter。

例如两个 OS 需求文件可以合成 os_requirements_test，清单既能一次调用全部，也能使用两次不同的 --gtest_filter 分别启动。bandwidth_benchmark 可以包含多个规模和方法，通过 --benchmark_filter 选择。

同一进程内部顺序由原生框架决定。要求 A、B、A 顺序时拆成三个清单项目，不依赖注册顺序。以后调整目标粒度主要修改 BUILD、包清单和执行清单，用例通过公共接口保持可复用。

Bazel test_suite 只聚合测试规则，普通 benchmark 程序使用其他聚合构建目标，不强行包装成可缓存的硬件性能测试。

## 4. 底软需求检查方法

每个文件至少说明需求及版本、测试意图、适用平台、前置条件、步骤、预期及依据、失败证据、清理和可能的副作用。各 TEST 说明覆盖条件及断言意图。

“当前身份允许某操作”与“内核编译开启某能力”是不同需求。同样的权限拒绝，对前者可能明确不满足，对后者可能只是证据不足。保留 errno、参数和必要诊断，断言消息说明原因。

不强加一套替代 GTest 的领域状态机：需求不满足与检查故障都可能表现为原生失败，消息和附件必须说明区别；证据不足不能通过。GTEST_SKIP 仅用于明确不适用或非被检对象的前置条件不成立，不能将被检能力缺失预先跳过。跳过必检项在汇总中显示为未完全验证。

通过 fixture 或 RAII 恢复正常执行中修改的状态。TearDown 不保证在崩溃或强杀后执行；已知清理失败必须显式报告，可能影响后续项目时以异常退出通知脚本停止，具体约定见第 04 篇。

## 5. CPU 与内存基准方法

一期已实现以下原生目标，默认包按 OS、CPU、内存顺序各启动一次进程。

| 目标/源文件 | 当前方法与正确性 | 原生输出 |
| --- | --- | --- |
| `//cases/requirements/os:os_requirements_test` | 两个 GTest：系统身份非空、在线 CPU 数为正，以及拒绝空输出指针；只读无特权 | GTest XML |
| `//cases/benchmarks/cpu:integer_benchmark` | `IntegerMix`：每次 1024 次依赖的 uint64 xorshift/multiply，参考值 `0x73de1661de800754`，报告 mixes/s | Benchmark JSON |
| `//cases/benchmarks/memory:bandwidth_benchmark` | `SmallWorkingSetCopy/65536`、`LargeWorkingSetCopy/67108864`；64 字节对齐、预触页，复制后逐字节校验，逻辑流量每次 `2N` | Benchmark JSON |

CPU 基准使用框架 CPU 时间；内存基准使用 `UseRealTime()` 墙钟时间。
初始化、分配和正确性校验均在原生迭代计时区间之外。默认清单内存项重复 3 次，
保留重复值和框架 mean/median/stddev；校验失败使用 `SkipWithError` 记录。
当前 Google Benchmark 的 `--benchmark_min_time` 使用浮点秒，例如 `0.05`。

后续用例仍通过 Google Benchmark 注册和原生命令行选择参数。方法至少说明：

| 项目 | 内容 |
| --- | --- |
| 负载 | 算法、类型、规模、线程数和实现 |
| 计时 | CPU 时间或墙上时间、同步边界、是否包含分配及初始化 |
| 重复 | 预热、迭代校准、固定迭代及 repetitions 设置 |
| 环境 | CPU 绑定及实际生效集合，已知调度和功耗条件 |
| 正确性 | 参考结果、校验和或容差 |
| 指标 | 操作数或逻辑字节数、单位及吞吐约定 |

内存 Copy 的代表方法：预先分配对齐缓冲区并触页，在计时外初始化；循环中复制并防止编译器消除负载，在计时外验证内容。采用读 N 字节、写 N 字节口径时，每迭代逻辑流量为 2N，并明确它不是实测 DRAM 总线流量。

缓存驻留测试和大工作集流式测试使用不同名称及参数，不把任意规模复制都称为 DRAM 峰值带宽。多线程注明总工作量和每线程缓冲区关系。需要操作完成时间的负载使用 UseRealTime 或明确的手动计时，准备、日志及报告不进入被测区间。防优化辅助不能代替正确性校验。

正确性异常使用框架原生错误机制记录。已经产出的性能值保留供诊断，但失败项目不作为有效性能通过项。一期不设置默认性能准入阈值。

## 6. 新增用例步骤

1. 确认归属，增加源码、需求或方法说明。
2. 使用合适的原生框架，复用或补充必要平台能力。
3. 决定目标粒度，登记真实依赖、适用平台和包内路径。
4. 添加清单示例，注明 filter、参数、超时和附件。
5. 验证报告、失败证据和清理，在实际目标环境验证方法。
