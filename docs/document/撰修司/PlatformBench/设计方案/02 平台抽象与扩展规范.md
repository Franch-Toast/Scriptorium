# 02 平台抽象与扩展规范

## 1. 依赖方向

用例依赖原生框架及所需公共库，OS/SDK 实现依赖实际平台 API。公共平台库不依赖 GTest、Google Benchmark 或执行脚本，不返回测试通过或失败结论。

```text
用例 → 公共 OS 接口 → Linux 或 QNX 实现
用例 → 按需 SDK 能力接口 → 对应厂商实现
厂商专有用例 → 对应专有适配库
```

接口按能力拆分为可独立依赖的 Bazel 库，不增加涵盖所有能力的大基类。公共头文件不泄漏厂商 SDK 头文件和句柄；仅单处使用且无复用需求的辅助可以留在用例旁。

## 2. OS 公共接口

当前实际公共接口为 `platform/api/system_info.h` 的 `SystemInfo` 和
`bool GetSystemInfo(SystemInfo* info, std::string* error)`，目标为 `//platform:system_info`。
读取 OS 名称、架构和在线 CPU 数；两个输出指针均必须非空，失败时不改写结果，
错误文本保留失败操作和可取得的 errno。CPU 数初值 `-1` 表示尚未成功读取，不能当作有效数据。

`platform/os/linux/system_info.cc` 与 `platform/os/qnx/system_info.cc` 当前都使用
`uname` 和 `sysconf(_SC_NPROCESSORS_ONLN)`，分别维护以容纳后续差异。
`platform/BUILD` 依据 `@platforms//os:linux` / `qnx` 选择唯一实现，
其他 OS 编译 `unsupported_platform.cc` 并明确失败，不静默退回 Linux。

优先使用目标平台支持的标准库。下表是按需扩展的能力边界；除上述系统信息外，
线程绑定、调度、特殊内存和计时接口尚未实现，不预先包装全部 POSIX 调用。

| 能力 | 公共语义 | 平台责任 |
| --- | --- | --- |
| CPU 绑定 | 查询可用集合、绑定测试线程、返回实际生效集合 | API、权限及编号语义 |
| 调度 | 查询策略，显式请求时调整及恢复 | 策略、参数范围和权限 |
| 系统信息 | 本次检查所需 OS/CPU/内存信息 | 字段、单位、缺失原因 |
| 特殊内存 | 标准分配不能表达的实际测试需求 | 页、锁页或映射的真实语义 |
| 特殊计时 | 标准单调时钟不足时补充 | 时钟域、精度与有效性 |

例如线程亲和性可提供查询、设置及恢复相关声明，Linux/QNX 实现相同符号，由 Bazel 链接一份。平台固定实现无需运行时 OS 分支或工厂；确实需要多实现或测试替身时，再局部采用小接口与注入。

公共返回值表达操作结果、不支持和原始诊断。未知数据用缺失值加原因，不能用零伪装。绑定不意味着独占 CPU，总物理内存不意味着可分配容量。错误是否构成需求失败由用例判断。

不包装所有 POSIX 调用。需求本身验证专有 API 时，允许平台专有测试直接调用，在 BUILD 中限制适用性；共享检查方法和诊断辅助按需提取。

## 3. SDK 按需抽象

一期不预定义覆盖 CUDA、OpenCL、NPU 和推理运行时的完整接口。后续同一方法出现多个实现时，先确认输入、完成语义、正确性及计量是否可比较，再提取最小接口。

| 情形 | 组织方式 |
| --- | --- |
| 多个 SDK 有可比的显式传输能力 | 共享方法，适配库封装分配、复制及同步 |
| 显式复制与共享内存映射 | 分别定义方法和口径，不把映射耗时当作复制带宽 |
| 同平台同时有多个后端 | 显式选择后端和设备，失败时不自动切换 |
| 只有厂商专有功能 | 专有库和用例，注明限制 |
| NPU 只有模型执行能力 | 接入推理，不伪造通用 kernel 接口 |

资源由创建它的实现销毁，不跨不兼容后端传递。异步操作区分提交与完成。设备事件不可用时明确缺少设备计时，不能用主机耗时代替并沿用相同指标名。

SDK 由所选用例或 fixture 初始化，脚本不初始化所有设备。公共库只查询实际所需能力，不增加全局能力注册中心。

### 后续推理接入

可以用 Google Benchmark 调用 ONNX Runtime：准备模型和输入、创建会话、预热、执行并验证；也可独立调用已有性能工具。两种方式均保留原生报告。

接入时登记模型及输入来源和校验标识、shape、精度、运行时版本、Execution Provider、线程与 fallback 设置。计时确认实际完成，区分加载、首次执行和稳态推理。是否共享推理接口依据真实后端共性决定，不假定所有厂商都支持 ONNX。

## 4. 缺能力与检查故障

| 情况 | 行为 |
| --- | --- |
| 被检能力不满足明确需求 | 断言失败，保存实际值和依据 |
| 需求明确不适用当前平台 | 原生跳过，附适用性依据 |
| 非被检对象的前置条件未满足 | 按需求说明跳过或失败，不得通过 |
| 权限或探测错误导致无法判断 | 检查失败，记录证据不足，不推断能力不存在 |
| 承诺交付的程序或运行库缺失 | 交付或执行错误，不当作正常跳过 |

例如需求要求当前身份可以锁定内存，权限属于被检条件，权限不足不得自动跳过。若只检查内核配置，权限错误不足以证明配置关闭。

通过方法说明、原生消息和附件表达这些区别，不重新实现 GTest 状态机。汇总展示失败与跳过，不合成为通过。

## 5. 扩展流程

### 新增平台或 OS 版本

1. 确认真实公司工具链、平台和依赖标签。
2. 实现实际需要的 OS 能力，或复用已验证实现。
3. 声明适用目标和默认集合，隔离无关 SDK。
4. 核验架构、ABI、运行库、Shell 与 SSH 工具，执行开发测试。
5. 实机验证需求方法、计时和报告，登记 OS/BSP、工具链及证据。

### 新增 SDK

1. 明确方法及依赖，不先扩大公共接口。
2. 隔离 SDK 目标，说明资源、同步和错误诊断。
3. 根据共性选择共享或专有方法，记录可比条件。
4. 补充包依赖、清单和实机正确性验证。

### 新增框架或已有工具

1. 增加可独立执行的 Bazel 目标，保留原生参数和报告。
2. 清单声明调用、超时和附件，必要时提供短小调用辅助。
3. 说明退出码、零退出但报告错误的可能性及报告完成条件。
4. 需要自动解读时提供主机专用解析器，尚未解析的结论标为未知。

不要求继承统一测试接口。框架辅助只处理参数和输出路径，不接管内部执行。

## 6. 验证记录

当前已接入 Linux x86_64/AArch64，以及 QNX SDP 7.1、8.0 和公司 SDP 8 v2 的
x86_64/AArch64，具体公司配置见第 03 篇。OS 示例、CPU 和内存基准均已完成对应构建。
只有本机 Linux 包已有执行和正确性证据；QNX/Linux AArch64 仍待板端验收。
每个实际部署组合仍需登记板卡、OS/BSP、架构、工具链、SDK 和适用目标。
mock、宿主机编译和交叉构建均不替代板端装载、运行及测量正确性证据。

`support/process.cc` 的 `pb_process` 是目标机 runner 使用的独立 POSIX 进程辅助，
不属于 `platform/api` 的测试能力接口。它通过 `fork/setsid/execv/waitpid` 保留真实退出码与信号，
控制进程组终止并保存原始状态；不依赖测试框架，不接管断言或基准循环。
QNX SDK 下载和布局适配放在 `toolchains/`，不混入公共 OS API。

验收检查依赖隔离、公共头文件、不适用与失败证据，以及原生框架命令能否独立运行。

构建见[第 03 篇](./03%20Bazel%20构建与测试包交付.md)，执行和报告见[第 04 篇](./04%20脚本运行与结果收集.md)。
