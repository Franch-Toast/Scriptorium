# 04 脚本运行与结果收集

## 1. 双入口共用执行路径

主机负责部署、调用和回收，目标机负责清单预检、串行启动、超时及结果记录。主机不再次逐项调度，不维护第二份失败策略。

| 入口 | 职责 | 依赖 |
| --- | --- | --- |
| `scripts/host.py` | SSH/SCP 部署、调用一次 run.sh、回收并调用分析 | 主机 Python 3.8+ 和 SSH/SCP |
| `scripts/run.sh` | 预检、逐项运行、记录 | 目标机 POSIX Shell、基本工具和包内 pb_process |
| `scripts/analyze.py` | 解读摘要和原生报告 | 主机 Python 3.8+ |

目标机可直接运行同一份 run.sh。两种入口的顺序、参数、策略和原始目录约定一致。主机分析文件放在 analysis，不修改回收的原件。

以下接口已经实现。先用第 03 篇命令生成 `./out/platformbench-host-phase1` 或交叉包；
`board-a`、远端目录必须替换成真实连接和路径。主机 `--suite` 是本地清单路径，省略时使用包内默认清单：

```bash
# 主机：远程部署、执行、回收；远端包目录和输出目录均不得已存在
python3 scripts/host.py run --target board-a --package ./out/platformbench-orin-phase1 \
  --remote-package /data/platformbench/build-example \
  --remote-output /data/platformbench-results/run-example \
  --suite ./out/platformbench-orin-phase1/suites/default.sh --collect ./results/run-example

# 目标机：独立批量运行
sh scripts/run.sh --suite suites/default.sh \
  --output /data/platformbench-results/run-local

# 主机：人工回收的结果也使用相同分析入口
python3 scripts/analyze.py --input ./results/run-example
```

SSH 调用正确引用路径和参数，不拼接未经转义的命令；使用已有 SSH 认证。结果不保存密钥或无关环境变量。目标机独立运行后可人工 SCP 回收。

## 2. 受信任的 Shell 清单

清单由仓库维护或操作者确认，属于可执行代码，不接受不可信上传内容。清单声明有序项目，不自行编写调度或结果覆盖逻辑。

`run.sh` 提供的清单声明函数为：

```text
pb_gtest     ID TIMEOUT_SECONDS POLICY PROGRAM [ARG...]
pb_benchmark ID TIMEOUT_SECONDS POLICY PROGRAM [ARG...]
pb_command   ID TIMEOUT_SECONDS POLICY PROGRAM [ARG...]
```

当前 `suites/default.sh` 内容如下，内存项保留三次重复及原生统计：

```sh
pb_gtest os-checks 60 default bin/os_requirements_test \
  '--gtest_filter=OsRequirements.*'
pb_benchmark cpu-integer 180 default bin/integer_benchmark \
  '--benchmark_filter=IntegerMix' '--benchmark_min_time=0.05'
pb_benchmark memory-copy 180 default bin/bandwidth_benchmark \
  '--benchmark_filter=.*WorkingSetCopy/.*' \
  '--benchmark_repetitions=3' '--benchmark_min_time=0.05'
```

ID 唯一，以字母、数字、点、下划线、连字符组成安全目录名；禁止空值、单独的点和双点。TIMEOUT_SECONDS 为不含前导零的正整数秒，最大 `2147483647`。POLICY 为 default、stop 或 continue：default 使用第 3 节规则；stop 在该项普通失败后也停止；continue 允许该项超时或崩溃后继续，前提是已确认不会污染后续项目。写入失败、人工中断和无法确认终止的项目不可继续。

PROGRAM 为包内相对路径，拒绝绝对路径及逃出包目录的路径。ARG 逐项传递，保留空格及空参数，不 eval 或重新拆分字符串。报告路径由辅助函数统一传入，清单不得传冲突的输出参数。框架内部的 repeat/fail-fast 与脚本项目策略分别生效。

run.sh 先加载清单为有序调用列表，再预检全部 ID、程序、参数、超时及输出目录。加载阶段公共函数只登记项目，不启动程序。预检与执行使用同一份参数，不第二次加载清单；加载失败或空清单拒绝执行。

为避免目标机增加解析器，参数按序号逐项保存在独立文件中，并在 Shell 中按原边界恢复，不按空格或 TSV 拆分。空参数文件代表空字符串。输入中的换行和制表符在预检时拒绝，使行式记录保持简单；文件不额外添加换行。修改清单后使用新结果目录，保存本次清单副本与实际参数。

pb_gtest 指定每项目独立 XML，pb_benchmark 指定独立 JSON；只处理参数和路径，不接管框架循环。pb_command 通过 PB_ARTIFACT_DIR 提供附件目录，工具使用自有报告，未解析前测试结论未知。

工作目录固定为包根目录，数据使用包内路径。每项目拥有独立 tmp 和 artifacts，正常清理由用例 fixture/RAII 负责。清单不能依赖测试程序反向修改 Shell 状态。

## 3. 串行、失败与超时

同一时刻只启动一个清单项目，项目内部允许测试所需工作线程。每项开始前记录 started，结束后立即保存执行状态。

| 事件 | 默认动作 | 执行记录 |
| --- | --- | --- |
| 退出码 0 | 继续 | completed，测试结论待解析 |
| 普通非零退出 | 继续 | nonzero_exit，保留退出码 |
| 超时 | 终止当前项并停止 | timeout 及终止结果 |
| 崩溃或信号终止 | 停止 | signal 和原始信号编号 |
| 无法启动、依赖缺失 | 停止 | execution_error |
| 已知清理失败或状态污染 | 停止 | execution_error 及原因 |
| 结果无法保存 | 停止 | 尽力 stderr 告警，不声称保存成功 |
| SIGINT/SIGTERM | 终止当前项并停止 | interrupted |

脚本不解析所有错误文本。随包程序约定退出码 125 表示不能安全继续的执行或清理故障，普通测试失败使用框架正常非零约定；新工具占用该码时用薄包装映射并保留原始退出信息。无法启动、超时和信号由执行辅助独立记录。清理失败仅写一条普通断言不足以通知脚本停止，适配入口必须传递上述异常信号。

原生报告可能只在进程结束时完整写出。GTest/Benchmark 项目结束后检查预期报告是否存在且非空，缺失记录 report_missing，默认继续收集其他项；格式与内容由主机分析。pb_command 不强制固定报告文件，解析器按其工具约定检查附件。脚本不模拟生成原生结果。

Benchmark 可能零退出但在 JSON 中标记错误。目标机只记录 completed，主机解析后判为失败，批次不能通过。stop 策略不保证识别尚未解析的报告内部错误；需要即时停止时，工具接入层应提供可靠非零退出约定。

超时在目标机控制，不依赖 SSH 客户端等待时限。当前实现由 Shell watchdog 在到时后向
`pb_process` 发送 USR1；辅助进程通过 `fork/setsid/execv/waitpid` 管理独立会话和进程组，
先 TERM，等待 5 秒后 KILL，再等待最多 2 秒核实清理。真实退出码和原始信号分别记录，
不从 `128+N` 推测崩溃，因此可区分普通高退出码与真实信号终止。
`process.tsv` 保存辅助进程的原始状态，`execution.tsv` 保存 runner 对本项的执行记录。

每批启动前运行 `pb_process --self-check`，验证会话、信号和 wait 能力；缺少能力就拒绝执行。
当前没有替代进程辅助的降级路径。禁止用例自行脱离会话或启动不可控守护进程；
残留子孙进程、执行/清理故障、不能确认终止时停止整批，不重试测试。

Linux/QNX 实际命令和信号识别能力分别验证，不假定 GNU timeout 或相同的 Shell 信号退出编码。continue 仅改变可确认终止后、已确认不会污染环境的单项超时或崩溃策略，不能绕过结果保存故障、清理失败及未知设备状态。

不自动重试、重启设备或恢复客户业务。正常停止为后续项目记录 not_run 及原因；强杀、掉电或磁盘故障可能无法收尾，主机通过已保存计划识别未完成项，不补写伪造的板端完成记录。

## 4. 最小结果约定

```text
run-example/
  build-info.json                 # 测试包构建信息副本
  manifest.tsv                    # 包内容副本
  suite.sh                        # 本次清单副本
  environment.tsv                 # 实际可取得的 OS/架构/身份及必要运行条件
  filesystem.txt                  # 结果文件系统 df -Pk 预检记录
  plan.tsv                        # 有序项目、程序、框架、超时、策略
  summary.tsv                     # 逐项更新的执行摘要
  run-status.tsv                  # 正常收尾的终态；缺失可能意味着不完整
  items/
    memory-copy/
      args/                       # 按序独立保存参数，保留空字符串
      execution.tsv               # runner 保存的时间、退出码/信号和执行状态
      process.tsv                 # pb_process 保存的原始 wait、exec_errno 和清理状态
      stdout.log
      stderr.log
      report.json                 # GTest 项目对应 report.xml
      artifacts/
      tmp/
  analysis/                       # 主机生成，不改原件
```

统一的是执行摘要字段和目录，原生报告保持原格式；目标机不要求 Python 或统一指标 JSON。最小字段为项目 ID、序号、程序、参数路径、起止时间、执行状态、原始退出码或信号、报告状态与路径、停止原因。

TSV 采用 UTF-8 和表头，缺失字段为空并附原因，不以零替代未知；诊断中的换行和制表符转义，原始诊断留在日志。不能可靠区分信号时保存原始 wait 状态并说明不确定，不猜测。记录格式随脚本版本一同交付。

当前 `environment.tsv` 白名单记录 `uname` 的 OS/release/machine/host、UID、在线 CPU 数、
`LD_LIBRARY_PATH`、时钟和信号记录方式；`id/getconf` 不可用时记 unavailable。
不自动读取 BSP、频率、温度或 CPU 绑定信息；需要性能比较时，由操作者明确固定并补充记录。
不做系统周期采集，不导出整个环境或凭证。

各结果子目录的用途：

| 目录 | 内容与写入者 |
| --- | --- |
| `items/<ID>/` | 一个清单进程的证据，runner 创建；与源文件或原生 TEST 数量无固定对应关系 |
| `args/` | 编号文件逐个保存清单实参，零字节文件表示空参数；框架报告参数由 runner 统一追加 |
| `artifacts/` | 用例自有附件，目标机程序通过 `PB_ARTIFACT_DIR` 定位 |
| `tmp/` | 本项独立临时空间，通过 `TMPDIR` 提供，不借用业务目录 |
| `analysis/` | 主机分析生成的 `summary.json` / `summary.md`，保留原件不改写 |

目标机实际要求 `dirname mkdir cp mv cat date sleep uname sed rm df` 和可执行的包内程序；
`printf/read/kill/wait/pwd` 等使用 Shell 能力，不依赖 GNU timeout 或目标机 Python。
通过 `df -Pk` 检查结果文件系统；真实 QNX 命令和动态装载能力仍待对应板卡验收。

拒绝覆盖已有输出目录，开始前确认可写及基本资源，过程持续处理写入失败。执行辅助状态文件以同目录临时文件加 rename 更新，确认写出成功后才宣称已保存；不承诺断电持久性。原生报告是否完整仍需解析。

stdout/stderr 直接分别重定向，避免管道掩盖退出码。脚本总时长只用于执行诊断，性能指标来自用例内部测量。后项失败不删除前项结果，复测使用新目录。

## 5. 离线解析与退出约定

| 报告 | 解读原则 |
| --- | --- |
| GTest XML | 保存测试名、失败/跳过详情和原生属性；零匹配标 empty，不算通过 |
| Benchmark JSON | 保留方法、参数、迭代、重复统计、counters 和单位，检查错误标记 |
| 其他工具 | 无解析器时 unknown，提供日志和附件，不凭零退出判通过 |
| 缺失或截断报告 | missing/invalid，原件不变，部分数据仅用于诊断 |

分析器输出人可读 summary.md 和机器可读 summary.json，仅归纳执行与测试结论并链接原生指标，不创建统一性能样本协议。存在错误的 benchmark 项目保留数字供诊断，不能作为有效通过项。

只有所有计划项均执行完成、报告有效且测试通过，批次才为通过。跳过、空匹配、未知、缺失和未运行均单列，属于未完全验证；明确失败和执行异常也分别展示。

| 程序 | 退出约定 |
| --- | --- |
| run.sh | 0：执行正常收尾、均零退出且预期报告存在；1：普通非零或报告缺失；2：预检/执行故障或异常停止。人工中断保留相应 Shell 约定。0 不代表测试通过 |
| analyze.py | 0：完整解析并全部通过；1：有明确失败；2：无明确失败但存在未完全验证；3：分析工具错误。失败和不完整并存时返回 1，并保留不完整标记 |
| host.py | 正常部署回收后使用分析返回码；部署、连接、回收故障返回 3，并保留远端、传输及分析各自状态 |

`host.py` 为每次操作保存传输日志，并在本地回收目录维护 `transport-status.json`，
分别记录部署、执行、回收和分析退出状态。远端包与结果目录必须是无空白的安全绝对路径，
二者互不嵌套且尚不存在；本地回收目录也必须新建。

远端非零后仍尝试回收，SSH 255/断连后也不重跑测试；SSH 中断不证明远端已停止，
未核实前不发起重叠运行。回收部分文件标记不完整。
远端记录异常但报告看似通过时，分析仍标记未完全验证，不能只看报告忽略执行状态。

## 6. 验收与演进

| 类别 | 场景与标准 |
| --- | --- |
| 双入口 | 相同包和清单产生相同项目、参数及目标机目录约定 |
| 参数 | filter、空格、空参数不失真，重复 ID、越界路径、非法超时及空清单预检拒绝 |
| 选包 | 缺程序、数据或运行库明确报错 |
| 普通失败 | 断言失败后执行下一项，日志和报告独立保存 |
| 原生结论 | 跳过、零匹配、零退出但报告错误均不算通过 |
| 异常 | 超时、信号、清理失败和无法启动按约定停止，验证 continue 的边界 |
| 中断与保存 | 强杀、SSH 断连和写出失败不删除已有结果，缺失终态可识别 |
| 实机 | Linux/QNX 分别验证工具、信号、等待及路径，mock 不代替测量 |
| 代表用例 | 底软检查与内存带宽贯通构建、执行、正确性、回收和解析 |

当前最小链路已贯通；宿主机回归使用 `tests/test_workflow.py` 的 17 项测试，覆盖参数边界、
一次登记、预检、失败/停止策略、TERM/KILL、中断、写出故障、原始信号与高退出码区分、
空/缺失/截断/跳过报告、零退出 Benchmark 错误、选包/runfiles、许可缺失、递归运行库和假 SSH 断连回收。

```sh
cd /sandbox/PlatformBench
python3 -m unittest discover -s tests -v
python3 scripts/bazel.py test --config=host --test_output=errors //:host_tests

# 使用已经生成的本机交付包，结果路径必须尚不存在。
sh ./out/platformbench-host-phase1/scripts/run.sh \
  --suite ./out/platformbench-host-phase1/suites/default.sh --output ./results/host-new
python3 ./out/platformbench-host-phase1/scripts/analyze.py --input ./results/host-new
```

本机默认包和内存选包都已从仓库外目录启动，通过受限 PATH 只提供 POSIX 基本命令，
执行阶段没有 Python/Bazel/编译器；分析阶段再在主机调用包内分析器。
默认包保留两个原生 GTest、一个 CPU Benchmark 及两种内存规模的重复/统计报告。
假 SSH 回归只验证部署和回收协议，真实板端 SSH、QNX/Linux AArch64 装载、信号与计量仍未验收。
一次性验证产物保存在调用者指定的输出位置，不进入源码和设计文档附件。

后续 CI 可复用主机入口，比较工具可读取原生报告。数据库、门户、并发调度和通用设备恢复不进入一期，
不为这些未来能力预建服务框架。
