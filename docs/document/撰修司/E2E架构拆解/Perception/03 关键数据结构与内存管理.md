## 1. 核心结构体总览

**一句话结论**：四层结构——每帧输入聚合体（不可变）、FrameContext（跨帧槽位）、pipeline 黑板（可变+锁）、proto（传输格式），各管一段生命周期。

**为什么数据结构值得单独一讲**：感知是全链路的「数据洪峰」——每 100ms 进来 12 路 MB 级消息，一帧数据要被十几个节点先后读。如果每次传递都拷贝，单帧内存与 CPU 开销会放大十几倍，100ms 节拍根本撑不住。本篇的四层结构、只读指针、零拷贝通道，都为一个目标服务：让数据只「流」不「搬」。

感知链路的数据结构分为四层：**组件层输入/输出聚合体（PerceptionProcessInput/Output）、帧上下文层（FrameContext）、pipeline 层共享数据（PerceptionSharedData/MsgBuffer）、proto 层**序列化消息（PerceptionObstacles 等）。

```cpp
class PerceptionFrameContextManager : public base::Singleton<...> {
 public:
  void ActivateFrameContext(uint64_t frame_id);   // 每帧激活/重置槽位
  void BuildNnFrame(uint64_t frame_id, const NnFrame& frame);
  std::shared_ptr<NnFrame> BuildSnapshot(uint64_t frame_id);
 private:
  mutable std::mutex mutex_;      // 保护全部槽位状态
  int frame_stride_ = 10;         // 发布步长：每10帧发布一次frame_context
  bool ShouldPublishFrameContextUnlocked(uint64_t frame_id) const {
    return frame_id % frame_stride_ == 0;   // 100ms帧基 × 10 = 1Hz发布
  }

// ActivateFrameContext 实现要点（.cc）：
//  - 找到空闲槽位（kFrameContextSlotCount），填入新 frame_id
//  - ClearSlotLocked() 将 slot 内 obstacle3d_nn_ 等 std::optional 重置
```

逻辑说明：FrameContext 是感知内部"上一帧遗留信息"的载体（如障碍 3D 框 NN 输出的跨帧缓存、pull_over 状态等）。管理器为**单例**，内部用固定数量槽位（slot）轮转保存多帧上下文；`ActivateFrameContext` 在每帧装配入口被调用，清空旧数据避免跨帧污染；`BuildSnapshot` 仅在 `frame_id % 10 == 0` 时才真正构建快照供发布（**推断**：降低发布频率以节省带宽）。

## 2. 生命周期

**一句话结论**：每帧一进一出——输入/输出聚合体每帧新建、shared_ptr 引用计数管理、没有对象池；重内存靠只读共享免拷贝。

### 2.1 每帧创建/复用模型

```mermaid
flowchart LR
    A[FrameSyncCalculator
12路帧同步] --> B[make_shared&lt;PerceptionProcessInput&gt;
每帧新建输入聚合体]
    B --> C[PerceptionInputTransformCalculator
填充字段 + ActivateFrameContext]
    C --> D[算法子图
只读消费]
    D --> E[make_shared&lt;PerceptionProcessOutput&gt;
每帧新建输出聚合体]
    E --> F[PerceptionOutputTransformCalculator
按topic拆包]
    F --> G[FrameDoneCalculator
按序发布]
    B -.->|slot轮转| H[FrameContextManager
跨帧槽位]
```

**图 2-1 · 一帧数据的生命周期**（A→G 自上而下，B/E 是两次新建点，虚线是跨帧侧写）

**读图提示**：① B 处每帧 `make_shared` 新建输入聚合体，不复用旧对象防脏数据；② 虚线 slot 轮转是 FrameContext 的跨帧侧写，不在主链上流动；③ G（FrameDone）按序发布——先数据后触发的顺序契约见 §5.2。

> 文件路径：/sandbox/perception/perception/calculators/perception_input_transform_calculator.cc  
> 函数名：PerceptionInputTransformCalculator::Process  
> 核心逻辑：

```cpp
absl::Status PerceptionInputTransformCalculator::Process(CalculatorContext* ctx) {
  // 每帧新建输入聚合体（不复用旧对象，避免脏数据）
  auto input = std::make_shared<PerceptionProcessInput>();
  uint64_t frame_id = ctx->InputTimestamp().Value();
  input->frame_id = frame_id;

  // 激活该帧的 FrameContext 槽位（清空上一帧遗留）
  auto& frame_context_manager = PerceptionFrameContextManager::Instance();
  frame_context_manager.ActivateFrameContext(frame_id);

  // 逐 topic 从 ChannelCache 查找消息并填入 input
  TransformInputMsgsToProcessInput(ctx, input.get());

  ctx->Outputs().Tag("OUT").Add(input);
  // DTU_REPS 请求先于主流程输出（规划请求要及时透传）
  // SetNextTimestampBound(InputTimestamp() + 1)：声明时间界，允许后续calculator
  // 在同一时间戳内完成再推进，避免下游过早关闭
}
```

逻辑说明：生命周期为"**每帧一进一出**"：输入聚合体在 Transform 节点每帧新建，输出聚合体在算法子图末端生成，二者都是 `shared_ptr`，沿图流动由框架引用计数管理，**没有对象池**（每帧全量新建，靠只读共享避免拷贝）。

### 2.2 FrameContext 传递路径

```mermaid
flowchart TD
    A[Process入口
ActivateFrameContext frame_id] --> B[算法子图各节点
写槽位: BuildNnFrame等]
    B --> C{frame_id % 10 == 0 ?}
    C -->|是| D[BuildSnapshot
CopyFrom NnFrame 生成快照]
    C -->|否| E[不发布]
    D --> F[PerceptionProcessOutput.frame_context]
    F --> G[FrameDoneCalculator
按序发布到 /perception/frame_context]
```

**图 2-2 · FrameContext 槽位与 1Hz 快照发布**（C 是分频闸门）

**读图提示**：① FrameContext 不在图上流动，走单例管理器+锁；② `frame_id % 10` 是 1Hz 发布闸门（100ms 帧基×10）；③ 快照 CopyFrom 是全链路少数深拷贝之一（§4.1）。

FrameContext 不在图上流动，而是经**单例管理器**传引用：写方（子图节点）与读方（输出 Transform）都通过 `PerceptionFrameContextManager::Instance()` 访问同一批槽位，由 `mutex_` 保证并发安全。**推断**：快照发布频率 1Hz（100ms 帧基 × stride 10），用于给下游/云端做场景级特征回传。

## 3. 内存与缓存机制

**一句话结论**：内存三板斧——shm pool 零拷贝（大消息）、MsgBuffer 时间查询（位姿）、三级 queue 管理（图级/Channel/组件）。

**为什么缓存是容错的后备**：正常路径下，各路数据按时间戳精确对齐；但传感器各有各的时钟与节拍，位姿与点云的到达时刻天然有微小错位。缓存（MsgBuffer、ChannelCache）的作用就是「多留几手」：当查询时刻没有恰好对齐的数据时，按时间邻域取最近的一条——没有缓存，任何毫秒级的错位都会变成整帧失败。

### 3.1 shm pool 共享内存读取（大消息零拷贝通道）

点云/图像这类 MB 级消息跨进程传递时，**proto 载荷里只编码"共享内存块索引"**，接收方按索引回到共享内存取真数据。

> 文件路径：/sandbox/perception/perception/calculators/perception_input_transform_calculator.cc  
> 函数名：PerceptionInputTransformCalculator::ReadImageMayFromShareMemory  
> 核心逻辑：

```cpp
absl::Status ReadImageMayFromShareMemory(const std::string& topic_name,
                                         sensor::Image* img_out) {
  const auto& pkg_data = img_out->data();       // data字段此时不是像素，是编码串
  // 不足64字节视为普通数据直接用；否则解析出块索引
  if (img_out->data().size() < 64) return absl::OkStatus();
  int index = std::stoi(pkg_data);
  // 用 topic + index + seq 从共享内存池取块（seq 比对防覆写）
  auto read_block = read_pool_.AcquireReadabledBlock(
      topic_name, index, img_out->shm_msg_seq());
  if (read_block == nullptr) {
    MLOG(WARN) << "Perception acuire read block failed, topic=" << topic_name;
    return absl::InternalError("read shm block failed");
  }
  // 取到真实像素首地址（cuda_data()，GPU共享内存）
  img_out->set_data(reinterpret_cast<const char*>(read_block->cuda_data()),
                    read_block->real_msg_size());
  img_out->set_data_storage(DATA_STORAGE_POINTER);  // 标记: data是指针/映射而非拷贝
  shm_blocks_.emplace_back(std::move(read_block));  // 持有引用防共享内存被发布方复用
}
```

> 文件路径：/sandbox/platform/church/node/shm/shm_pool.h  
> 函数名：ShmPool::AcquireReadabledBlock / AddSegment  
> 核心逻辑：

```cpp

                  uint64_t ceiling_real_msg_size = 16 * 1024);
  // key+index 定位块；seq 与块内序号比对：不一致说明数据已被发布方覆盖
  ShmBlockPtr AcquireReadabledBlock(const std::string& key, uint32_t index,
                                    uint64_t seq);
 private:
  std::unique_ptr<ShmPoolImpl> impl_;   // 实现在未检出的 .cc 中
};
```

逻辑说明：**shm pool**（共享内存池）按 topic 分段、段内固定块数轮转。`seq`（序号）机制是防读撕裂的关键：发布方写第 index 块时递增 seq，读取方带 seq 读取，若不匹配则说明该块已被新消息覆写，读取失败。读取成功后**必须持有 ShmBlockPtr**（存入 `shm_blocks_`），否则发布方可能立即复用该块；本帧结束后 `shm_blocks_.clear()` 释放。点云侧 `ReadPointCloudMayFromShareMemory` 同理，`DATA_STORAGE_SHM` 判断后同样 `set_data_storage(DATA_STORAGE_POINTER)`。这套「零拷贝通道」的入口细节见 [**Perception/01 输入**](01%20输入数据接入与预处理.md)，与 [**FrameSync**（公共 02 §3）](../00_公共基础文档/02%20模块配置与%20Topic%20数据流拓扑（C01%20-%20orinx）.md) 的 12 路同步配合使用。

## 4. 数据拷贝策略

**一句话结论**：指针传递为主深拷贝为辅——只共享不复制；必要拷贝只有跨进程 shm 索引与 FrameContext 快照两处。

### 4.1 指针传递为主，深拷贝为辅

> 文件路径：/sandbox/platform/church/node/onboard_message.h  
> 函数名：OnboardMessage  
> 核心逻辑：

```cpp
class OnboardMessage {
  deeproute::common::Header header;
  std::shared_ptr<ProtoBaseMsg> payload;   // 载荷为shared_ptr，跨组件共享
  // lazy_payload：payload 可延迟解析（先传指针，用到再反序列化）
  uint64_t GetSourceTimestampOrDataplaneTimestamp() const;
};
```

逻辑说明：Church 框架内所有消息统一包成 OnboardMessage，payload 是 `shared_ptr<ProtoBaseMsg>`——**同一份 proto 对象被下游共享只读**，不做逐组件深拷贝。深拷贝只发生在两类必要处：

1. **跨进程大消息**：数据本体留在共享内存，proto 里只放索引字符串（3.1节）——"零拷贝"；
2. **FrameContext 快照**：`BuildSnapshot` 用 CopyFrom 复制 NnFrame，因为快照要脱离槽位生命周期发布。

> **📘 概念｜ObjectPtr 只读共享（shared_ptr 所有权约定）**
> **是什么**：感知全链路的指针纪律——数据用 `shared_ptr<const T>`（或 XxxConstPtr 别名）传递，「复制指针不复制数据」：一帧装配完成后内容不可变，下游各节点拿到的都是指向同一份内存的只读引用，改不了也不需要改。它与深拷贝的区别：深拷贝人人有一份、改了互不影响但贵；只读共享人人看一份、零拷贝但前提是「没人写」——整个 E2E 流水线按「每帧数据只流一趟」组织，天然满足这个前提。真正的可变状态被收敛到 PerceptionSharedData/FrameContextManager 两个带锁黑板（§1.3），不与只读流混在一起。
> **类比与角色映射**：ObjectPtr 只读共享是「博物馆的展柜参观制」——展品（数据）只放一份，游客（calculator 节点）领导览图（shared_ptr）排队看，看可以、摸不行（const）；最后一位游客离场（引用计数归零）展品才撤（内存释放），不用任何人操心「谁记得关门」；个别「必须带走的东西」（FrameContext 快照、跨进程消息）才走礼品店复印（CopyFrom/序列化）。真实数字：PerceptionProcessInput 约 22 个字段全是 `shared_ptr<const T>`（§1.1）；msg_type.h 全部别名 ConstPtr；OnboardMessage.payload 是 `shared_ptr<ProtoBaseMsg>`（§4.1），lazy_payload 还能先传指针、用到再反序列化。
> **🎯 为什么这样设计**：E2E 一帧数据在图上要被十几个节点读——深拷贝会把延迟和内存放大十几倍；只读共享把拷贝成本压到一次指针复制（原子计数）；「不可变+共享」也让多线程并发读无需加锁（有锁的黑板只有那两处），是延迟与安全的平衡点。
> **🗂 代码在哪里**：perception/util/msg_type.h（全部 ConstPtr 别名）；perception_component_api.h（PerceptionProcessInput 全 const shared_ptr 字段）；onboard_message.h（payload shared_ptr）；buffer.h MsgBuffer（(时间戳, ConstPtr) 环形缓冲）。
>
> **30 秒最小例子**：一帧点云 8MB 到达。FrameSync 组帧后 PerceptionProcessInput.point_cloud 指向 shm 块（真数据在共享内存，§3.1）；lidar 子图读它做补偿、tracker 读它做辅助、异常监控读它算噪声占比——三个节点先后执行，谁都没有复制过这 8MB，全靠同一个 shared_ptr；shm_blocks_ 一直持有 ShmBlockPtr——只要指针还在，发布方就不能覆写这块内存，本帧结束 clear() 才归还块。

### 4.2 OnboardMessageConstPtrVector 语义

`OnboardMessageConstPtrVector = std::vector<OnboardMessageConstPtr>`（msg_type.h）。它出现在 calculator 输出端口签名中，语义是"**一批消息的只读句柄集合"：Vector 本身随 Packet 在图上复制，但每个元素是 const shared_ptr——复制 vector 不复制消息体**。FrameDoneCalculator 拿到它后按 topic 分发发布（见 5 节）。**推断**：这种设计保证发布路径不因 vector 扩容触发 proto 深拷贝。

### 4.3 GPU 数据显式 Buffer 化

PerceptionSharedData 中 GPU 外参矩阵全部用 `deeproute::os::hpc_hal::Buffer<float>` 而非裸指针（源码注释："GPU参数全部改为Buffer"、"Buffer替换裸指针"），托管 GPU 显存生命周期，避免悬垂。这些外参矩阵（lidar→camera 投影、相机内参、颜色变换）会在 GPU 预处理阶段被推理引擎读取——GPU 侧如何用它们把图像/点云变换成模型输入，见 [**CUDA 与 GPU 预处理**](../../../正典阁/技术栈/AI/CUDA%20与%20GPU%20预处理.md)。

## 6. FAQ 与自测

**FAQ**：

**Q1：shared_ptr 复制是不是很贵/线程不安全？**（新手常见误解）
不贵且安全。复制只是原子引用计数+一次指针赋值，远低于任何数据拷贝；const shared_ptr 并发读无需加锁——本设计正是靠「不可变」绕开锁，有锁的黑板只有 PerceptionSharedData/FrameContextManager 两处（§4.1）。

**Q2：为什么没有对象池？每帧新建不浪费吗？**
每帧 make_shared 新建输入/输出聚合体（不复用旧对象防脏数据，§2.1）；真正的重内存（点云/图像）本来就躺在 shm pool 里零拷贝，聚合体只是几十个指针的壳，新建成本可忽略。

**Q3：FrameContext 为什么不走图流？**
它是「上一帧遗留信息」的跨帧侧写（NN 输出缓存/状态），而图流是单帧语义；走单例槽位+锁，每 10 帧发 1Hz 快照（§2.2）。

**Q4：队列满了会丢消息吗？**
图级 ADD_IF_NOT_FULL 阻塞注入不丢弃；ChannelCache 环形缓存满则 Push 失败打 WARN；真正的丢帧发生在上游 throttle（见 [**Perception/06 异常**](06%20异常处理与容错机制.md)）——「阻塞注入+上游限流」分工（§3.3）。

**自测**：
1. PerceptionProcessInput 的字段为什么全是 `shared_ptr<const T>`？
    装配完即不可变，全链只读共享零拷贝，多线程并发读免锁。
2. shm pool 的 seq 机制防什么？
    防读撕裂：发布方写块时递增 seq，读取方 seq 不匹配说明块已被覆写，读取失败而非读到半新半旧数据；读到的块靠持有 ShmBlockPtr 防发布方复用。
3. /perception/objects 为什么最后发布？
    先数据后触发：规划收到它（触发话题）才去读其余四个 topic，保证可见性（frame_done_calculator.cc 注释明确此顺序契约）。

## 小结

- 每帧一进一出：PerceptionProcessInput（只读）进、PerceptionProcessOutput 出，shared_ptr 全程零拷贝共享；
- 大消息走 shm pool（topic分段 + seq防覆写 + ShmBlock持有防复用），proto 只传索引；
- 可变状态收敛在 PerceptionSharedData / FrameContextManager 两个带锁的"黑板"；
- FrameContext 每10帧发布快照，槽位轮转防跨帧污染；
- 输出按"先数据后触发"次序发布，/perception/objects 是规划的时间锚点。
