# 05 输出发布与中间件交互

> 所属专项：C01 车型 E2E 架构拆解（子 Agent3-1：Perception 通用机制）。  
> 上游阅读：《00_Perception 模块架构总览》§3/§5、《01_输入数据接入与预处理》§2。  
> 名词：**PerceptionProcessOutput**（感知算法子图的聚合输出结构体，各成员对应一个输出 proto）；**ProtoBaseMsgPtrVectorMap**（topic 名 → proto 消息向量的映射，FrameDoneCalculator 的输入）；**Topic Supervision**（话题监督，中间件对该 topic 的发布频率/活性做健康监控）。

## 2. 输出数据组装逻辑

算法子图内的组装链：`PerceptionOutputProcessCalculator`（语义加工，写入 `PerceptionProcessOutput` 各成员）→ `PerceptionOutputTransformCalculator`（结构体 → topic→proto 映射）→ `FrameDoneCalculator`（按序发布，§3）。子图内相关节点见 /sandbox/perception/perception/cfg/graphs/graph_l2avp.cfg（`PerceptionOutputProcessCalculator` 带 `FINAL_*` 标签，`PerceptionOutputBackupCalculator` 在缺真实结果时产出兜底数据）。

## 3. FrameDoneCalculator 发布顺序契约

外层图配置（/sandbox/driver/config/component/perception_graph_l2avp_orin.cfg）：

> ```text
> node {
>   name: "perception_frame_done"
>   calculator: "FrameDoneCalculator"
>   input_stream: "INPUT:perception_process_output"
> 
>   # Keep this sequence to ensure the planning module receives the trigger
>   # topic (/perception/objects) after the other four input topics.        ← L150-151 契约注释
>   output_stream: "OUTPUT:0:perception__extra_objects"
>   output_stream: "OUTPUT:1:perception__ras_map"
>   output_stream: "OUTPUT:2:perception__ras_map_parking"
>   output_stream: "OUTPUT:3:perception__traffic_lights_status"
>   output_stream: "OUTPUT:4:perception__objects"                          ← 触发 topic 最后发
> 
>   output_stream: "OUTPUT:5:perception__obstacle3d_nn"
>   ... "OUTPUT:6:perception_aeb__objects" ... "OUTPUT:18:perception__frame_context"
>   output_stream: "ALL_OUTPUTS:perception_output_vector"
>   output_stream: "TRIGGER:perception_done"
>   input_side_packet: "TOPIC_TO_STREAM_ID_MAP:perception_topic_to_stream_id_map"
>   input_side_packet: "GENERATE_HEADER_CALLBACK:perception_generate_header_callback"
>   input_side_packet: "STREAM_PUBLISH_OBSERVER:perception_stream_publish_observer"
> }
> ```
> 
> 逻辑说明：`OUTPUT:0~4` 的次序是**给规划模块的时序契约**——先发规划会消费的 4 路输入（extra_objects/ras_map/ras_map_parking/traffic_lights_status），最后发触发 topic `/perception/objects`，确保规划被触发时其余输入已在中间件队列中（注释原文证据）。topic→流序号由 side packet `TOPIC_TO_STREAM_ID_MAP` 注入。

> 文件路径：/sandbox/platform/church/graph/calculators/frame_done_calculator.cc  
> 函数名：FrameDoneCalculator::Process()  
> 核心逻辑：
> 
> ```cpp
> absl::Status Process(CalculatorContext* cc) final {
>   const auto& input_message_map =
>       cc->Inputs().Tag(kInputTag).`Get<ProtoBaseMsgPtrVectorMap>`();        // topic→消息向量
>   for (const auto& [topic, messages] : input_message_map) {
>     if (topic_to_stream_id_.count(topic) == 0) { MLOG(ERROR) << "Topic not found in mapping: " << topic; continue; }
>     const int stream_id = topic_to_stream_id_[topic];
>     for (size_t i = 0; i < messages.size(); ++i) {
>       auto onboard_message = generate_header_callback_(topic, messages[i]); // 包一层 OnboardMessage 信封
>       cc->Outputs().Get(kOutputTag, stream_id)
>           .AddPacket(`MakePacket<OnboardMessageConstPtr>`(onboard_message)
>                          .At(Timestamp(cc->InputTimestamp() + i)));      // L150-158
>       if (stream_publish_observer_) stream_publish_observer_(onboard_message);
>     }
>   }
>   ... // ALL_OUTPUTS 汇总所有 OnboardMessage（调度事件记录用）
>   frame_id_++;                                                            // L169
>   cc->Outputs().Tag(kTriggerTag)
>       .AddPacket(`MakePacket<int>`(frame_id_).At(Timestamp(cc->InputTimestamp()))); // L170-172
>   return absl::OkStatus();
> }
> ```
> 
> 逻辑说明：按 `topic_to_stream_id_` 把每条消息发到对应 `OUTPUT:stream_id` 端口（时间戳微调 +i 保持同帧序）；`TRIGGER` 流输出**自增帧号**，经 back_edge `perception_done` 回灌 FrameSyncCalculator 的 FINISHED 输入，构成帧级节拍闭环（见《01》§2.3 第 4 条背压机制）。找不到映射的 topic 报错跳过，不阻塞其余输出。

## 4. 发布时机与频率

帧同步是整个输出链的节拍源，一帧数据的端到端发布时序：

- **出帧条件**：FrameSync 全同步或超时装配成功，且 `FrameStateMachine` 允许输出（在途帧 < 2 且有 TRIGGER 信用，frame_sync_calculator.cc L57-68、L132-143）。
- **帧内发布顺序**：由 FrameDoneCalculator `OUTPUT:0~4` 次序保证（§3 契约）。
- **下一帧放行条件**：子图尾部 `TriggerNextFrameCalculator` 在 DRIVING 模式下要求 `lidar_done && uni_model_done && ras_map_done` 三路完成才向 FrameSync 的 TRIGGER 流输出信用（/sandbox/perception/perception/calculators/trigger_next_frame_calculator.cc L109-125）；泊车等其他模式按各自分支放行。
- **频率**：基准节拍来自相机 `frame_nano_base: 100000000`（100ms 分桶），理论 ≈10Hz；实际发布率受算法耗时、`kMaxFramesInFlight=2` 并行度与三路 done 条件共同约束（**推断**：未在代码中找到显式频率常量，频率为帧同步分桶与调度共同决定的结果）。
- **监督**：`/perception/objects`、`/perception/ras_map` 开启 `need_topic_supervision`（jsonnet L269/L320），断流会被话题监督捕获（框架级健康监控）。

## 5. 与 Planning 交互协议

### 5.1 正向：/perception/objects 触发语义

- planning 侧以 `/perception/objects` 为 **TRIGGER 且 IMMEDIATE**：planning.jsonnet input_channels 声明订阅 → planning_graph.cfg `planning_assemble_node` 消费（基线 5，本文不重复验证）。
- 感知侧保障两点：① `/perception/objects` 每帧必发布（即使空结果——FrameDone 发的是 `PerceptionProcessOutput.objects`，为空的帧该 topic 缺席，**推断**规划侧依赖 ros wrapper/中间件超时兜底，未验证空帧行为）；② 其余 4 路规划输入先于触发 topic 发出（§3 cfg 注释契约）。
- 障碍物消息内嵌协议字段：`curr_driving_mode`（当前行驶模式，ProcessObjectResultInternal L787-788）与 `invisible_sector`（相机数据不全标记，L754-763）是感知→规划的**隐式协议**，规划据此理解结果的置信边界。

### 5.2 反向：/planner/trajectory 回灌 prediction

> 文件路径：/sandbox/perception/perception/calculators/perception_input_transform_calculator.cc  
> 函数名：TransformInputMsgsToProcessInput()  
> 核心逻辑：
> 
> ```cpp
> {
>   onboard_msg = FindFirstMessage(input_msgs, "/planner/trajectory");
>   if (onboard_msg) {
>     auto adc_trajectory =
>         std::`dynamic_pointer_cast<const deeproute::planning::ADCTrajectory>`(
>             onboard_msg->payload());
>     process_input.adc_trajectory = adc_trajectory;                      // L779-787
>   }
> }
> ```
> 
> 逻辑说明：感知把规划上一周期输出的 `deeproute.planning.ADCTrajectory` 塞回 `PerceptionProcessInput.adc_trajectory`，供子图内 `PredictionWithPlannerCalculator`（graph_l2avp.cfg 节点）做**基于自车规划轨迹的他车预测**——形成"感知→规划→感知"的闭环。jsonnet 中该通道声明 `type: "optional"`（有新轨迹才带上，取 `FindFirstMessage` 最新一条）；ROS 模式对应 `InitAdcTrajectorySub`（ros_wrapper.cpp）。规划轨迹缺失时 `adc_trajectory` 为空，prediction 走无轨迹先验分支（**推断**，具体分支逻辑属子模块文档范畴）。
