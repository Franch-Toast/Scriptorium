> **本篇概念速成块**（30 秒，读完再进正文不卡壳）：
> - **三层容错**：预防（上游打包降频）→ 容忍（超时装配残缺帧）→ 重启（连续 10 帧限流 FATAL）——异常不是一层解决的（§1）。
> - **超时装配**：100ms 没凑齐也照样发——「能装多少装多少」，保 10Hz 拍点稳定（§1.2；FrameSync 完整卡片见 [**公共 02 §3**](../00_公共基础文档/02%20模块配置与%20Topic%20数据流拓扑（C01%20-%20orinx）.md)）。
> - **背压 kMaxFramesInFlight=2**：处理慢时新帧先不装配（入口侧机制见 [**在途帧背压**（Perception/01 §2.3）](01%20输入数据接入与预处理.md)）。
> - **错误处理三种姿势**：关键路径 fail-fast、非关键 log-and-continue、未知 topic 跳过——分级处置不搞一刀切（§2.1）。
> - **WatchDog vs ChannelSuspendAlarm**：前者看「还有没有帧」（1s），后者看「哪一路断了」（30s）——都是只告警不重启的哨兵（§3）。
> - **崩溃三段接力**：信号接管→回收+日志落盘（5s 超时保护）→逐组件上报后退出（§4）。
> - **RECOVERY_RESET**：感知没有「部分重启」——FATAL/崩溃后 DrDEM 整体重启 mainboard，四组件一并重启（§5）。

## 1. 输入异常：帧同步超时与丢帧

**一句话结论**：输入异常三层设防——上游打包降频（预防）、FrameSync 超时装配残缺帧（容忍）、连续 10 帧注入限流 FATAL（重启）。

**为什么容错要分三层**：单帧缺一路相机不值得重启，消费持续积压才值得——三层设防让系统对「小病容忍、大病重启」，把异常的处置代价与它的严重程度对齐。这也是所有高可用系统的通用思路，感知只是把它落在了帧节拍上。

> 函数名：GraphScheduler::FillSidePacketsForFrameSync（449-530行）  
> 核心逻辑：

```cpp
// 把配置注入 FrameSyncCalculator 的 side packet：
//   FRAME_SYNC_TIMEOUT  → task().frame_sync_timeout()（未配置用默认100ms）
//   SETUP_TIMER_CALLBACK → timer_.Emplace(...) 定时器注册
// 定时器触发时：
//   graph_->AddPacketToInputStream(timer_stream, packet)
//   // 带着超时事件进入图 → FrameSyncCalculator 执行 TimeoutAssemble
// 限流保护：
//   if (fatal_on_throttle) {
//     if (++consecutive_throttled >= 10) {
//       MLOG(FATAL) << "Graph input stream throttled for " << count
//                   << " consecutive frames, triggering restart.";
//     }   ← 连续10帧注入失败直接致命退出（触发进程重启）
```

逻辑说明：**frame_sync_timeout**（帧同步超时）默认 100ms，perception_orin.jsonnet 未覆写即生效。超时不是"放弃本帧"而是**降级装配**（见 1.2）；真正致命的是**注入限流**：组件消费不过来导致输入流满（`ADD_IF_NOT_FULL` 下注入阻塞/失败），连续 10 帧后 `MLOG(FATAL)` 主动结束进程——宁可重启也不带着积压跑。

### 1.2 超时装配与最大在途帧数

> 文件路径：/sandbox/platform/church/graph/calculators/frame_sync_calculator.cc  
> 函数名：FrameSyncCalculator::TimeoutAssemble（460-495行）与帧状态机  
> 核心逻辑：

```cpp
// kMaxFramesInFlight —— 最大在途帧数（C01 orin 平台为 2）：
#if defined(DR_VEHICLE_C01_PT) || defined(ORIN_PLATFORM)  // 57-68行（示意）
constexpr int kMaxFramesInFlight = 2;
#endif
// 帧状态机 FrameStateMachine::CanOutput()：
//   在途帧 ≥ kMaxFramesInFlight 时不再输出新帧（背压）

// TimeoutAssemble(timeout_frame_id)（460-495行）：
//   1. 若该帧已被取消 → 忽略
//   2. 若更高帧已处理过（higher_frame_processed）→ 跳过旧超时帧
//   3. 否则按各 topic 的 ChannelInputType 语义"尽力装配"残缺帧输出
//      （REQUIRED 缺失的通道为空，下游需容忍）
// 乱序保护（BreakingOrderNotifier）：
//   MLOG(WARN) << "frame sync state has been reset, due to breaking-order"
//   // 乱序消息到达后复位帧同步状态机

// 非帧同步输入的装配语义（AssembleNonFramesyncInputs）：
//   ALL_NEW  → 循环 ConsumeOld 取全部新消息
//   REQUIRED → GetNewest（必须有，否则本路为空）
//   OPTIONAL → ConsumeNew（可选，缺了不报错）
//   NEAR     → 取时间戳最近
```

逻辑说明：FrameSyncCalculator（**帧同步计算器**）对超时的处理是"**能装多少装多少**"：`TimeoutAssemble` 输出残缺帧而非丢弃，保证 10Hz 拍点稳定；同时用 `kMaxFramesInFlight=2` 限制同时在途帧数形成背压——处理慢时新帧先不装配，等待 `TriggerNextFrameCalculator` 回边放行。12 路 REQUIRED 输入全部齐套则提前触发（无需等超时）。**FrameSync 帧同步**的完整机制卡片见 [**公共 02 §3**](../00_公共基础文档/02%20模块配置与%20Topic%20数据流拓扑（C01%20-%20orinx）.md)；入口侧背压与 12 路通道语义见 [**在途帧背压**（Perception/01 §2.3）](01%20输入数据接入与预处理.md)。

## 3. 框架级监控

**一句话结论**：框架级监控只告警不重启——WatchDog 看图级「有没有帧」（1s）、ChannelSuspendAlarm 看「哪一路断了」（30s）、AnomalyMonitor/ScheduleMonitor 盯组件健康与调度事件。

## 5. 降级与恢复

**一句话结论**：降级分帧级/进程级/系统级三档——帧级残缺输出靠算法容忍，进程级 FATAL 退出走崩溃接力，系统级 RECOVERY_RESET 由 DrDEM 整体重启；感知没有"部分重启"。

```mermaid
flowchart TD
    A[连续10帧注入限流 fatal_on_throttle] --> F[MLOG FATAL 退出进程]
    B[段错误 abort 未捕获异常] --> G[信号接管 failure_writer刷日志]
    C[上游断流] --> H[WatchDog 1s WARN
ChannelSuspendAlarm 30s WARN]
    G --> R[ModuleCrashReporter
ReportAllComponentsAbnormalExit]
    F --> R
    R --> D[进程退出]
    D --> E[DrDEM 按recovery_method
RECOVERY_RESET 重启mainboard]
    H -->|人工/上层决策| E
```

**图 5-1 · 异常与降级处理链路（从异常源到 DrDEM 重启）**（A/B/C 三类异常源：FATAL 与真崩溃自动走重启，断流只告警）

**读图提示**：① 三条入口对应三类异常——注入限流 FATAL（A）、真崩溃（B）、断流告警（C）；② G→R 是崩溃三段接力的后两段：日志落盘完成才逐组件上报；③ 断流路径（C→H）只打 WARN，重启决策留给人工/上层；④ 所有 FATAL/崩溃的终点都是 DrDEM RECOVERY_RESET 整体重启，感知不"带病运行"。

降级层级总结（对照代码证据）：

| 层级 | 机制 | 后果 | 证据 |
|-|-|-|-|
| 帧 | FrameSync 超时装配 | 残缺帧输出，下游容忍 | frame_sync_calculator.cc TimeoutAssemble |
| 帧 | kMaxFramesInFlight=2 | 背压限流，处理慢时缓收帧 | 同上（C01_PT 条件编译） |
| 进程 | fatal_on_stream_throttle 连续10帧 | MLOG(FATAL) 主动重启 | graph_scheduler.cc FillSidePackets |
| 进程 | 崩溃信号接管+上报 | 日志落盘→上报→退出 | church_main.cc / module_crash_reporter.cc |
| 系统 | DrDEM RECOVERY_RESET | 重启 mainboard 进程 | 感知组件配置 dem_launch 字段；**DrDEM 源码未检出，重启退避策略未验证** |

> 文件路径：/sandbox/driver/config/component/perception_orin.jsonnet  
> 函数名：dem_launch 配置段  
> 核心逻辑：

```jsonnet
dem_launch: {
  recovery_method: "RECOVERY_RESET",   // 异常退出后由守护进程整体重启
},
```

逻辑说明：感知没有进程内的"部分重启"——组件配置的恢复方式是 `RECOVERY_RESET`（整体重置）：任何 FATAL/崩溃后由 **DrDEM**（守护进程管理器）重启整个 mainboard（四个 church 组件随之一并重启）。帧级异常（残缺帧）则完全交给算法自行容忍，不升级为重启。**推断**：残缺帧频率过高会体现在 AnomalyMonitor 的发布频率/耗时指标中，间接促发运维介入。

```cpp
}
```

逻辑说明：MLOG 底层是 **spdlog 异步 logger**：业务线程只做入队（10000 深度队列），名为 "async_logger" 的专用后台线程负责格式化落盘（对应 perception.json 中 async_logger 条目，SCHED_OTHER priority -10）。`flush_on` 保证 ERROR 级别以上即时刷盘；队列溢出策略由 `GetAsyncOverflowPolicy` 决定（具体取值未验证）。崩溃路径 failure_writer 会强制刷队列（"Church async_logger flush successful"），保证致命错误日志不丢。

### 6.2 日志在容错体系中的角色

- **WARN 级**：WatchDog 无帧 / ChannelSuspendAlarm 断流 / 读 shm 失败 / 乱序复位——供车端日志检索定位；
- **ERROR 级**：未知 topic 跳过等单点失败，触发 flush；
- **FATAL 级**：主动重启开关（throttle 连续10帧、配置错误），进入崩溃链路。

## 7. FAQ 与自测

**Q1（新手常见误解）**：感知异常"降级"后，是不是只重启出问题的那几个组件？
不是。感知没有进程内的"部分重启"——dem_launch 配置的恢复方式是 `RECOVERY_RESET`（整体重置）：任何 FATAL/崩溃后由 DrDEM 重启**整个 mainboard**，四个 church 组件一并重启。帧级异常（残缺帧）则完全交给算法容忍，不会升级为重启——降级粒度只有"帧"和"整个进程"两档。

**Q2**：WatchDog 告警 "There is no incoming frame" 之后系统会自动重启吗？
不会。WatchDog 只打 WARN 上报监控平台，由人工/上层决策；它也不区分"上游没发"还是"处理卡死"。自动触发重启的只有两处：fatal_on_throttle 连续 10 帧注入限流的 MLOG(FATAL)，和真崩溃（段错误/abort，走崩溃接力链路）。

**Q3**：为什么 MLOG 打日志不会拖慢实时线程？
MLOG 底层是 spdlog 异步 logger：业务线程只把日志放进 10000 深的内存队列就返回，名为 async_logger 的后台线程（优先级压到 -10/-15，让位于业务）负责格式化落盘。ERROR 以上等级触发即时 flush；崩溃路径 failure_writer 会强制刷队列，保证致命错误日志不丢。

**Q4**：超时装配输出的残缺帧，下游怎么知道数据不全？
装配按各 topic 的 ChannelInputType 语义"尽力而为"：REQUIRED 缺失的通道为空、需下游容忍；相机数据不全的帧还会附加空 invisible_sector 字段显式告知规划（输出侧见《05 输出发布与中间件交互》§2.1）。

**自测**（先自己想，再看答案）：

1. fatal_on_stream_throttle 连续多少帧注入失败会触发 MLOG(FATAL)？之后是重启单个组件还是整个进程？
    连续 10 帧；MLOG(FATAL) 结束整个进程，由 DrDEM 按 RECOVERY_RESET 重启 mainboard（四个组件一并重启）。
2. WatchDog 和 ChannelSuspendAlarm 的监控粒度与阈值分别是什么？
    WatchDog 看图级"有没有帧"：最后收到新输入超过约 1s（kWaitMsgArrivedMaxTimeNs≈1s）打 WARN；ChannelSuspendAlarm 看单通道"哪一路断了"：已配置 topic 超过 30s 无新消息打 WARN。
3. 崩溃链路的三段接力是什么？哪一步有 5s 超时保护？
    信号接管（glog failure handler 挂入回收回调）→ 资源回收+日志落盘（WaitForReclaimDone 5s 超时，防回收卡死）→ ModuleCrashReporter 逐组件上报异常退出后进程退出，交给 DrDEM 重启。
