> **本篇回答**：核心数据结构怎么关联？配置优先级谁高谁低？gflags 怎么调？

> **本篇概念速成块**（30 秒，读完再进正文不卡壳）：
> - **单帧三主件**：PlanningFrameData（输入装配包）→ Frame（帧内世界模型，完整卡片见 [**Planning/00 §2**](00%20Planning%20模块架构总览.md)）→ PlanningFrameDataOutput（输出包）。
> - **跨帧记忆**：FrameContext proto 经 `/planner/context` 回环——上一帧的选中轨迹/参考线摘要供下一帧拼接（通道拓扑见 [**公共 02**](../00_公共基础文档/02%20模块配置与%20Topic%20数据流拓扑（C01%20-%20orinx）.md)）。
> - **FrameContext ≠ Context**：前者是 proto 大消息，后者是带锁的 C++ 封装类。
> - **所有权四策略**：输入层 shared_ptr 共享读、图流转 Consume 移动、跨帧拷贝+锁、跨线程原子握手（详见 [**ObjectPtr 只读共享**（Perception/03 §4.1）](../Perception/03%20关键数据结构与内存管理.md) 的同族思想）。
> - **配置三层**：gflags 代码默认 → jsonnet 叠加链（风格/车型包） → MDCHECK 运行期硬校验。
> - **jsonnet 的 +**：基础 em 配置 + 风格包（casual/standard/sports）+ 车型包——驾驶风格注入就靠它。
> - **trajectory_type**：ADCTrajectory 直接编码 NORMAL/PATH_FALLBACK/SPEED_FALLBACK，降级语义在 proto 层就有（详见 [**Planning 06 异常与降级**](06%20异常处理与降级机制.md)）。


> 适用范围：C01（orinx 平台 C01PT，`/task/task_type=L2_driving`）E2E 主进程 perception mainboard 中的 PlanningComponent。  
> 代码根目录：`/sandbox/planning/planning/`。本文所有结论均给出代码证据，推断处已标注。

## 1. 核心结构体

**一句话结论**：单帧数据主干是"输入包→Frame→输出包"三件套，跨帧记忆靠 FrameContext proto 回环——每个结构体的生命周期都严格单帧或严格跨帧，不混。

**为什么数据结构值得先讲**：规划是 300 多个任务协作的流水线，而流水线上所有工序只认两种"工件"——Frame 和 ReferenceLineInfo；搞不清它们的字段与生命周期，看任何 Task 的代码都是雾里看花。本篇就是这两份"工件图纸"，后续子模块篇反复引用它。

## 2. 数据所有权与拷贝策略

**一句话结论**：四条策略各司其职——输入共享读、流转移动、跨帧拷贝加锁、跨线程原子握手，目标都是同一个：别在大 proto 上做无谓拷贝，也别在并发点上裸共享。

规划数据的传递策略可总结为：**输入层共享指针（零拷贝读），中间层原地写，输出层移动语义，跨线程拷贝**。

1. **图内流转：unique_ptr/移动优先**。Calculator 间大对象用 `Consume`（mediapipe 移出）：

> 文件路径：/sandbox/planning/planning/calculators/planning_core_calculator.cc  
> 函数名：PlanningCoreCalculator::Process()
> 
> ```cpp
> auto input_data = cc->Inputs()
>                       .Tag(kInPlanningFrame)
>                       .Value()
>                       .`Consume<DeepRoute::planning::PlanningFrameData>`()
>                       .ValueOrDie();   // 把上游 PlanningFrameData 移动过来
> ```
> 
> 逻辑说明：`Consume` 使流包的所有权被独占移动，避免大 proto 拷贝；`PlanningPostProcessCalculator::Process()`（planning_post_process_calculator.cc L80\~85）同样对 `PlanningFrameDataOutput` Consume。

1. **PlanningFrameData 内部：shared_ptr 共享读**。所有上游消息成员都是 `shared_ptr`（planning_api.h L51\~79），Frame/Preprocess 只读解引用；感知 obstacles 拷贝一次到成员（`perception_obstacles_->CopyFrom`，见 1.1）后共享。Frame 中则用裸指针 + 堆持有者双轨（frame.h L4690\~4700：`perception_obstacles_ptr_` 与 `perception_obstacles_heap_holder_`），并引入 `ArenaManager`（protobuf arena，减少重复分配）。
2. **跨帧上下文：拷贝 + 锁保护读**。FrameContext 是值语义 proto：每帧由 `CopyFrom` 继承（planning_input_preprocess_calculator.cc L173 `frame_context_->CopyFrom(*last_frame_context_)`），而并发访问点（Context）用 mutex + 返回拷贝接口（frame/context.h `GetLastSelectedTrajectorySafe` 注释："从 Context 中安全读取轨迹（返回拷贝，避免竞争）"）。
3. **跨线程：任务闭包捕获 this，结果用 atomic 标志**。open-space 异步线程把 `plan_finish_` 设为 release，主线程 acquire 读取（open_space_planning_async_manager.cpp L192、L214）。
4. **障碍物：`shared_ptr<Object>`（ObjectPtr，内存模型详见 [**Perception/03 §4.1**](../Perception/03%20关键数据结构与内存管理.md)）**。`std::unordered_map<ObstacleId, ObjectPtr> obstacles_`（frame.h L4719），参考线只 AddObstacle 挂引用，不做深拷贝；`PathDecision` 内以指针集合持有（推断，依据 path_decision.h 存在 mutex 与指针 Items() 接口）。
5. **protobuf 修辞性拷贝仍存在**：输入预处理器对 `/perception/objects`、`/map/fusion_map` 等做 `CopyFrom`（planning_input_preprocess_calculator.cc L360、L563），这是因为 church 图消息为 const payload，需要可变本地副本。

## 5. FAQ 与自测

**Q1（新手常见误解）**：FrameContext 和 Context 是同一个东西的两种叫法？
不是。`FrameContext` 是 proto 定义的大消息（跨帧回环的"上一帧记忆"载体，经 `/planner/context` 发布）；`Context` 是 planning 内部的 C++ 封装类，持有 `shared_ptr<FrameContext>` 并加互斥锁，提供 `GetLastSelectedTrajectorySafe` 这类"返回拷贝"的线程安全接口——一个是数据本体，一个是带锁的访问门面（§1.2）。

**Q2**：为什么输入层用 shared_ptr 共享，图流转却要用 Consume 移动？
场景不同：PlanningFrameData 内的各上游消息在整帧内被多个计算节点只读复用，共享指针最省；而 PlanningFrameData 这个大包本身沿图单向流动，每个节点用完就不再需要，`Consume` 把所有权独占移动过去，避免整包深拷贝（§2 策略 1/2）。

**Q3**：为什么改了 jsonnet 里的参数还没生效？
检查三层：① gflags 默认值可能被启动参数覆盖（`parse_config` 指向的 jsonnet 路径本身就是 gflags）；② jsonnet 叠加链中后 import 的风格/车型包会覆盖基础配置；③ 即便加载成功，`Planning::Init` 的 MDCHECK 会把与车辆物理极限矛盾的配置直接拦下（进程起不来比静默生效好，§3.4）。

**自测**：

1. 规划的"跨帧记忆"载体是什么？怎么流转？
    FrameContext proto：PlanningCoreCalculator 输出 → 图回边（`back_edge: true`）送回输入预处理 → 同时经 `/planner/context` 发布给下游；C++ 侧经 Context 类带锁访问（§1.2）。
2. jsonnet 叠加（+）的作用是什么？
    把基础 em 配置与风格包（casual/standard/sports）、车型包（driving_ilqr/model）叠加组合，驾驶风格/车型差异注入的核心手段（§3.1）。
3. 启动时最硬的配置校验是什么？
    MDCHECK 校验速度规划的加/减速度配置不得超过车辆控制配置（VehicleConfigRetriever），违反直接终止进程（§3.4）。

## 小结

1. **单帧数据主干**：PlanningFrameData（shared_ptr 输入包）→ Frame（含 ReferenceLineInfo 列表与 obstacles）→ PlanningFrameDataOutput（shared_ptr 输出包）。
2. **跨帧记忆**：FrameContext proto（/planner/context 回环），C++ 侧 Context 类带锁。
3. **配置三层**：gflags（代码默认值）→ jsonnet 叠加链（车型/风格注入）→ MDCHECK 运行期校验。
4. **关键文件**：planning_api.h、frame/frame.h、frame/context.h、reference_line_info/reference_line_info.h、common/trajectory/discretized_trajectory.h、config/share/planning_internal_config.jsonnet、planning_gflags/planning/common/planning_gflags.cpp。
